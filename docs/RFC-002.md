RFC-002
Catalog Ingestion & Canonicalization

**상위·연관 문서**

- `RFC-000: Wine Intelligence Engine Master Architecture.md` — offline truth vs query-time decision·**행동신호 overlay는 ingestion에 역류 금지** (§3.4)
- `RFC-001: Entity Identity Graph SSOT` — merge·`identity_signature` 규칙·외부 ID 매핑
- `RFC-003` (Alias) — 이 RFC의 `alias_candidates`·노이즈 제목은 **catalog_noise_alias** 쪽으로 넘어감

0. 목적

RFC-001이 “정체성이 무엇인가” 를 고정했다면,
RFC-002는 “현실의 더러운 데이터가 어떻게 그 정체성으로 들어오느냐” 를 고정한다.

이 RFC의 한 줄은 이거다.

외부 카탈로그/마켓플레이스/수작업 데이터는 그대로 SSOT에 들어가면 안 된다.
반드시 canonicalization pipeline을 거쳐 Entity Graph로 승격되어야 한다.

이 레이어가 없으면:

marketplace title이 canonical label을 오염시키고
빈티지/생산자/지역이 잘못 붙고
alias와 identity 경계가 무너지고
결국 exact/entity 검색이 망가진다.
1. 비목표까지 포함한 핵심 정의
1.1 이 RFC가 하는 일
여러 source에서 raw catalog를 받는다
normalize한다
candidate entity를 만든다
merge / split / reject를 결정한다
최종적으로 RFC-001의 Entity Identity Graph에 반영한다
1.2 이 RFC가 하지 않는 일

| 하지 않음 | 비고 |
|-----------|------|
| retrieval ranking | 런타임 검색 |
| alias prior **동적** 튜닝 (클릭·bandit) | RFC-000 §3.4 — **core SSOT·이 파이프라인으로 역류 금지** |
| query-time interpretation | Query Planner 영역 |
| user-facing explanation | Response Builder |
| **온라인** 사용자 행동으로 canonical 덮어쓰기 | evidence는 별도 플라이휠(RFC-000 §14) |

즉 이 RFC는 **offline / batch data truth pipeline** 이다.

2. 설계 원칙
2.1 Source of Truth 계층 분리

반드시 3계층으로 분리한다.

Raw Source Record
→ Canonicalization Candidate
→ Entity Graph SSOT
→ Projection rebuild (RFC-001 §5)

절대 금지:

Raw marketplace title
→ 바로 canonical_label

**Idempotency:** 동일 `source_record_id` 재수집 시 **멱등**하게 처리한다 (중복 merge·이중 alias 삽입 방지).
2.2 Source는 truth가 아니라 evidence다

외부 소스는 정답이 아니다.

각 source record는 이렇게 취급한다.

SourceRecord = identity evidence + attribute hints + alias candidates

즉 source는 SSOT를 “정의”하지 않고, SSOT 형성을 위한 근거만 제공한다.

2.3 Append-only provenance

정규화와 병합은 덮어쓰기보다 계보(lineage) 를 남겨야 한다.

어떤 source에서 왔는지
어떤 규칙으로 normalize됐는지
어떤 merge decision이 있었는지

이게 남아야 나중에 wrong-top1 원인 추적이 된다.

2.4 Marketplace contamination 방지

리테일러/마켓 제목은 거의 항상 노이즈를 포함한다.

예:

Opus One Napa Red 750ml Gift Box Import
샤또 마고 프리미엄 선물세트
케이머스 나파 카베르네 750ML 미국와인

이런 값은 canonical label 후보가 아니라:

alias candidate
packaging/noise metadata
retail presentation evidence

로 처리해야 한다.

3. 입력 모델
3.1 RawSourceRecord
RawSourceRecord {
  source_record_id: string
  source_system: string
  source_type: "catalog" | "marketplace" | "retailer" | "manual" | "editorial"

  raw_title: string
  raw_subtitle?: string
  raw_description?: string

  producer_text?: string
  region_text?: string
  grape_text?: string
  vintage_text?: string
  price_text?: string
  volume_text?: string

  source_url?: string
  locale?: string
  currency?: string

  ingestion_timestamp: timestamp
}

핵심:

raw는 raw 그대로 저장
정규화 결과와 절대 혼합 금지
3.2 SourceTrustProfile

각 소스는 신뢰도 프로파일을 가진다.

SourceTrustProfile {
  source_system: string

  title_reliability: float
  producer_reliability: float
  region_reliability: float
  vintage_reliability: float
  attribute_reliability: float

  marketplace_noise_risk: float
}

예:

공식 생산자 사이트: producer/region 신뢰 높음
대형 마켓플레이스: title noise risk 높음
수작업 에디토리얼: description 좋지만 price 신뢰 낮을 수 있음

이건 merge conflict 해결에서 중요하다.

4. Canonicalization Pipeline

전체 흐름은 이렇게 간다.

Raw ingestion
→ Field normalization
→ Structured extraction
→ Noise stripping
→ Candidate generation
→ Entity matching
→ Merge / Split / Reject
→ SSOT write
→ Projection rebuild

4.1 Ingestion-to-Searchable SLA

Entity Graph 변경이 검색 결과에 반영되기까지의 **최대 허용 지연**을 tier별로 정의한다.

| Tier | 변경 유형 | 목표 SLA | 비고 |
|------|-----------|----------|------|
| **T0 (긴급)** | 잘못된 entity merge 수정, 위험 alias 제거 | **1시간 이내** | kill switch + hotfix 경로 |
| **T1 (신규)** | 새 entity 등록, 신규 vintage 추가 | **4시간 이내** | 정규 파이프라인 |
| **T2 (속성)** | attribute 변경, price_band 업데이트 | **24시간 이내** | 배치 처리 허용 |
| **T3 (보강)** | alias 추가, recall 보조 필드 갱신 | **48시간 이내** | 품질 검증 포함 |

**측정:** ingestion_timestamp → projection rebuild 완료 → index 반영 확인까지의 e2e latency를 모니터링. SLA 위반 시 알람.

**병목 관리:** projection rebuild가 SLA 병목이 되면 incremental projection update를 검토 (전체 rebuild 대비 정합성 검증 부담은 증가).

5. Field Normalization
5.1 문자열 정규화

최소한 다음은 공통 적용한다.

trim / whitespace collapse
lowercasing where safe
accent stripping
punctuation normalization
unicode normalization
volume / unit normalization
year parsing
locale-specific token normalization

예:

Château Margaux / Chateau Margaux
750ML / 750 ml
2018년 / 2018
5.2 언어/표기 normalization

와인 도메인에서는 반드시 처리해야 한다.

한글 음역
영문 표기
악센트 제거
붙여쓰기/띄어쓰기
흔한 축약형

단, 여기서 주의:

normalization 결과가 canonical label이 되는 게 아니다.
matching candidate를 만드는 재료일 뿐이다.

5.3 Noise token stripping

다음은 identity 토큰이 아니라 noise일 가능성이 높다.

gift box
import
sale
best
premium
750ml
set / bundle
행사 문구
retailer promo phrase

이 토큰들은 기본적으로:

canonical identity candidate에서는 제거
alias evidence나 packaging metadata에는 보존

한다.

6. Structured Extraction
6.1 추출 대상

raw record에서 최소 다음을 뽑아야 한다.

producer candidate
wine label candidate
vintage candidate
region/appellation candidate
grape candidate
packaging/volume candidate
gift/bundle/promo flag
6.2 extraction 결과 모델
CanonicalizationCandidate {
  candidate_id: string        // 이 파이프라인 run 내 유일 ID (lineage 연결)
  source_record_id: string

  normalized_title: string

  extracted: {
    producer?: string
    wine_label?: string
    vintage?: int
    region?: string
    grape?: string[]
    volume_ml?: int
  }

  noise_flags: string[]
  alias_candidates: string[]   // RFC-003: type 부여 전 **후보만**; catalog_noise·행사문구 구분은 downstream
  parsing_confidence: float    // 런타임 **calibrated C**(RFC-000 §8.4)와 동일 스케일 아님 — 혼동 금지
}
6.2.1 외부 식별자 (선택)

원본에 SKU / LWIN / 바코드가 있으면 `external_refs[]`로 보관한다. **RFC-001 §2.5** — `EntityId` 대체 금지, 매칭 **힌트**로만 사용.

6.3 원칙

추출 실패는 허용된다.
헛추출은 위험하다.

즉:

missing field > wrong field

이건 전체 시스템 철학과 같다.
틀린 확정보다 ambiguity가 낫다.

7. Entity Matching

여기서 RFC-001의 Entity SSOT와 연결된다. **merge 키는 RFC-001 `identity_signature` 규칙과 동일해야 한다** (wine vs vintage 분리).

7.0 금지

- **임베딩 단독**으로 merge/split 결정 금지 — 후보 순위·힌트로만 (틀린 확정 방지).

7.1 matching 대상

candidate는 아래 순서로 매칭한다.

exact identity hints
producer + label + vintage
producer + label
label + region
unresolved candidate
7.2 match 결과 상태
EntityMatchResult {
  status: "matched" | "ambiguous" | "new_entity_candidate" | "rejected"

  matched_entity_ids?: string[]
  confidence: float

  reasons: string[]
}
7.3 강한 규칙

다음은 merge 금지에 가깝게 본다.

producer 충돌
vintage 충돌
region 강충돌
서로 다른 core label family

예:

Opus One 2018 과 Caymus 2018은 절대 merge 불가
Château Margaux 2015 와 Margaux appellation 2015는 ambiguity 처리
8. Merge / Split / Reject Rules
8.1 Merge

아래가 충족될 때만 merge 후보가 된다.

same entity type
**RFC-001 identity_signature compatible** (타입별 규칙 일치)
trusted attributes not conflicting
8.2 Split

아래 경우는 기존 엔티티에서 분리 필요.

동일 wine label인데 vintage가 다름
producer line이 다름
region hierarchy 상 다른 branch
catalog가 사실 bundle/packaging variant임
8.3 Reject

다음은 SSOT 반영 금지.

parsing confidence 너무 낮음
identity token 거의 없음
promo/bundle text만 있고 실제 entity 근거 없음
source reliability 너무 낮고 corroboration 없음

**Reject 출력:** dead-letter 큐·원시 스냅샷 보존 — 나중에 규칙 개선 시 재처리.

8.4 감사 (RFC-001 §4.4 정합)

merge/split/override 시 **이전/이후 entity id·소스·규칙 버전**이 `LineageRecord`에 남아야 한다.

9. Provenance & Lineage

이 RFC의 핵심 중 하나다.

모든 canonicalization decision은 추적 가능해야 한다.

9.1 LineageRecord
LineageRecord {
  source_record_id: string
  candidate_id: string
  matched_entity_id?: string
  previous_entity_ids?: string[]   // split/merge 시

  normalization_rules_applied: string[]
  extraction_version: string
  matching_version: string

  decision: "merge" | "split" | "reject" | "manual_review"
  decision_reason: string
  operator?: string                // manual 시 필수 권장

  timestamp: timestamp
}
9.2 왜 필요한가

이게 있어야:

wrong-top1 원인 추적 가능
alias contamination root cause 확인 가능
특정 source의 품질 저하 감지 가능
eval harness에 실패 사례 편입 가능
10. Manual Review Boundary

모든 걸 자동화하면 안 된다.

다음은 manual review queue로 보내는 게 맞다.

high-value producer conflict
top brand ambiguity
repeated merge/revert oscillation
low-confidence but high-traffic entities
source disagreement 큰 경우

즉 운영상 중요한 엔티티는 human-in-the-loop를 둔다.

10.1 Catalog Abuse Detection (Adversarial Robustness)

마켓플레이스·리테일러가 의도적으로 카탈로그를 오염시키는 시나리오를 방어해야 한다.

**위협 모델:**

- **SEO-style pollution:** 인기 와인명을 제목에 삽입해 검색 노출을 탈취 (예: "Opus One 스타일 칠레 와인 5000원")
- **경쟁사 redirect:** 특정 와인 검색 시 다른 와인으로 유도하는 alias 오염
- **대량 저품질 등록:** 동일 entity를 미세 변형해 대량 등록 → merge pipeline 과부하

**방어:**

- **Source Trust throttle:** `SourceTrustProfile.marketplace_noise_risk`(§3.2)가 높은 소스에서 단기간 대량 등록 시 자동 throttle + manual queue.
- **Title anomaly detection:** canonical entity와 raw_title의 의미 거리가 threshold 초과하면 → `catalog_noise_alias` 강제 + reject 후보.
- **Cross-source corroboration:** 단일 소스에서만 주장하는 entity 속성(producer, region 등)은 corroboration 없으면 SSOT 반영 보류.
- **Frequency cap:** 동일 `source_system`에서 동일 entity에 대한 merge/alias 제안이 단기간 급증하면 알람.
- **Audit trail:** 의심 패턴은 `LineageRecord`에 `abuse_flag` 마킹 → 오프라인 분석·차단 규칙 갱신.

11. 출력 모델

핵심 산출물은 3가지이며, **반영 순서는 §11.4**를 따른다.

11.1 Entity Graph Update

RFC-001 SSOT 반영

11.2 Alias Candidates

RFC-003 입력으로 전달 — **타입·scope·출처**를 붙이기 전에는 “후보만”이다. **마켓플레이스/리테일 제목에서 온 표면형**은 기본적으로 **`catalog_noise_alias` 후보**로 분류하며, projection에서는 **recall 보조 필드**에만 포함 가능하고 **canonical·identity 필드로의 승격은 금지**(RFC-003 §2.6, RFC-012).

**상태 전이 시작점:** ingestion이 넘긴 후보는 RFC-003에서 **`proposed` → `validated` | `rejected`**(RFC-010 `promotion_status`와 정합)로만 SSOT·인덱스에 반영한다 — 운영 게이트는 RFC-009 §13·RFC-010 §6.2.1.

11.3 Retrieval Projection Build Input

Vespa projection용 normalized document 생성 입력 — **SSOT write 이후**에만 트리거 (RFC-001 §5).

11.4 출력 순서 (불변)

1. Entity Graph commit (RFC-001)  
2. Lineage 저장  
3. Alias 파이프라인(RFC-003)  
4. Projection rebuild  

역순·병렬로 canonical을 건너뛰지 않는다.

12. 주요 실패 모드
12.1 Marketplace Title Pollution

리테일러 제목이 canonical을 오염

12.2 Wrong Vintage Merge

2018/2019가 합쳐짐

12.3 Producer Drift

producer가 누락되거나 다른 producer로 붙음

12.4 Bundle Confusion

gift set/bundle을 단일 wine entity로 오인

12.5 Source Trust Inversion

낮은 품질 source가 높은 품질 source를 덮어씀

13. 메트릭

이 RFC도 자체 메트릭이 있어야 한다.

canonicalization precision
merge precision
split precision
reject precision
source-wise error rate
vintage merge error rate
producer conflict rate
manual review rate

추가로 꼭 보자:

marketplace contamination rate
bundle confusion rate
low-confidence accept rate (잘못된 accept가 wrong-resolve로 직결)
lineage completeness (§9)

최종 품질은 **엔티티 검색 wrong-top1 / wrong-resolve**으로도 번진다 (RFC-000 §10.7).

14. 릴리즈 게이트

이 RFC는 아래를 만족해야 다음 단계로 넘길 수 있다.

merge precision 목표치 충족
wrong vintage merge 거의 0에 수렴
high-trust source override 오류 없음
lineage completeness 100%
contaminated title**이** canonical_label로 승격되는 사례 금지
15. RFC 경계
이 RFC가 끝내는 것
raw catalog를 SSOT 후보로 바꾸는 규칙
source trust / provenance / merge pipeline
canonical entity write 전 단계

16. 체크리스트 (리뷰용)

- [ ] 마켓 제목이 canonical으로 승격되지 않는가 (§2.4, §14)
- [ ] merge가 RFC-001 signature·타입 규칙과 일치하는가 (§8.1)
- [ ] `parsing_confidence`를 런타임 calibrated confidence와 혼동하지 않는가 (§6.2)
- [ ] LineageRecord가 merge/split 추적에 충분한가 (§9.1)
- [ ] 클릭·행동신호가 이 파이프라인으로 **역류**하지 않는가 (§1.2)

한 줄 요약

**더러운 카탈로그는 evidence일 뿐이고, SSOT는 파이프라인 끝에서만 갱신된다.**
