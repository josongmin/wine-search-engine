RFC-008
Response & Evidence System (SSOT Output + LLM-ready)

**상위·정합 문서**

- `RFC-000: Wine Intelligence Engine Master Architecture.md` — **§9 Result·EvidenceItem**이 **필드 SSOT**다. 이 RFC는 API 모양(`SearchResponseV1`)·엔진 결정 노출 방식을 풀어 쓴다. **충돌 시 RFC-000 우선.**
- `RFC-007` — `DecisionOutput`·`decision_trace` → `EngineDecision` 매핑
- `RFC-015` — **`decision_snapshot`**, Replay, counterfactual 계약
- `RFC-016` — **Admission Gate**, `FailureReason`·`admission_trace_ref` surface
- `RFC-004` — constraint 문자열·정규화 키
- `RFC-003` — alias 출처·type (evidence `source`에 반영)

0. 목적

이 시스템은 단순 검색 결과를 반환하는 게 아니다.

“결과 + 왜 이게 나왔는지 + 얼마나 확실한지”를 같이 반환해야 한다

즉:

UI는 설명 가능해야 하고
LLM은 reasoning 없이 바로 이해 가능해야 하며
Decision Layer의 판단이 손실 없이 전달되어야 한다
1. 비목표

| 하지 않음 | 담당 |
|-----------|------|
| ranking 계산 | Retrieval / SignalSet |
| entity resolve | RFC-006 |
| decision 판단 | RFC-007 / RFC-000 §8 |
| 자연어 문장 생성 | LLM optional — **authority 아님** |

이 RFC는 **output serialization + evidence structuring**이다.

2. 핵심 원칙
2.1 Output은 SSOT다

UI / API / LLM / Analytics 전부 이 구조를 사용한다.

다른 형태로 변환 금지 (loss 발생)

2.2 Explanation보다 Evidence가 먼저

잘못된 설계:

"이 와인은 ~~해서 좋습니다"

올바른 설계:

어떤 signal이 기여했는지
어떤 constraint가 만족됐는지
어떤 부분이 불확실한지
2.3 Deterministic + Machine-readable

LLM-friendly의 핵심은 자연어가 아니다.

LLM이 추가 reasoning 없이 바로 쓸 수 있는 구조

2.4 Uncertainty는 필수 필드

확실한 것만 말하는 시스템은 위험하다.

불확실성은 숨기면 안 된다

2.5 Failure transparency

`ambiguous` / `failed` 응답은 가능하면 RFC-016 **`failure_reason`**(또는 동등한 reason code)를 함께 surface한다. 이유 없는 abstain·fail은 디버깅·학습·LLM consumption 품질을 떨어뜨린다.

3. 전체 구조
SearchResponseV1 {
  engine_decision: EngineDecision

  results: ResultItem[]

  /** P1 — 왜 다른 후보가 탈락했는지 (구조화) */

  clarification?: ClarificationPayload

  meta: ResponseMeta
}
4. EngineDecision

Decision Layer의 결과를 그대로 노출한다.

EngineDecision {
  decision_status: "resolved" | "ambiguous" | "failed"

  next_action: "return_result" | "clarify" | "hybrid_search" | "fail"

  route: "entity" | "hybrid" | "mixed"

  decision_confidence: float            // RFC-007 `decision_confidence`와 동일 — **calibrated decision** 신호 (일반 IR score·fusion score와 혼동 금지)

  confidence_semantics: "calibrated_decision_confidence"   // 리터럴 고정 — 외부 소비자가 "정답 확률" 등으로 오해하지 않도록

  decision_trace_ref: string           // deprecated 하위호환 trace — Phase A/B 동안 동시 노출
  authority_trace_ref?: string         // 권위 결정론 trace — replay / audit / cache key 기준
  runtime_correlation_ref?: string     // 런타임 상관관계 ID — 로그·지원용
  execution_mode?: "authoritative" | "degraded" | "heuristic" | "advisory"
  blocking_eligible?: boolean
  degradation_reasons?: string[]

  decision_snapshot: DecisionSnapshot   // RFC-015 §2 — 재현·감사 필수

  failure_reason?: string              // RFC-016 `FailureReason` enum (직렬화는 string)
  admission_trace_ref?: string          // RFC-016 — Admission Gate 감사·replay 연동
}

Deprecated `decision_trace_ref` lifecycle, consumer inventory, and removal gate는 [Wave 4 Deprecated-Field Migration Guide](/Users/songmin/wine-search-engine/docs/bugbash/apr-6-hardening-wave4-migration-guide.md)를 따른다. Runtime/support triage는 [Wave 4 Ops Runbook](/Users/songmin/wine-search-engine/docs/bugbash/apr-6-hardening-wave4-ops-runbook.md)을 기준으로 한다.
5. ResultItem (핵심)
ResultItem {
  entity: EntitySummary

  relevance_score: float

  match: MatchDetail

  constraints: ConstraintEvaluation

  uncertainty: UncertaintyBlock

  evidence_items: EvidenceItem[]      // RFC-000 §9.1 — **flat list 권장** (카테고리별 그룹은 클라이언트가 분류 가능)

  human_readable_evidence_summary?: string   // optional — 휴먼 디버그; **권위는 evidence_items**
}
**외부·공식 API 계약(RFC-014):** 결과 행의 근거 리스트 필드명은 **`evidence_items`만** 사용한다 — `evidence` 같은 동의 필드명을 두지 않아 lossless·단일 스키마를 유지한다.

10. EvidenceItem (핵심 — RFC-000 §9.1 정합)

이 시스템의 가장 중요한 output이다. Evidence는 **설명 문장**이 아니라 **추적 가능한 신호**다.

EvidenceItem {
  type: string                // lexical | alias | semantic | anchor | reranker | constraint | ...

  source: string              // 예: observed_query_alias, embedding_v3, vespa_field_match, constraint_engine

  contribution: string           // signed normalized 기여 (**예: "+0.42", "-0.36"**) — 정확한 % 분해를 **주장하지 않음** (RRF·CE·비선형 혼합 시)
  strength: "low" | "medium" | "high"

  provenance: string          // lineage: 인덱스 / 모델 / 필드 / rank profile **버전**

  metadata?: object           // 타입별 세부 (alias_id, scope, similarity, …)
}
10.1 예시 (RFC-000 §9.3과 동일 취지)

```json
{
  "evidence_items": [
    {"type":"alias_match","source":"observed_query_alias","contribution":"+0.42","strength":"high","provenance":"alias_index:v3"},
    {"type":"vintage_match","source":"query_parse","contribution":"+0.19","strength":"medium","provenance":"planner:v1"},
    {"type":"semantic_similarity","source":"embedding_v3","contribution":"+0.11","strength":"medium","provenance":"dense:bge-m3"},
    {"type":"price_constraint_miss","source":"constraint_engine","contribution":"-0.36","strength":"high","provenance":"rfc004:v2"}
  ]
}
```

10.2 Vespa·검색 엔진 연동

가능하면 **rank features**·**summary-features** 등으로 계산된 신호를 evidence에 실어 보낸다 (RFC-000 §9.3).

10.3 원칙

- **모든 주요 신호**는 evidence로 노출하거나, 의도적으로 누락 시 `reason_codes`를 남긴다.
- **총합 1.0 근처** 같은 강제는 하지 않는다 — 비선형·RRF 혼합에서는 **오해의 소지**가 있다.

12.1 CounterfactualReject (P1)

탑 후보가 아닌 **주요 탈락 후보**와 이유 — LLM·디버깅·신뢰용. **authority는 Decision+evidence**와 정합해야 한다.

```
CounterfactualReject {
  entity_id: EntityId
  canonical_label?: string
  rejected_reason: string       // 예: "constraint_price_violation", "anchor_mismatch", "below_threshold"
  evidence_ref?: string          // EvidenceItem id 또는 trace 키
}
```

13. LLM Consumption Pattern

LLM은 이걸 이렇게 쓴다:

entity: 바로 응답 생성
constraints: 조건 설명
evidence: 근거 생성
uncertainty: caveat 생성
clarification: follow-up 질문 생성

즉:

LLM이 reasoning 안 해도 되게 만드는 구조

14. What-if 재점수 (선택 — §12와 구분)

RFC-000 **§9.4** 취지 — **조건 제거·대안 시나리오** 재점수. `SearchResponseV1.counterfactuals`(§12.1)는 **탈락 이유**용이고, 아래는 **가설적 재순위**용.

CounterfactualWhatIf {
  condition: string              // 예: "price_constraint_removed"
  rank_delta: number             // 또는 재순위 결과 ref
  provenance: string
}

"가격 조건이 없었으면 1위였음" — **재점수 결과**가 있을 때만 구조화.

19. 체크리스트 (리뷰용)

- [ ] `EvidenceItem`이 RFC-000 §9.1 **필드·의미**와 일치하는가 (contribution·strength·provenance)
- [ ] “정확한 % attribution”을 약속하지 않는가 (§10)
- [ ] LLM이 evidence 없이 **권위 있는** 답을 만들지 않도록 구조가 잡혀 있는가 (§13)
- [ ] `EntitySummary`·clarification에 **EntityId** 타입이 일관되는가
- [ ] `decision_snapshot`이 **프로덕션 응답**에 붙는가 (§4, RFC-015)
- [ ] 탈락 후보 `counterfactuals`(§12.1)가 있을 때 **rejected_reason**이 구조화되는가
- [ ] what-if 재점수(§14)가 **재점수 근거** 없이 자연어만 쓰이지 않는가

한 줄 요약

Response는 **점수 나열**이 아니라 **결정·근거·불확실성**을 같이 실어 보내는 계약이다.
