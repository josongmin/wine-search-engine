RFC-009
Evaluation System (Wrong-Avoidance First, SOTA++)

**상위·정합 문서**

- `RFC-000: Wine Intelligence Engine Master Architecture.md` — **§10.5 Calibration / Abstention**, **§10.7 Decision Utility Score**가 이 영역의 **수학·우선순위 SSOT**다. 이 RFC는 벤치 구성·운영 절차·dataset을 풀어 쓴다. **충돌 시 RFC-000 우선.**
- `RFC-007` — `DecisionOutput`·`decision_trace` 품질
- `RFC-006` — resolver·calibration·gap
- RFC-000 **§14** — data flywheel → **eval set 갱신** (wrong-top1 → gold 추가)
- `RFC-016` — **Admission invariant** — `resolved`의 identity·snapshot·evidence closure

0. 목적

이 시스템은 일반 검색 시스템이 아니다.

“틀리지 않는 것”이 “잘 맞히는 것”보다 중요하다

따라서 평가 기준도 완전히 달라야 한다.

이 RFC의 한 줄:

Evaluation은 accuracy 측정이 아니라, decision correctness 검증이다.

5. Composite Metric (핵심)
5.1 Decision Utility Score (RFC-000 §10.7 SSOT)

**쿼리 단위 utility (기본 가중치 — 팀이 튜닝 가능, 단 의미는 유지):**

```
Utility(query) =
  + 1.0   if correct_resolve
  + 0.4   if safe_abstain
  + 0.1   if useful_clarification_set
  - 1.5   if wrong_resolve
  - 0.3   if avoidable_abstain
```

**집계:**

`Decision Utility Score = mean_q Utility(query)`

`useful_clarification_set`은 **정의를 벤치에 고정**해야 한다 (예: 정답 후보가 top-k 안에 포함).

5.2 의미 (일반적인 가중 패턴)

wrong resolve 패널티가 **correct resolve보다 크게** — RFC-000과 동일 철학.

레거시 가중 스케치(`w1`~`w4`)를 쓸 경우에도 **wrong 항이 압도적으로 커야** 한다 (RFC-000 §10.7 수치가 기본 기준점).
5.3 Selective Prediction Metrics (학계 SOTA 정합)

이 시스템은 본질적으로 **selective predictor**다 — 확정할 쿼리를 선택하고 나머지는 abstain한다. Decision Utility는 이를 **단일 숫자**로 요약하지만, **coverage-risk tradeoff**를 정밀하게 보려면 추가 지표가 필요하다.

**필수 추가 지표:**

1. **Selective Risk @ Coverage:**
   ```
   SelectiveRisk(τ) = E[wrong_resolve | C ≥ τ] / P(C ≥ τ)
   ```
   coverage(확정 비율)를 τ로 조절하며 risk(오답률)를 본다. τ = T_resolve(Q)일 때의 값이 운영 포인트.

2. **AURC (Area Under Risk-Coverage Curve):**
   coverage 0→1로 sweep하며 risk를 적분. 낮을수록 좋다.
   ```
   AURC = ∫₀¹ risk(coverage) d(coverage)
   ```
   **E-AURC** (Excess AURC) = AURC - AURC_optimal로 이론 최적과의 격차를 본다.

3. **Risk-Coverage Curve 시각화:** 릴리즈 게이트에서 baseline과 신규의 R-C curve를 겹쳐 봐야 한다.

**해석:**

- Decision Utility가 같아도 R-C curve 모양이 다를 수 있다 (한쪽은 high-coverage low-risk, 다른 쪽은 low-coverage zero-risk).
- **운영 포인트**(현재 threshold)에서의 selective risk가 악화되면 Decision Utility가 개선돼도 배포를 재검토한다.
- AURC는 **threshold-free** 요약이므로 T_resolve 튜닝 전 전체적인 모델·calibration 품질 비교에 적합.

6.3 Automated Slice Discovery (P1)

수동 slice(query_class, locale 등)만으로는 새로운 failure mode를 놓친다.

**방법:**

1. **Failure case embedding clustering:**
   - wrong-resolve·avoidable abstain 케이스의 query embedding을 수집
   - HDBSCAN / k-means로 클러스터링
   - 클러스터별 공통 패턴 추출 (예: "~느낌", "~스타일" 접미사 쿼리, 특정 region 집중, 특정 producer family)

2. **Domino-style slice discovery (P2):**
   - Eyuboglu et al. 2022 — embedding space에서 loss가 높은 coherent subgroup을 자동 발견
   - 발견된 slice를 **named slice**로 등록 → §13 릴리즈 게이트의 slice 하한선에 추가

3. **운영 연동:**
   - 신규 발견 slice의 wrong-resolve rate가 전체 평균의 **2배 이상**이면 **알람 + 팀 리뷰**
   - 확인된 slice는 §10 Dataset에 **over-sample**로 편입
   - 자동 발견 slice의 **안정성 검증:** 2주 연속 동일 패턴이 재현되면 정식 slice, 아니면 일시적 분포 변동으로 처리

8.1 Evidence Faithfulness Metric (P1)

evidence가 실제 Decision 기여와 일치하는지 검증한다.

**지표:**

1. **Sufficiency:** evidence_items만으로 decision을 재현할 수 있는 비율
   ```
   Sufficiency = P(same_decision | only evidence signals retained)
   ```
   evidence에 나열된 신호만 남기고 나머지를 0으로 했을 때 decision이 유지되는지 측정.

2. **Comprehensiveness:** evidence_items를 모두 제거했을 때 decision이 바뀌는 비율
   ```
   Comprehensiveness = P(different_decision | evidence signals removed)
   ```
   높을수록 evidence가 실제로 중요한 신호를 담고 있다는 뜻.

3. **Evidence coverage:** `decision_status == resolved`인 결과 중 evidence_items가 RFC-007 Evidence Obligation을 만족하는 비율 (RFC-009 §12.6과 동일).

**릴리즈 게이트:** Sufficiency ≥ 0.85, Comprehensiveness ≥ 0.70 (팀 조정 가능).

9. Hybrid Retrieval Metric

9.1 Clarification Efficiency Metric

clarification 품질은 단순 success rate만으로 부족하다.

**지표:**

1. **avg_turns_to_resolve:** clarification 시작 후 최종 resolve까지 평균 턴 수. 낮을수록 좋다. 목표: ≤ 1.5 turns.
2. **disambiguation_success@1turn:** 첫 번째 clarification 질문으로 ambiguity가 해소된 비율. 목표: ≥ 0.70.
3. **information_gain_per_clarification:** clarification 전후 top-1 confidence 변화의 평균.
   ```
   IG = E[C_after - C_before | clarification_given]
   ```
4. **clarification_set_precision:** clarification 후보 중 사용자가 선택한 entity가 포함된 비율. ≥ 0.90 목표.
5. **unnecessary_clarification_rate:** resolve 가능했는데 clarification으로 간 비율 (avoidable abstain의 clarification 버전).

10.5 Gold Set Quality Metrics

gold set의 라벨 품질이 나쁘면 Decision Utility 자체가 흔들린다.

**필수 지표:**

1. **Inter-Annotator Agreement (IAA):**
   - 최소 2인 독립 라벨링 후 **Cohen's Kappa ≥ 0.8** (substantial agreement) 목표
   - 3인 이상이면 **Fleiss' Kappa** 또는 **Krippendorff's Alpha** 사용
   - entity resolve 정답: κ ≥ 0.85 목표 (wine/vintage 혼동이 잦으므로 높게)
   - ambiguity 판정: κ ≥ 0.75 목표 (주관성이 약간 더 높으므로 약간 낮게 허용)

2. **Label Confidence Tier:**
   | Tier | 조건 | 용도 |
   |------|------|------|
   | **Gold** | IAA ≥ 0.85, adjudicated | 릴리즈 게이트, regression test |
   | **Silver** | IAA ≥ 0.70, 다수결 | threshold tuning, A/B |
   | **Bronze** | 단일 라벨러 또는 자동 생성 | 탐색적 분석, slice discovery |

3. **Adjudication process:**
   - annotator 간 불일치 케이스는 **senior adjudicator** 최종 결정
   - adjudication 결과도 lineage로 남김 (누가, 왜, 어떤 근거로)

4. **Gold set freshness:**
   - 전체 gold set 중 **최근 3개월 내 검증**된 비율 ≥ 0.7
   - entity merge/split 후 해당 entity 관련 gold case는 **자동 재검증 큐**에 편입

**LLM-as-judge 제한:**
   - LLM 자동 라벨링은 **Bronze tier까지만** 허용
   - 릴리즈 게이트(§13)에 LLM 라벨만으로 구성된 slice는 사용 금지

10.6 Temporal Split Policy

검색 시스템에서 random split은 미래 쿼리로 과거를 평가하는 것과 같다 — **temporal leakage**.

**규칙:**

1. **시간 기준 분리:** eval set은 반드시 **수집 시점** 기준으로 분리. 학습/튜닝 데이터보다 **이후** 시점의 쿼리만 eval에 사용.
2. **Concept drift window:** eval set 내에서도 **최근 N주**(권장: 4주) 데이터와 **그 이전** 데이터를 분리해 drift를 관측. 최근 데이터에서만 성능이 떨어지면 모델 열화 신호.
3. **Seasonal holdout:** 연말(11-12월), 추석(9월), 여름(7-8월) 등 계절 피크는 별도 slice로 보관. 비시즌 데이터로만 튜닝한 모델이 시즌에서 깨지는지 검증.
4. **Entity lifecycle:** 신규 등록 entity(최근 30일 내 ingestion)가 포함된 쿼리는 **cold-start slice**로 분리. cold-start에서의 wrong-resolve rate를 따로 추적.

**금지:**

- calibration holdout, conformal set, eval set을 **동일 시간 윈도우**에서 random sample하는 것
- "전체 로그에서 10% random"을 eval로 쓰는 것 (temporal leakage + selection bias)

10.4 Benchmark hygiene (SOTA++ 운영 필수)

오프라인 벤치는 **점수판**이 아니라 **회귀 방지 장치**여야 한다.

- **학습/튜닝 누수 금지:** threshold tuning, alias promotion 검증, reranker 학습에 사용한 케이스를 그대로 릴리즈 벤치에 재사용하지 않는다.
- **slice 균형:** locale, transliteration, short-form ambiguity, mixed query, cold-start entity를 별도 slice로 유지한다.
- **라벨 품질:** gold는 가능하면 **human adjudication** 또는 명시 규칙으로 확정한다. LLM-as-judge는 **보조 triage**까지만 허용하고, release gate의 단독 근거로 쓰지 않는다.
- **counterfactual hygiene:** 같은 원문 쿼리의 변형 케이스(조건 제거, spelling 변형)는 train/test에 무작위 분산하지 말고 leakage를 점검한다.

12.5 Determinism & Replay Gate (P0 — RFC-015)

릴리즈·회귀 시 다음을 만족해야 한다 (인프라가 지원하는 범위에서):

- **동일 `DecisionSnapshot`**에서 동일 입력 **N회** 실행 시: `decision_status`·`next_action`·top-1 `entity_id` **동일 또는 문서화된 tolerance** (부동소수·ANN 변동 허용 시 명시).
- **`decision_trace` 해시**(또는 정규화된 canonical trace) **일치** — 스냅샷·버전 불일치 시 실패.

12.6 Evidence completeness rate (P0)

- 정의: `decision_status == resolved`인 케이스 중 **RFC-007 Evidence Obligation**을 만족하는 비율.
- 릴리즈: **하한선** 미달 시 배포 금지 (팀이 수치 고정).

12.7 Drift monitor (운영 — Failure containment)

다음 **시계열 이상**이면 알람·자동 롤백 후보 (RFC-015 kill switch):

- resolve rate·ambiguous rate의 급변
- `query_class` 분포 급변
- top entity 분포 skew (인기 편향·오염 의심)
- wrong-resolve·ECE 악화

13. Release Gate (중요)

다음 조건 없으면 배포 금지:

WrongTop1 / **wrong-resolve** rate < threshold
**Decision Utility Score** 회귀 없음 (baseline 대비)
ambiguity detection 충분
calibration 안정 (ECE 목표)
decision trace 완전
query-class별 최소 성능 확보 — 특히 **`ambiguous_short_form`**, **`short_entity`**, **`anchored_similarity`** 등 고위험 클래스는 전체 평균이 아닌 **슬라이스 하한선**을 둔다 (평균만 좋고 위험 클래스가 묻히는 것 방지).
locale / language / transliteration slice 회귀 없음 — 다국어·음역 계열은 평균에 묻히기 쉬우므로 별도 하한선을 둔다

**학습·운영 변경과 동일 게이트:** overlay 업데이트, alias promotion, threshold 변경 제안, rank profile 조정도 **위 §13 조건의 동일 부분집합**(wrong-resolve·Decision Utility·ECE·ambiguity slice·trace 완전성)을 통과해야 배포한다 — RFC-010 §6.2.1과 직결.

**§12.5·§12.6:** 새 모델·인덱스·프로파일 롤아웃 시 **Determinism snapshot 테스트**·**evidence completeness** 하한을 **동일 릴리즈**에서 본다 — RFC-015.

**RFC-016 Admission invariant:** §4.7 **AdmissionViolation = 0** — replay에서 snapshot mismatch **false success** 0 — `resolved` 응답의 **EntityRef 부착률 100%**(RFC-001 §1.5, RFC-007).

**Kill switch 검증:** RFC-015 §7 플래그가 켜졌을 때 시스템이 **안전 모드**(overlay off 등)로 동작하는지 **주기적 드릴**.
