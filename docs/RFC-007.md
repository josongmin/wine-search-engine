RFC-007
Decision Layer (Final Authority & Governance)

**상위·정합 문서**

- `RFC-000: Wine Intelligence Engine Master Architecture.md` — **Decision boundary function §8.4·§8.5**, `SignalSet`, **EvidenceItem §9**, **§10.7 Decision Utility**. 수학적 게이트(`C`, `Δ`, `A`, `Q`, 선택적 `conformal_set_size`)의 **SSOT는 RFC-000**이다.
- `RFC-005` — `QueryPlanV1`, `QueryPolicy`
- `RFC-006` — `EntityResolveResult`, resolver `decision_trace`
- `RFC-015` — **`decision_snapshot`**, Evidence obligation과 **연동**, Replay·kill switch
- `RFC-016` — **Admission Gate**, `FailureReason` SSOT, identity sealing·snapshot·evidence 최종 closure

이 RFC는 **운영·구현 관점**에서 Decision의 입력/출력·trace·정책 우선순위를 풀어 쓴다. **규칙이 RFC-000과 충돌하면 RFC-000이 우선**한다.

0. 목적

이 시스템의 핵심 차별점은 retrieval도 아니고, embedding도 아니다.

“언제 확정하고, 언제 멈추고, 언제 다른 경로로 넘길지”를 통제하는 것

이다.

즉 이 RFC의 한 줄은 이거다:

Decision Layer는 모든 신호를 받아 **`decision_status`(resolved / ambiguous / failed)와 `next_action`**을 확정하는 유일한 authority다. **"fallback"은 상태가 아니라** `next_action`(주로 `hybrid_search`)으로만 표현한다 (RFC-000 §8.2).

ranking도 아니고, resolver도 아니다.
오직 이 레이어만 확정 권한을 가진다.

1. 비목표

| 하지 않음 | 담당 |
|-----------|------|
| hybrid retrieval | RFC-012 |
| alias matching | RFC-003 / Resolver |
| attribute·constraint 수치화 | RFC-004 |
| candidate **초기** scoring | Ranking·Resolver 신호 |
| 자연어 explanation 작성 | LLM (authority 아님, RFC-000) |

이 레이어는 **신호·정책·임계를 소비해 상태만 확정**한다.

**Evidence 직렬화**는 RFC-000 **§9** — Decision은 `decision_trace`·포인터만 남기고, 풀 evidence 패킷 조립은 Response 경로에서 처리할 수 있다.

2. 핵심 원칙
2.1 Authority Separation (절대 규칙)

| 레이어 | 역할 |
|--------|------|
| Ranking | signal 생성 (RFC-000 §6) |
| Resolver | 후보 + **calibrated** `C`, `Δ`, ambiguity **입력** (RFC-006) |
| Decision | **최종** `decision_status` + `next_action` (RFC-000 §8.2) |

절대 금지:

ranking score가 높다고 자동 resolve

2.2 Decision ≠ Ranking

ranking은 “누가 더 높은가”를 말한다.
decision은 “확정해도 되는가”를 말한다.

2.3 Fail-Closed 기본 전략

기본 전략은 항상 이거다:

확신 없으면 확정하지 않는다

즉:

default = safe
aggressive resolve 금지
2.4 모든 결정은 traceable해야 한다

Decision Layer는 반드시 다음을 남겨야 한다.

어떤 신호를 봤는지
어떤 threshold를 썼는지
왜 resolve했는지 / 왜 멈췄는지

이게 없으면:

디버깅 불가
eval 불가
governance 불가
3. 입력 계약

Decision Layer는 여러 레이어의 결과를 통합한다. **임계값 SSOT**는 `query_plan.threshold_profile_id`(RFC-005 §7.4) — Decision은 이 id로만 `T_resolve(Q)` 등을 조회한다.

DecisionInput {
  query_plan: QueryPlanV1

  resolver_result: EntityResolveResult

  ranking_signals?: SignalSet

  policy: QueryPolicy

  uncertainty: QueryUncertainty

  // 단순 bool A 대신 — planner·resolver·alias 출처 보존 (RFC-005 `decision_effect`와 합성)
  ambiguity_summary?: {
    types: string[]
    severity: "low" | "medium" | "high"
    sources: ("planner" | "resolver" | "alias")[]
    decision_effect?: "trace_only" | "raise_threshold" | "force_clarify" | "block_resolve"
  }

  /** RFC-008 직렬화 이전에도 gate 가능한 최소 증거 요약 */
  evidence_summary?: {
    identity_evidence_present: boolean
    constraint_evidence_present?: boolean
    anchor_evidence_present?: boolean
    evidence_ref_count?: int
  }

  conformal_set_size?: int    // P2 — RFC-000 §8.5 보조 게이트; 미사용 시 생략 또는 1
}
4. 출력 계약

**`fallback`은 `decision_status`에 넣지 않는다** (RFC-000 §8.2). hybrid 전환은 `next_action = hybrid_search` + `decision_status` = `failed` 또는 `ambiguous`.

DecisionOutput {
  decision_status: "resolved" | "ambiguous" | "failed"

  next_action: "return_result" | "clarify" | "hybrid_search" | "fail"

  selected_entity?: EntityRef   // RFC-001 §1.5, RFC-016 — entity_id + identity_signature + snapshot_ref

  candidates?: CandidateSet

  decision_confidence: float   // semantics 고정 — RFC-008 `confidence_semantics`

  decision_snapshot: DecisionSnapshot   // RFC-015 — 재현·감사·A/B 필수

  failure_reason?: FailureReason      // RFC-016 §6 enum — downgrade·fail 시 필수 권장
  admission_trace_ref?: string         // RFC-016 — 감사·replay 연동

  decision_trace: DecisionTrace
}
4.1 Evidence Obligation (P0 — “근거 없는 확정” 방지)

본 레이어는 **Evidence completeness**를 게이트한다 (RFC-008 `evidence_items`, RFC-009 metric). **직렬화 이전**에는 `DecisionInput.evidence_summary` 또는 동등 trace 입력으로 검사 가능해야 한다.

**`decision_status == resolved`이면** 아래를 만족해야 한다 — 아니면 **downgrade**: `decision_status` → `ambiguous` 또는 `failed`, `next_action` → `clarify` | `hybrid_search` (정책).

| 조건 | must_have (최소 1) |
|------|------------------|
| 항상 | **identity evidence** — entity match·alias_match·canonical path 등 RFC-000 §9 허용 타입 |
| `constraints`가 비어 있지 않음 | **constraint evidence** — 해당 hard/soft가 `evidence_items`·trace에 반영 |

- semantic score만 높고 identity·constraint 증거가 없으면 **resolved 금지**.

**Mixed / anchor 존재(RFC-011):** anchor가 있는데 **anchor_similarity·anchor_match 계열** `evidence_items`가 없으면 상위 결과 **resolved로 확정하지 않거나** invalid 조합으로 처리한다.

4.2 Admission Gate (P0)

Decision Layer의 **마지막 단계**로 RFC-016 Admission Gate를 호출한다.

**입력 (요약):** `selected_entity` / candidate set, `decision_snapshot`, `evidence_summary`, `query_plan.admission_context`, policy·`ambiguity_summary`.

**규칙:**

- 수치 게이트 통과만으로 **`resolved`를 반환하지 않는다.**
- Admission Gate가 실패하면 **`resolved` → `ambiguous` 또는 `failed`로 downgrade**한다.
- downgrade 시 반드시 **`failure_reason`**(RFC-016 enum)을 남긴다.
- 최종 **`admission_trace_ref`**로 감사·replay와 연결한다.

5. Decision State 정의
5.1 RESOLVED

조건:

high confidence
ambiguity 없음
policy 위반 없음

출력:

단일 entity 확정
5.2 AMBIGUOUS

조건:

ambiguity 존재
Δ 낮음
policy.require_clarification = true

출력:

후보 집합
clarification 필요
5.3 Entity path → hybrid (구 “fallback” 브랜치)

조건:

entity resolve가 수치·정책 게이트를 통과하지 못함
또는 approximate·hybrid 허용 정책

출력:

**상태는** `decision_status` = `failed` 또는 `ambiguous`(정책) — **네 번째 status 값 "fallback" 없음**
**행동은** `next_action` = `hybrid_search` (또는 `fail`)
5.4 FAILED

조건:

어떤 route도 유효하지 않음
policy.fail 명시

출력:

실패 상태
6. Decision Logic (Formal)
6.1 입력 변수
C = calibrated confidence (**raw score 금지**, RFC-000 §8.4)
Δ = top1 − top2 **calibrated** decision score gap
A = ambiguity detected — **`ambiguity_summary`**(§3)로 세분화하는 것을 권장 (단순 bool만 쓰면 RFC-005·006 신호가 뭉개짐)
Q = query_class
P = policy
선택: `conformal_set_size` (RFC-000 §8.5, P2)

**통합 권장 순서:** (1) §6.3 — `require_clarification` 등 **정책 선처리**로 즉시 분기 가능한지 본다. (2) 확정되지 않으면 §6.2 **수치 게이트**로 후보 상태를 만든다. (3) `require_exact`·`fallback_mode`로 최종 라우팅을 정리한다.

6.2 기본 게이트 (RFC-000 §8.4 SSOT)

수치 게이트는 아래와 같다 (P0/P1에서 `conformal` 미사용 시 해당 조건 제거).

```
if C >= T_resolve(Q) and Δ >= T_gap(Q) and not A:
    candidate_decision_status = resolved ; next_action = return_result
elif conformal_set_size >= 2 or A or Δ < T_gap(Q):
    candidate_decision_status = ambiguous ; next_action = clarify (등)
else:
    # entity 경로가 확정 resolve/명시적 ambiguous가 아닌 경우 — **"FALLBACK" status 없음**
    candidate_decision_status = failed | ambiguous  // 정책
    next_action = hybrid_search | fail
```

**Selective Prediction 관점 (RFC-009 §5.3):** 위 게이트는 **Selective Risk @ Coverage** 관점에서 `τ = T_resolve(Q)` 지점의 risk를 통제한다. 릴리즈 전 **AURC**·**Risk-Coverage curve**를 baseline과 비교해야 하며, Decision Utility가 같아도 R-C curve가 악화됐으면 배포를 재검토한다.

6.3 Policy Compiler 오버레이 (RFC-005 `QueryPolicy`)

**정책 선처리 (§6 상단 순서의 1단계):**

1. `P.require_clarification == true` → **AMBIGUOUS** (resolver가 RESOLVED를 줘도 무시 가능).
2. 그 다음 §6.2 수치 게이트 적용.
3. `P.require_exact == true`이면 §6.2에서 RESOLVED가 아니면 **AMBIGUOUS** 또는 **FAILED** (`fallback_mode`).
4. `P.allow_approximate`·`fallback_mode`에 따라 **`next_action`·hybrid 전환** (§9) — status에 "fallback" 라벨 없음.

**정책이 수치 게이트를 덮을 수는 있어도**, raw ranking으로 덮으면 안 된다.

6.4 핵심 포인트
policy는 **resolver 출력보다 상위**에서 안전장치로 작동할 수 있다
ambiguity는 hard constraint처럼 작동할 수 있다
`next_action = hybrid_search`는 실패가 아니라 **전략 선택**일 수 있다 (RFC-000 §14 data flywheel과 연결 가능)

6.5 Post-gate closure

본 RFC의 수치·정책 게이트 결과는 **provisional**이다. **최종 출력은 RFC-016 Admission Gate 이후**의 결과를 따른다 (`DecisionOutput.decision_status`·`next_action`·`failure_reason`·`admission_trace_ref`).
7. Policy Enforcement
7.1 require_exact
approximate 금지
ambiguity 시 resolve 금지
7.2 require_clarification
무조건 ambiguity 상태 유지
resolve 시도 자체 금지
7.3 allow_approximate
hybrid route 허용
semantic/attribute 기반 추천 가능
7.4 fallback_mode
fallback_mode =
  "clarify"
  "hybrid"
  "fail"

9. Interaction with Hybrid
9.1 `next_action` = hybrid_search → hybrid

Decision Layer가 hybrid route를 선택하면 (`decision_status`는 `failed` 또는 `ambiguous`일 수 있음):

QueryPlan 유지
constraints 유지
anchor 유지

그리고 **RFC-012** Hybrid Retrieval으로 넘긴다.

9.2 중요한 규칙

hybrid 전환은 반드시 degrade가 아니라 **전략 전환**일 수 있다 (`next_action` 의미)

10. Ambiguity Escalation
10.1 다단계 ambiguity
resolver 단계 ambiguity
planner 단계 ambiguity

Decision Layer는 이걸 통합한다.

10.2 escalation 규칙
if ambiguity severity = high:
    force clarification

15. 체크리스트 (리뷰용)

- [ ] RFC-000 §8.4 게이트와 **수식·변수 정의**가 일치하는가 (§6.2)
- [ ] raw score로 `C`·`Δ`를 만들지 않는가 (§6.1)
- [ ] `require_clarification` 등 정책과 수치 게이트 **평가 순서**가 문서화돼 있는가 (§6.3)
- [ ] 모든 요청에 **decision_trace**가 남는가 (§13)
- [ ] **`decision_snapshot`**(RFC-015)가 출력에 포함되는가 (§4)
- [ ] **Evidence Obligation**(§4.1) 위반 시 downgrade되는가
- [ ] **Admission Gate**(§4.2, RFC-016)가 수치 게이트 이후 최종 closure인가 — `failure_reason`·`admission_trace_ref`가 downgrade 시 남는가
- [ ] Ranking·Resolver가 최종 상태를 **덮어쓰지** 못하는가 (§2.1, §11.1)
- [ ] 정책 임계값 변경 시 RFC-009 **§5.3 AURC/Risk-Coverage curve**가 baseline과 비교되는가

한 줄 요약

Decision Layer는 “검색 결과를 고르는 레이어”가 아니라,
“시스템이 어떤 행동을 할지 결정하는 레이어”다.

이게 있어야
비로소 이 시스템이 검색엔진이 아니라 Decision System이 된다.
