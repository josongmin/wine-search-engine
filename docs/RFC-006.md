RFC-006
Entity Resolver (Calibrated + Abstention-aware)

**상위·연관 문서**

- `RFC-000: Wine Intelligence Engine Master Architecture.md` — **Decision boundary function §8.4** (`S1`, `S2`, `Δ`, `C`, `A`, `Q`), `EntityResolveResult`, **EvidenceItem §9**, **§10.7 Decision Utility**
- `RFC-005` — `QueryPlanV1`, `QueryPolicy`, `query_class`(`Q`)
- `RFC-003` — `alias_type_prior`, observed/catalog_noise 규칙
- `RFC-001` — `EntityId`, wine/vintage 구분
- `RFC-016` — Resolver 출력은 **신호·proposal**; 최종 `resolved`는 Admission Gate·`EntityRef` sealing

앞의 RFC들이 다 입력 정제와 계획 수립이었다면,
RFC-006은 처음으로 “정확히 하나를 뽑을지, 멈출지, 넘길지” 를 다룬다.

즉 이 레이어는 단순 matcher가 아니다.

Entity Resolver는 calibrated score와 abstention logic을 이용해
exact entity resolution을 수행하는 **decision-aware** 컴포넌트다.

잘못 만들면 이 시스템 전체가 그냥 “자신감 넘치는 오답 생성기”가 된다.

0. 목적

Track A의 목적은 명확하다.

messy query를 정확한 wine entity로 수렴시킨다
하지만 unresolved ambiguity에서는 절대 강제 확정하지 않는다

즉 이 RFC의 한 줄은 이거다.

Resolver의 목표는 많이 맞히는 것이 아니라, 틀릴 때 멈추는 것이다.

이 RFC는 exact entity resolution의 점수 계산, ambiguity 탐지, calibrated confidence, **Resolver 출력 계약**(`status`는 `resolved` \| `ambiguous` \| `failed`만)을 정의한다. **“fallback”은 상태가 아니라** `recommended_next_action`·상위 Decision의 `next_action`이다 (RFC-000 §8.2).

1. 비목표

| 직접 하지 않음 | 담당 |
|----------------|------|
| hybrid retrieval | RFC-012 |
| clarification UX 카피·UI | 제품 레이어 |
| counterfactual explanation | RFC-000 §9.4 (P2–P3) |
| 일반 추천 랭킹 | Track B |

이 RFC는 **entity route**의 core resolver contract다.

**역할 경계:** Resolver는 **candidate·calibrated 신호·제안**을 생산한다. **최종 `decision_status`·`next_action` 권한은 RFC-007 / RFC-000 §8**이 잠근다. Resolver 출력의 `status`는 **제안**에 가깝고, 상위에서 덮어쓸 수 있다 — 다만 필드 형식은 동일 계열(`resolved` \| `ambiguous` \| `failed`)을 유지한다.

2. 핵심 원칙
2.1 Resolver는 matcher가 아니라 selective predictor

기존 검색 시스템은 top1을 내놓는 데 집중한다.
이 시스템은 다르다.

Resolver는 맞을 때만 resolve하고, 아니면 abstain해야 한다.

즉 항상 출력이 하나일 필요가 없다.

2.2 Raw score threshold 금지

retrieval score, fuzzy match score, rerank score의 raw 값은 모델/프로파일마다 스케일이 흔들린다.
따라서:

resolve 기준에 raw score를 직접 쓰지 않는다.

반드시 calibrated confidence를 사용한다.

2.3 Score는 증거, authority는 policy

Resolver 내부에서도 동일 원칙을 유지한다.

match score = signal
calibrated confidence = normalized decision input
resolve authority = decision rule

즉 높은 score 하나만으로는 확정 불가다.

2.4 Wrong-top1은 no-result보다 더 나쁘다

이 RFC는 정확도보다 wrong resolve 최소화를 우선한다.

즉:

safe abstain 허용
avoidable abstain은 개선 대상
wrong resolve는 강한 실패

이 철학은 RFC-000 **§10.7 Decision Utility**·abstention 메트릭과 직결된다.

3.3 Blocking Strategy (Candidate Pre-filter)

entity 수가 10만~100만 규모로 커지면 전체 alias index를 full scan하는 것은 P95 latency를 파괴한다. Resolver에 도달하기 전 **blocking**으로 후보를 효율적으로 줄여야 한다.

**Blocking 방식 (단계적 적용):**

1. **Inverted alias index blocking (P0):** query token → alias inverted index에서 exact/prefix match하는 entity set 추출. 가장 기본적이고 확실한 방식.
2. **Producer + Region prefix blocking:** anchor candidate에서 producer·region이 추출되면 해당 조합으로 후보군 사전 필터.
3. **Embedding-based ANN pre-filter (P1):** query embedding → HNSW ANN으로 top-K entity를 먼저 뽑고, 이 중에서만 정밀 scoring. Dense retrieval(RFC-012)의 결과를 blocking으로 재사용 가능.
4. **Learned blocking (P2):** DeepBlocker / Sudowoodo 패턴 — query-entity pair의 blocking 여부를 학습. false negative 최소화가 핵심.

**Blocking 계약:**

- blocking 단계에서의 **recall ≥ 0.99**를 목표로 한다 (정답 entity가 blocking에서 탈락하면 downstream 전체 실패).
- blocking recall은 RFC-009 eval에서 **별도 슬라이스**로 추적.
- blocking이 정답을 누락시킨 wrong-top1은 **blocking_miss**로 분류해 일반 resolver failure와 구분.

5. Candidate Scoring
5.1 개념적 기본식
base_match_score(e) =
  w1 * canonical_exact_match
+ w2 * canonical_normalized_match
+ w3 * alias_exact_match * alias_type_prior
+ w4 * alias_fuzzy_match * alias_type_prior
+ w5 * producer_match
+ w6 * vintage_match
+ w7 * region_match
+ w8 * phonetic_match
+ w9 * edit_distance_score
- w10 * ambiguity_penalty

이 점수는 내부 ranking signal이다.
이 자체로 resolve하지 않는다.

5.2 규칙
canonical/translation 신호 > phonetic/misspelling 신호
vintage conflict는 큰 penalty
catalog_noise_alias는 contribution 상한 제한
observed_query_alias는 contribution 가능하지만 core override 금지

즉 alias 시스템의 위험한 부분이 resolver core를 덮지 못하게 해야 한다.

5.3 Learned Matcher Interface (P1–P2)

P0은 rule-based `base_match_score`로 시작하지만, 학계 SOTA entity matching (Ditto, Unicorn, MatchGPT 등)에서는 PLM 기반 learned matcher가 유의미한 gains를 보인다.

**Interface 계약:**

```
LearnedMatcherOutput {
  entity_id: EntityId
  match_probability: float          // [0, 1] — **calibration 필수** (§7과 동일 기준)
  match_signal_vector: float[]      // MatchSignalSet과 동일 차원 또는 superset
  model_id: string
  model_version: string
}
```

**Pluggability 규칙:**

- learned matcher는 `MatchSignalSet`(§4.1)과 **동일 출력 계약**을 지키거나, 상위 호환(superset)이어야 한다.
- `match_probability`는 rule-based `base_match_score`와 **별도 calibration**을 거쳐 `CalibratedResolutionScore`(§7.2)에 합류한다.
- learned matcher가 canonical/producer/vintage 신호를 무시하고 embedding만으로 결정하는 것은 **금지** — §5.2 우선순위 규칙은 learned model에도 적용.
- 승격: RFC-009 release gate + RFC-015 shadow → canary → full rollout.

**Training hygiene:**

- positive label: RFC-009 gold set의 correct resolve 케이스
- hard negative: near-miss entity (같은 producer 다른 vintage, 같은 region 다른 producer)
- train/eval leakage 방지: RFC-009 §10.4 benchmark hygiene 동일 적용

7. Calibration
7.1 왜 필요한가

같은 score gap이라도 query class마다 의미가 다르다.

short entity query에서 Δ=0.12
ambiguous short-form에서 Δ=0.12

이건 전혀 같은 상황이 아니다.

따라서 base score를 그대로 thresholding하면 안 된다.

7.2 출력 confidence

Resolver는 다음을 만든다.

CalibratedResolutionScore {
  top1_calibrated_score: float
  top2_calibrated_score: float
  calibrated_gap: float
  decision_confidence_c: float    // RFC-012 `retrieval_fusion_score`·RFC-005 anchor_confidence와 혼동 금지
}

여기서 `decision_confidence_c` = **C** — decision rule의 핵심 입력 (구 옛 필드명 `calibrated_confidence`·`top1_score`는 폐기).

7.3 calibration 방식

구현 선택지는 열어둔다.

Platt scaling
isotonic regression
class-conditional calibration
query-class conditional calibration

핵심은 하나다.

query_class별 calibration 가능성을 열어둔다

즉 전역 단일 calibration으로 고정하지 않는다.

7.4 Calibration Operational Protocol

calibration이 운영에서 실제로 작동하려면 **데이터·주기·검증** 프로토콜이 필요하다.

**Calibration holdout set:**

- **크기:** query_class별 최소 500개 (ambiguous_short_form, short_entity 등 고위험 클래스는 1000개 이상 권장)
- **구성:** production query 분포를 반영하되, 고위험 클래스는 over-sample
- **독립성:** train set·conformal set(RFC-000 §8.6)과 **겹치지 않아야** 한다
- **라벨:** ground truth entity + expected_decision_status (RFC-009 EvaluationUnit과 동일 형식)
- **라벨 품질:** calibration holdout의 라벨은 **RFC-009 §10.5 Gold tier** (IAA ≥ 0.85) 데이터만 사용. Silver/Bronze tier는 calibration에 사용 금지 — miscalibration의 원인이 된다.

**갱신 주기:**

| 트리거 | 행동 |
|--------|------|
| 모델 변경 (dense, reranker, matcher) | 즉시 re-calibrate |
| 인덱스 대규모 변경 (entity 10% 이상 변동) | 즉시 re-calibrate |
| 주기 (모델 변경 없어도) | 최소 **2주 1회** |
| ECE 악화 알람 (RFC-009 §12.7) | 즉시 re-calibrate + 원인 조사 |

**검증:**

- re-calibration 후 반드시 **ECE < 목표치** (팀 합의, 예: ECE < 0.05) 확인
- query_class별 calibration curve를 시각화하고, 특정 클래스에서 miscalibration이 심하면 **class-conditional calibration** 적용
- calibration 전/후 **Decision Utility** 비교 — calibration이 오히려 utility를 깎으면 배포 금지

**Class-imbalance 처리:**

- `ambiguous_short_form`은 전체 쿼리의 소수일 수 있지만 wrong-top1 리스크가 높음 → calibration holdout에서 비율을 올려 충분한 bin 정밀도 확보
- isotonic regression은 데이터가 적은 bin에서 불안정 → 해당 클래스는 Platt scaling 또는 temperature scaling이 더 안전할 수 있음

8. Formal Decision Boundary

이 RFC의 중심이다.

8.1 정의

Let:

S1 = top1_calibrated_score
S2 = top2_calibrated_score
Δ = calibrated_gap
C = decision_confidence_c
A = ambiguity detected
Q = query_class
8.2 기본 규칙 (RFC-000 §8.4 정합)

P0/P1:

```
if C >= T_resolve(Q) and Δ >= T_gap(Q) and not A:
    status 제안 = resolved ; next_action 제안 = return_result

elif conformal_set_size >= 2 or A or Δ < T_gap(Q):
    status 제안 = ambiguous ; next_action 제안 = clarify (등)

else:
    status 제안 = failed | ambiguous ; recommended_next_action = hybrid_search | fail
```

`conformal_set_size`를 아직 쓰지 않으면 해당 조건을 끄거나 **1로 간주** (RFC-000 §8.4 — P2 보조 게이트).

**Selective Prediction 프레임워크 (RFC-009 §5.3):** 위 규칙의 `T_resolve(Q)`·`T_gap(Q)` 선택은 **Risk-Coverage curve**에서 운영 포인트를 고르는 것과 동치다. AURC가 낮을수록 전체적으로 좋은 calibration·threshold 조합이다.

여기서 `T_resolve(Q)` 와 `T_gap(Q)` 는 query class별로 다를 수 있다.
예를 들어:

short_entity는 resolve 임계 낮게
ambiguous_short_form은 resolve 임계 높게
anchored_similarity는 exact resolve보다 anchor identification만 우선
8.3 정책 해석
RESOLVED
top_entity 확정 가능
wrong-top1 리스크 수용 가능 수준
AMBIGUOUS
후보 집합 반환
clarification 필요
resolve 금지
failed / hybrid 전환 (상태명으로 "fallback" 사용 금지)
entity route 실패 시 `recommended_next_action` = hybrid_search 등
policy fallback_mode에 따름
8.4 중요한 제약
C는 calibrated confidence여야 함
raw retrieval score 그대로 금지
A는 planner ambiguity + resolver ambiguity 통합 가능
Δ는 calibrated space에서 계산

**Ranking은 authority가 아니다:** `base_match_score`는 **신호**이고, 최종 상태는 위 규칙·정책으로만 (RFC-000 §6·§8).

**주의:** RFC-006의 `decision_confidence_c`, `S1`, `S2`, `Δ`는 **수치 게이트 입력**일 뿐이다. 이 수치 게이트를 통과해도 RFC-016 Admission Gate의 **identity sealing**, **snapshot consistency**, **evidence sufficiency**를 통과하지 못하면 최종 **`resolved`는 금지**된다.

9. Resolver Output Contract
9.1 EntityResolveResult

RFC-000 §5.1과 **의미적으로 동일**해야 한다 (`status`·`recommended_next_action`·`candidates`·`ambiguity`·`decision_trace`).

EntityResolveResult {
  status: "resolved" | "ambiguous" | "failed"

  recommended_next_action?: "return_result" | "clarify" | "hybrid_search" | "fail"

  decision_confidence_c?: float   // optional mirror — canonical source는 `decision_trace.decision_confidence_c`

  top_entity?: {
    entity_id: EntityId
    canonical_label: string
    calibrated_score: float
  }

  candidates: ResolvedCandidate[]

  ambiguity?: {
    types: AmbiguityType[]
    severity: string
    explanation_codes: string[]
  }

  decision_trace: ResolverDecisionTrace
}

**EntityRef 승격 (RFC-016):** Resolver **exact path** 후보는 최종 확정 전 **`EntityRef`**로 승격 가능해야 한다 (`entity_id` + `identity_signature` + `snapshot_ref`). top candidate가 있어도 아래 중 하나라도 실패하면 exact resolve **proposal은 downgrade 대상**이다.

- `identity_signature` 조회 실패
- `snapshot_ref` 부착 실패
- projection / alias-only **역구성** 경로

9.1.1 Multi-entity resolve (`comparison_query`)

`query_class == comparison_query`(RFC-005)일 때는 **단일 wine로 collapse하지 않는다**. Resolver는 **복수 anchor·복수 후보**를 각각 점수화해 `candidates`에 유지하거나, 구현이 분리된 경우 **`MultiEntityResolveResult`** 확장을 쓴다.

- **금지:** 비교 쿼리를 임의로 한 entity만 남기고 `resolved`로 확정 (RFC-007이 최종 판단).
- **권장:** 엔티티별 `calibrated_score`·`evidence_refs`를 분리해 Decision·Evidence(RFC-007·008)로 전달.

9.2 ResolvedCandidate
ResolvedCandidate {
  entity_id: EntityId
  canonical_label: string

  calibrated_score: float
  rank: number

  evidence_refs: string[]     // EvidenceItem id 또는 RFC-000 §9 연결 키
}
9.3 ResolverDecisionTrace
ResolverDecisionTrace {
  query_class: string

  top1_calibrated_score: float
  top2_calibrated_score: float
  calibrated_gap: float
  decision_confidence_c: float

  ambiguity_detected: boolean
  ambiguity_types: string[]

  applied_thresholds: {
    resolve_threshold: float
    gap_threshold: float
  }

  outcome_reason_codes: string[]
}

이 trace는 **eval·로그·(선택) 상위 Decision Layer**의 공통 입력이 된다. Evidence 직렬화는 **RFC-000 §9**.

10. Routing semantics (`fallback_mode` → `next_action`)

resolver가 실패했다고 무조건 user failure는 아니다. **상태명 "fallback" 없이**, `QueryPolicy.fallback_mode`가 **`next_action`**(clarify / hybrid_search / fail)으로 매핑된다 (RFC-000 §8.2).

10.1 정책 문자열 (RFC-005 `fallback_mode`와 동형)
FallbackMode =
  "clarify"
  "hybrid"
  "fail"
10.2 예시
마고
ambiguous
`next_action` = clarify
오푸스원 같은 와인
exact resolve 자체는 anchor 식별로 끝
이후 mixed route로 넘김
나파 묵직한 와인
entity resolve 실패는 자연스러움
hybrid 라우팅이 정답
10.3 원칙

resolver failure와 product failure를 구분해야 한다.

즉:

exact entity resolve가 실패해도, 시스템 전체는 성공할 수 있다.

11. Failure Modes
11.1 Forced Resolve

애매한데도 하나 찍음

11.2 Raw Score Thresholding

calibration 없이 threshold 사용

11.3 Alias Overweight

alias 하나가 canonical/producer/vintage를 덮음

11.4 Vintage Collapse

2018과 2019를 하나로 봄

11.5 Ambiguity Silent Pass
