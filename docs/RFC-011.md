RFC-011
Mixed Query Solver (Anchor + Constraint + Semantic Fusion)

**상위·연관 문서**

- `RFC-000: Wine Intelligence Engine Master Architecture.md` — **§7 Mixed Query Solver**, `SignalSet`, **Decision Layer**가 최종 권한; ranking은 신호만 (§6·§8)
- `RFC-005` — `QueryPlanV1`, `route: mixed`, constraints·expansion
- `RFC-004` — 속성·constraint 정규화
- `RFC-006` — anchor **entity resolve**
- `RFC-015` — evidence·snapshot과 **정합**
- `RFC-001` / RFC-000 — `AnchorProfile` (entity SSOT 투영)
- `RFC-008` — 응답·evidence
- `RFC-009` — Anchor Preservation·constraint 지표는 **Decision Utility**와 함께 본다
- `RFC-016` — mixed·anchor 경로의 **evidence sufficiency**·`EntityRef` sealing

**충돌 시 RFC-000 우선.**

0. 목적

Mixed query는 이런 것들이다:

“오푸스원 같은 10만원 와인”
“샤또마고 느낌인데 좀 더 싸게”
“나파 묵직한 레드 추천”
“케이머스랑 비슷한데 덜 비싼거”

이건 단순 검색이 아니라:

“기준(anchor)을 이해하고, 조건을 적용하고, 의미를 유지하면서 결과를 찾는 문제”

다.

1. 핵심 정의
Mixed Query =
Anchor (선택적)
+ Constraints (명시/암묵)
+ Semantic Intent
2. 비목표

| 하지 않음 | 담당 |
|-----------|------|
| 단순 entity-only resolve | RFC-006 (Track A 단독) |
| pure semantic-only 검색 | hybrid route |
| LLM-only reasoning | 금지 — **결정론적 계약** 우선 |
| **최종** `decision_status` / `next_action` 확정 | **Decision Layer** (RFC-000 §8) |

이건 **구조적으로** 풀어야 하는 문제다.

3. 핵심 원칙
3.1 Anchor First (절대 규칙)

anchor가 있으면 무조건 먼저 resolve한다

이걸 어기면:

의미 붕괴
엉뚱한 추천
user trust 박살
3.2 Constraint는 hard vs soft로 분리
hard: 반드시 만족
soft: 최대한 반영
3.3 Semantic은 보조 신호

semantic embedding으로 다 해결하려 하면 망한다 (RFC-002 §7.0·RFC-006과 동일 취지).

semantic은:

attribute 보완
similarity 보정

용이다 — **단독으로 anchor identity를 덮지 못함.**

3.4 Anchor Preservation (핵심 KPI)

결과는 반드시:

anchor의 identity 특성을 유지해야 한다

4. 입력
MixedQueryInput {
  query_plan: QueryPlanV1          // RFC-005; route·constraints·expansion 포함

  anchor_resolve_result?: EntityResolveResult   // RFC-006

  constraints: ConstraintSet       // RFC-005 `ConstraintBundle`·RFC-004 정규화 값과 동일 의미

  semantic_intent?: SemanticVector
}
5. 처리 흐름 (개요)

1. Anchor Resolve (§6)
2. Anchor Profile 생성 (§7)
3. Constraint Overlay (§8)
4. Candidate Generation (§9)
5. Multi-objective Ranking·신호 계산 (§10) → **Decision Layer**가 최종 상태 (RFC-000 §8)

**단계별 상세 (§6–§12):**

5.1 Anchor failure typing & degrade policy (RFC-005 §11.2와 연결)

mixed query에서 anchor 경로가 깨졌을 때 **의미 없이 semantic-only로 흐르는 것**을 막기 위한 최소 계약:

```
anchor_failure_type =
  | "unresolved"
  | "ambiguous_identity"
  | "ambiguous_family"
  | "no_anchor_found"

degrade_policy =
  | "forbid_semantic_downgrade"   // 예: exact-ish anchor collision — semantic downgrade 금지
  | "clarify_first"
  | "safe_hybrid_allowed"         // 예: preference-heavy mixed — 안전한 hybrid만 허용
```

`degrade_policy`는 planner·정책·`anchor_failure_type`으로부터 결정되며, RFC-005 mixed collapse 규칙과 **같은 축**으로 유지한다.

6. Step 1 — Anchor Resolve

anchor는 **RFC-006** resolver 사용.

출력:

resolved → 진행
ambiguous → clarification 또는 `next_action` (RFC-007·RFC-000 §8) — status "fallback" 없음
failed → §12.1·`degrade_policy`에 따라 anchor 없이 처리 **허용 여부** 결정

7. Step 2 — Anchor Profile
7.1 정의

RFC-000 / RFC-001 `AnchorProfile`과 정합.

AnchorProfile {
  entity_id: EntityId

  attributes: {
    region
    grapes              // RFC-004 필드명 통일
    body
    acidity
    price_band
    style_vector
  }

  embedding: vector
}
7.2 목적

anchor를 단순 entity가 아니라:

검색 기준 벡터 + 속성 집합

으로 변환한다.

8. Step 3 — Constraint Overlay
8.1 구조

SSOT 이름은 RFC-005의 **`ConstraintBundle`** 과 동일하다. 아래 `ConstraintSet`은 동의어.

ConstraintSet {
  hard: Constraint[]
  soft: Constraint[]
  inferred: Constraint[]
}
8.2 예시

“오푸스원 같은 10만원 와인”

anchor: Opus One
hard: price ≤ 100k
soft: similar body/style
inferred: premium red
8.3 중요 규칙
hard constraint 위반 → 제거
soft constraint → score 반영
inferred → 약한 prior
9. Step 4 — Candidate Generation
9.1 Hybrid Retrieval 사용
sparse (BM25/SPLADE)
dense (embedding)
ANN
9.2 Query 구성
Query =
  anchor_profile
+ constraint filters
+ semantic expansion
9.3 Candidate Pool

Top-K (보통 100~500)

10. Step 5 — Ranking & Signals (핵심)

**권한:** 이 단계는 **신호만** 만든다. 최종 확정은 **Decision Layer**(RFC-000 §6·§8).

10.1 SignalSet (RFC-000 §6.1과 정합)

SignalSet ≈

  anchor_similarity_score / entity_integrity
+ hard_constraint_pass
+ soft_constraint_score
+ semantic_relevance_score
+ attribute_alignment_score
+ popularity_score
+ availability_score
- uncertainty_penalty

10.2 Anchor Similarity

가장 중요

anchor_similarity =
  attribute_distance
+ embedding similarity
10.3 Constraint 처리
hard → 필터
soft → penalty/bonus
10.4 Attribute Alignment

예:

region match
grape match
body match
11. Anchor Preservation Rule

이 RFC의 핵심이다.

**Minimum evidence obligation (KPI 보조 — RFC-007 §4.1과 동일 축):** anchor가 존재하는 mixed 경로에서 결과 **상위 K**에는 `evidence_items` 중 **anchor_similarity / anchor_match** 계열이 최소 1개 이상 있어야 한다. 없으면 **resolved 확정 금지**·downgrade (RFC-007) — semantic drift·anchor 상실 방지.

잘못된 결과
가격만 맞고 완전 다른 스타일
semantic만 비슷하고 구조 다름
올바른 결과

“anchor의 정체성을 유지하면서 조건을 만족”

12. Fallback 처리
12.1 anchor 없음

→ pure hybrid

12.2 anchor ambiguous

→ clarification 또는 multi-anchor 처리

12.3 constraint 충돌

→ soft downgrade or fallback

13. Output

`SearchResponseV1` / **RFC-008** 구조 — `evidence_items`에 anchor·constraint·semantic 기여를 싣는다 (RFC-000 §9).

추가 필드 (예시):

MixedContext {
  anchor_entity_id?: EntityId
  applied_constraints: object   // hard/soft/inferred 요약
  similarity_basis: string[]   // 어떤 속성·벡터로 유사도를 봤는지
}
14. Failure Modes
14.1 Anchor 무시

semantic만 보고 결과 생성

14.2 Constraint 무시

조건 반영 안 됨

14.3 Overfitting to price

가격만 맞고 의미 붕괴

14.4 Semantic Drift

점점 엉뚱한 결과

18. 체크리스트 (리뷰용)

- [ ] anchor가 있을 때 **항상 먼저** resolve하는가 (§3.1)
- [ ] ranking만으로 **최종 RESOLVED**를 강제하지 않는가 (§10)
- [ ] constraint가 RFC-004 **정규화 스키마**와 맞는가 (§8)
- [ ] `AnchorProfile`이 RFC-001·Entity **투영**과 모순 없는가 (§7)
- [ ] 출력에 **evidence**·mixed context가 RFC-008에 실리는가 (§13)

한 줄 요약

RFC-011은 “비슷한 걸 찾는 시스템”이 아니라,
**기준(anchor)을 이해하고 조건을 만족한 뒤**, 신호를 Decision·Evidence로 넘기는 시스템이다.

이게 잘 되면
검색이 아니라 **decision + recommendation**에 가까워진다.
