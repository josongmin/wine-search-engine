RFC-005
Query Planner & Policy Compiler

**상위·연관 문서**

- `RFC-000: Wine Intelligence Engine Master Architecture.md` — **QueryPlanV1**·`query_class`(`Q`)·Policy·**Decision Layer §8.4** (`C`, `Δ`, `A`)와 직접 연결; Planner=WHAT / Policy=HOW FAR
- `RFC-003` — anchor·alias 후보; Policy가 **require_clarification** 등으로 ambiguity 게이트
- `RFC-004` — `NormalizedConstraint`·NL mapping은 **버전 있는** 속성 SSOT와 정합 (`mapping_version`)
- `RFC-015` — **DecisionSnapshot**, Replay, kill switch, drift·determinism과 **연동**
- `RFC-016` — **`admission_context`** → Admission Gate 입력; Planner는 `resolved`를 확정하지 않음

0. 목적

사용자 쿼리는 본질적으로 불완전하다.

예를 들면:

오푸스원
마고
묵직한 레드
오푸스원 같은 10만원 와인
고기랑 잘 어울리는 달지 않은 와인

이걸 그냥 검색창에 바로 던지면 안 된다.
먼저 이 쿼리가

exact entity를 찾는 건지
탐색형인지
anchor 기반 mixed query인지
ambiguity가 높은지
approximation을 허용해도 되는지

를 분해해야 한다.

따라서 이 RFC의 한 줄은 이거다.

Planner는 “무엇을 찾을지”를 결정하고, Policy Compiler는 “어디까지 허용할지”를 결정한다.

이 둘이 분리되지 않으면 route 튜닝도 안 되고, ambiguity 정책도 흔들리고, resolve/fallback 품질도 떨어진다.

1. 비목표

| 직접 하지 않음 | 담당 |
|----------------|------|
| entity resolve | RFC-006 등 Resolver |
| hybrid retrieval | RFC-012 |
| ranking·신호 계산 | Retrieval / SignalSet (RFC-000 §6) |
| **최종** RESOLVED / AMBIGUOUS / FALLBACK 확정 | **Decision Layer** (RFC-000 §8.4) |

즉 이 RFC는 **query-time orchestration 계약**만 만든다 — 출력은 **불변 QueryPlan**이 아니라 **버전 있는 스냅샷**(`planner_version`, `policy_rule_version`).

**LLM:** 허용 시 **후보 추출·의도 힌트**에만 쓰고, **QueryPlanV1 필드는 결정론적 규칙·테이블**으로 채워야 한다 (RFC-000: LLM never authority).

2. 핵심 원칙
2.1 Parsing이 아니라 Planning

단순 parser는 토큰을 뽑는다.
Planner는 실행전략을 만든다.

잘못된 접근:

"오푸스원 같은 10만원 와인"
→ tokens: [오푸스원, 같은, 10만원, 와인]

정답:

intent = mixed_similarity_search
anchor = Opus One
constraint.price <= 100000
route = mixed
policy.allow_approximate = true
policy.require_exact = false
2.2 Planner와 Policy Compiler는 분리

Planner가 하는 일:

intent
anchors
constraints
route proposal
expansions

Policy Compiler가 하는 일:

exact 강제 여부
approximate 허용 여부
clarification 강제 여부
fallback 모드 결정

즉:

Planner = WHAT
Policy = HOW FAR
2.3 Query는 항상 불확실성을 가진다

Planner 출력에는 uncertainty가 반드시 포함돼야 한다.

왜냐하면:

마고는 ambiguity 높음
오푸스원은 대체로 entity 쿼리
묵직한 와인은 entity가 아니라 preference query
샤또마고 2018은 entity 강하지만 vintage ambiguity 가능

즉 query understanding은 deterministic parsing + uncertainty modeling 둘 다 필요하다.

3. 출력 SSOT
3.1 QueryPlanV1

RFC-000 §4.1과 **필드 의미가 같아야 한다.** (이 RFC는 필드 확장·타입만 구체화)

QueryPlanV1 {
  raw_query: string
  normalized_query: string

  intent: QueryIntent
  route: QueryRoute
  query_class: QueryClass        // **Q** — RFC-000 §8.4의 `T_resolve(Q)`, `T_gap(Q)` 튜닝 입력

  anchors: AnchorCandidate[]
  constraints: ConstraintBundle
  expansions: ExpansionBundle

  policy: QueryPolicy
  uncertainty: QueryUncertainty

  planner_version: string
  policy_rule_version: string     // Policy Compiler 규칙 세트 버전 (재현성·A/B)

  threshold_profile_id: string   // §7.4 `ThresholdProfileV1.id` — `T_resolve(Q)`, `T_gap(Q)` SSOT

  admission_context?: {
    requires_identity_seal: boolean      // exact / mixed anchor path 등
    requires_constraint_evidence: boolean
    requires_anchor_evidence: boolean
  }

  session_context?: SessionContext   // §7.5 — P1 follow-up·세션
  query_budget?: QueryBudget         // §7.6 — 비용·지연 상한
}

이게 이 RFC의 핵심 산출물이다.

**`admission_context`:** RFC-016 Admission Gate가 **`resolved` 허용 조건**을 닫는 데 쓴다. Planner는 `resolved`를 확정하지 않지만, 어떤 종류의 **evidence·identity sealing**이 필요한지는 미리 표면화해야 한다.

**역할 분리:** `uncertainty`·`policy.require_clarification`·`ambiguous_short_form` 등은 downstream에서 **ambiguity 플래그 `A`**(RFC-000 §8.4)와 합성될 수 있다 — Planner가 `A`를 최종 확정하지 않는다.

3.2 QueryIntent
enum QueryIntent {
  entity_exact
  entity_fuzzy
  facet_search
  semantic_discovery
  pairing_search
  budget_search
  comparison_search
  mixed_query
}

주의:

intent는 하나일 수도 있고 dominant + secondary일 수도 있다
다만 planner 출력은 최종 dominant intent를 반드시 하나 고정해야 한다

3.2.1 Multi-intent Decomposition

단일 쿼리에 복수 intent가 공존할 수 있다.

예:
- "오푸스원 2018 가격이랑 2019 비교" → entity_exact + comparison_search
- "나파 카베르네 추천해주고 가격도 알려줘" → semantic_discovery + budget_search
- "마고 와인 말고 비슷한 거" → entity_fuzzy + mixed_query (+ exclusion)

**처리 규칙:**

1. **dominant intent 고정:** 항상 하나의 `intent`를 primary로 선택한다 (§3.2 기존 원칙 유지).
2. **secondary_intents 필드 추가:**
   ```
   secondary_intents?: QueryIntent[]   // 보조 intent — routing에는 dominant만 사용, evidence·응답 구성에 활용
   ```
3. **Decomposition 판단:**
   - intent 간 route가 동일하면 → 합성 가능 (단일 route로 처리)
   - intent 간 route가 다르면 → **dominant route 우선**, secondary는 결과 후처리에서 반영 (예: 가격 정보 보강)
   - **금지:** 하나의 쿼리를 2개 독립 QueryPlan으로 분리해서 병렬 실행 (P0에서는 복잡도 대비 이득 부족)

4. **comparison_search 특수 처리:** 복수 anchor가 있으면 `anchors[]`에 모두 포함, RFC-006 multi-entity resolve로 넘긴다.

3.3 QueryRoute
enum QueryRoute {
  entity
  hybrid
  mixed
}

정의:

entity: exact/fuzzy entity resolution 우선
hybrid: lexical + semantic + structured retrieval
mixed: anchor + constraint + candidate search
3.4 QueryClass

이건 decision boundary 튜닝용이다.

enum QueryClass {
  short_entity
  ambiguous_short_form
  anchored_similarity
  pure_constraint
  semantic_preference
  comparison_query   // multi-entity 비교 — RFC-006 multi-entity resolve
  unknown
}

예:

오푸스원 → short_entity
마고 → ambiguous_short_form
오푸스원 같은 10만원 와인 → anchored_similarity
10만원 이하 드라이 레드 → pure_constraint
부드럽고 달지 않은 와인 → semantic_preference

이 `query_class`는 RFC-000 §8.4에서 `T_resolve(Q)`, `T_gap(Q)` 튜닝에 직접 쓰인다.

4. AnchorCandidate
4.1 정의
AnchorCandidate {
  surface_form: string
  normalized_form: string

  candidate_entity_ids: EntityId[]
  confidence: float              // anchor 후보 신뢰도 — **≠ RFC-000 calibrated C**

  source: "alias" | "planner_heuristic" | "entity_lookup"
}
4.2 의미

anchor는 “이 쿼리가 무엇을 중심으로 회전하는가”를 나타낸다.

예:

오푸스원 같은 10만원 와인

여기서

anchor = Opus One
나머지는 similarity + constraints

anchor가 없으면 mixed query는 풀 수 없다.

4.3 anchor 추출 규칙

다음 경우 anchor를 적극 추출한다.

known entity alias strong match
producer/wine mention 후 “같은”, “비슷한”, “말고”, “대신” 같은 패턴
comparison query (A vs B, A보다 덜 ~)
5. ConstraintBundle
5.1 구조
ConstraintBundle {
  hard: NormalizedConstraint[]
  soft: NormalizedConstraint[]
  inferred: NormalizedConstraint[]
}

5.1.1 ExclusionConstraint

"~말고", "~빼고", "~제외" 패턴을 처리한다.

NormalizedConstraint에 추가:
```
operator: "=" | "<=" | ">=" | "range" | "in" | "exclude"
```

**exclude 용법:**

- **Entity exclusion:** "오푸스원 말고 비슷한 거" → `{ attribute: "entity_id", operator: "exclude", value: "ent_opus_one", source_phrase: "오푸스원 말고" }`
- **Attribute exclusion:** "스파클링 빼고" → `{ attribute: "style", operator: "exclude", value: "sparkling", source_phrase: "스파클링 빼고" }`

**처리:**

- `exclude` constraint는 **hard constraint로 기본 분류** (사용자가 명시적으로 제외를 요청했으므로)
- retrieval 단계(RFC-012)에서 **negative filter**로 반영
- entity exclusion은 candidate pool에서 해당 entity를 제거하되, **anchor profile은 유지** (제외 대상이 anchor일 수 있음 — "오푸스원 말고 비슷한" = anchor는 오푸스원, 결과에서는 제외)

5.2 NormalizedConstraint
NormalizedConstraint {
  attribute: string
  operator: "=" | "<=" | ">=" | "range" | "in"
  value: string | number | [number, number]

  source_phrase: string
  confidence: float
}
5.3 RFC-004 정합

`attribute`·`value` 범위는 **RFC-004** 정규화 스키마·`mapping_version`과 충돌 없이 매핑되어야 한다. 가격·통화는 QueryPlan 메타(로케일)와 함께 고정한다.

5.4 예시

10만원 이하 드라이 레드

{
  "hard": [
    {"attribute":"price", "operator":"<=", "value":100000, "source_phrase":"10만원 이하"},
    {"attribute":"style", "operator":"=", "value":"red", "source_phrase":"레드"}
  ],
  "soft": [
    {"attribute":"sweetness", "operator":"<=", "value":0.2, "source_phrase":"드라이"}
  ],
  "inferred": []
}
5.5 hard/soft 판정 원칙

hard:

사용자가 명시적으로 필수 조건으로 말함
위배 시 결과가 무의미해짐

soft:

성향/뉘앙스/선호
일부 위반 허용 가능

inferred:

쿼리 문맥상 시스템이 추론
반드시 provenance 남겨야 함

예:

고기랑 잘 어울리는 → pairing=beef (soft)
선물용 → occasion=gift (soft/inferred)
입문용 → approachable/high complexity penalty (soft)
6. ExpansionBundle
6.1 구조
ExpansionBundle {
  lexical: string[]
  semantic: string[]
}
6.2 목적

expansion은 retrieval recall을 높이기 위한 것이지, identity를 강제하는 것이 아니다.

예:

묵직한 와인

lexical expansion:

full-bodied wine
rich red wine

semantic expansion:

Cabernet Sauvignon heavy style
bold structured wine
6.3 규칙
expansion은 planner가 만들 수 있다
하지만 policy에 따라 사용 여부를 제한할 수 있다
entity route에서는 expansion이 entity identity를 오염시키면 안 된다

예:

케이스 1

케이스 2

마고

  "fallback_mode": "clarify"
}
케이스 3

오푸스원 같은 10만원 와인

  "require_exact": false,
  "allow_approximate": true,
  "require_clarification": false,

7.3 policy compile 규칙

다음 요소를 본다.

intent
query_class
anchor confidence
ambiguity patterns
explicit numeric constraints 존재 여부
entity surface form 강도
known short-form ambiguity 사전

**결정론:** 동일 입력·동일 `planner_version`·`policy_rule_version`·`threshold_profile_id`이면 **동일 QueryPolicy·동일 임계 프로파일 조회**가 나와야 한다 (튜닝·실험은 버전으로 분리).

7.4 ThresholdProfileV1 (SSOT)

`T_resolve(Q)`, `T_gap(Q)`·abstention·ambiguous 패널티를 **query class별로 버전 고정**한다. region/실험군별로 다른 프로파일은 **id만 바꿔** 라우팅한다.

```
ThresholdProfileV1 {
  id: string
  version: string

  per_query_class: {
    short_entity: { resolve_tau: float, gap_tau: float }
    ambiguous_short_form: { resolve_tau: float, gap_tau: float }
    anchored_similarity: { resolve_tau: float, gap_tau: float }
    pure_constraint: { resolve_tau: float, gap_tau: float }
    semantic_preference: { resolve_tau: float, gap_tau: float }
    comparison_query: { resolve_tau: float, gap_tau: float }
    unknown: { resolve_tau: float, gap_tau: float }
    // **QueryClass enum과 1:1** — 누락/별도 키 금지
  }

  ambiguity_penalty_default: float
  abstention_policy_ref?: string   // 문서·정책 id
}
```

- Decision Layer(RFC-007)는 `threshold_profile_id`로만 수치를 조회한다 — **하드코드 금지**.
- RFC-010 학습 루프가 **제안**하는 프로파일은 promotion gate(RFC-009·010) 통과 후 `id`가 배포된다.
- route/intent 차이는 `QueryPolicy`·`abstention_policy_ref`에서 다루고, **threshold lookup key는 항상 `query_class` 하나로 닫는다.**

**Selective Prediction 연동 (RFC-009 §5.3):** `T_resolve(Q)`·`T_gap(Q)` 튜닝은 **AURC (Area Under Risk-Coverage Curve)**·`SelectiveRisk(τ)` 기반으로 수행한다. 단순 accuracy 최적화가 아니라, coverage-risk tradeoff 곡선에서 **운영 포인트**를 선택하는 것이 올바른 방법이다.

7.5 SessionContext (P1 — stateless 엔진 위 세션)

```
SessionContext {
  session_id: string

  previous_entities: EntityId[]
  previous_constraints?: ConstraintBundle
  last_decision_status?: "resolved" | "ambiguous" | "failed"
  last_query_plan_ref?: string
}
```

- **follow-up:** 동일 `session_id`에서 planner는 **anchor 상속·constraint 정제**를 우선 시도한다 (RFC-007 ambiguity 감소).
- 저장·TTL·PII는 제품 정책 — 본 RFC는 **필드 계약**만.

7.6 QueryBudget (P1 — 비용·지연)

```
QueryBudget {
  max_latency_ms: number
  max_candidates: number
  rerank_limit: number
  max_dense_calls?: number
}
```

- Planner가 **hint**로 생성 — 실행기(RFC-012·013)가 adaptive pipeline(쉬운 쿼리는 rerank skip 등)을 **예산 내**로 맞춘다.

8. Planning 전략
8.1 Fast Path

아래 조건이면 빠른 path로 간다.

known strong alias
low ambiguity
short entity query
numeric/semantic constraint 거의 없음

예:

오푸스원
케이머스
샤또마고 2018

출력:

route = entity
policy.require_exact = true
8.2 Deep Path

아래는 deep path다.

mixed query
semantic discovery
multiple constraints
ambiguity 높음
comparison query

예:

오푸스원 같은 10만원 와인
고기랑 어울리는 달지 않은 와인
케이머스보다 덜 무거운 와인

출력:

route = mixed or hybrid
expansions 활성화
inferred constraints 허용
8.3 route 결정 규칙

기본 원칙:

strong anchor + no meaningful constraint → entity
no anchor + preference/constraint 중심 → hybrid
anchor + additional semantic/budget/preference → mixed
8.4 Follow-up & session (P1)

`session_context`가 있고 이전 턴에 anchor가 확정됐으면:

- 동일 anchor를 **재질문 없이** 후보로 유지
- 사용자가 “더 싸게”, “다른 지역” 등만 바꾼 경우 **constraints만 갱신**

comparison_query(`query_class`)는 **복수 anchor 후보**를 추출해 RFC-006 multi-resolve로 넘긴다.

8.4.1 Reformulation-aware Planning (P1)

동일 세션 내 쿼리 연쇄가 reformulation인지 판단하고 context를 이어받는다.

**Reformulation 탐지 규칙:**

1. **Entity refinement:** "마고" → "샤또마고" → "샤또마고 2015" — 점진적 구체화. anchor candidate가 이전 턴의 부분집합이면 reformulation.
2. **Constraint narrowing:** "레드 와인" → "10만원 이하 레드" — 이전 intent 유지 + constraint 추가. intent·route 동일하면 constraint union.
3. **Correction:** "오퍼스원" → "오푸스원" — 이전 query와 edit distance가 작고 intent 동일하면 correction으로 간주. 이전 턴의 ambiguity/failure를 반영.
4. **Topic switch:** "오푸스원" → "묵직한 화이트" — anchor·intent 모두 변경. 새 QueryPlan 생성 (이전 context 무시).

**Planner 행동:**

- reformulation인 경우:
  - 이전 턴의 `anchor_candidates`를 **warm start**로 재사용 (re-resolve 생략 가능)
  - 이전 턴의 `constraints`를 **base**로 두고 현재 턴의 constraint를 merge
  - 이전 턴의 `decision_status`가 `ambiguous`였으면 현재 턴의 `uncertainty.ambiguity_severity`를 **한 단계 낮춤** (사용자가 구체화했으므로)
- topic switch인 경우: `SessionContext.previous_entities`는 유지하되 constraint·anchor는 초기화

9. Ambiguity Handling at Planning Stage

이 단계에서 이미 ambiguity를 일부 surface해야 한다.

9.1 ambiguity sources
short alias collision
producer vs wine
region vs wine
missing vintage in high-ambiguity family
overloaded marketplace expression
9.2 planner responsibility

planner는 ambiguity를 해결하지는 않지만, 탐지하고 policy에 반영해야 한다.

예:

마고

{
  "route": "entity",
  "policy": {
    "require_clarification": true,
    "fallback_mode": "clarify"
  },
  "uncertainty": {
    "ambiguity_detected": true,
    "ambiguity_type": ["wine_vs_region", "producer_family"]
  }
}
10. Uncertainty Model
10.1 구조
QueryUncertainty {
  overall: float

  ambiguity_detected: boolean
  ambiguity_types: string[]

  ambiguity_severity: "low" | "medium" | "high"

  // Planner가 요구하는 Decision 효과 — 단순 bool A로 뭉개지 않게
  decision_effect:
    | "trace_only"
    | "raise_threshold"
    | "force_clarify"
    | "block_resolve"

  parser_confidence: float
  anchor_confidence: float
  constraint_confidence: float
}
10.2 원칙

uncertainty는 planner 단계에서 끝내는 게 아니라 downstream으로 전달돼야 한다.

왜냐하면:

RFC-006 Entity Resolver
Decision Layer (RFC-000 **§8.4** — 최종 상태 확정)
eval harness (RFC-000 §10.7 등)

가 이 신호를 계속 써야 하기 때문이다.

`parser_confidence`·`anchor_confidence` 등은 **planner 내부 불확실도**이며, **런타임 calibrated `C`**(RFC-000)와 동일 객체가 아니다.

11. Failure Modes
11.1 Route Misclassification

entity여야 할 쿼리를 hybrid로 보냄

11.2 Mixed Query Collapse

anchor를 못 잡아서 일반 semantic search로 흘러감

**semantic-only downgrade 허용 조건 (형식화):**

- `query_class`가 **ambiguous_short_form**·**exact-ish anchor collision**이면 → **forbid_semantic_downgrade** — semantic으로만 흘리지 말고 clarify 또는 hybrid+clarify.
- **preference-heavy mixed**·**anchored_similarity**에서 anchor가 **의도적으로 없음**(순수 유사 탐색)이면 → `safe_hybrid_allowed`로 hybrid만 허용 가능.
- 정책 필드 `degrade_policy`는 RFC-011과 동일 vocabulary로 맞춘다.

11.3 Over-Approximation

exact 쿼리인데 approximate 허용

11.4 Under-Approximation

탐색형 쿼리인데 exact 강제해서 no result

11.5 Inferred Constraint Hallucination

planner가 근거 없이 의미를 과하게 추론

12. 메트릭
route accuracy
policy compile accuracy
anchor extraction precision/recall
constraint extraction precision/recall
ambiguity detection accuracy
inferred constraint usefulness
mixed query planning success rate

특히 꼭 볼 것:

entity→hybrid misroute rate
hybrid→entity lock rate

이건 전체 시스템 품질을 크게 깎는다.

특히 **RFC-000 §10.7 Decision Utility**·wrong-resolve와 함께 본다.

13. 출력 계약

이 RFC의 산출물은 다음 RFC들의 입력이다.

RFC-006 Entity Resolver
RFC-012 Hybrid Retrieval
RFC-011 Mixed Query Solver

**Decision Layer**는 RFC-000에 통합 정의(§8.4); 구현에서 모듈을 분리해도 **입력은 QueryPlan**이어야 한다.

즉 planner 결과는 ephemeral parsing output이 아니라 하위 전체의 **SSOT query contract**다.

14. 릴리즈 게이트

다음 조건 없이는 rollout 금지.

route accuracy 목표치 충족
high-traffic ambiguous short-form 탐지 안정화
anchor extraction precision 충분
inferred constraint hallucination 낮음
exact query에 대한 over-approximation 거의 없음

15. 체크리스트 (리뷰용)

- [ ] Planner와 Policy Compiler 출력이 **분리 평가** 가능한가 (RFC-000)
