RFC-012
Hybrid Retrieval System (Sparse + Dense + Fusion + Constraint-aware Candidate Generation)

**상위·연관 문서**

- `RFC-000: Wine Intelligence Engine Master Architecture.md` — **§12 기술 스택**(Vespa, BM25→SPLADE, BGE-M3, HNSW, Cross-Encoder phase), **§6 SignalSet**(retrieval은 신호 기여), **§9 evidence**(Vespa `summary-features` 등)
- `RFC-005` — `QueryPlanV1`, `route`, `query_class`, lexical/semantic expansion
- `RFC-004` — hard/soft constraint 정규화
- `RFC-011` — mixed query에서 본 RFC의 후보 생성과 연결
- `RFC-003` — projection의 `aliases`는 **타입·출처**를 갖는 SSOT의 투영
- `RFC-015` — 인덱스·모델 버전 스냅샷, **projection contamination** 점검
- `RFC-008` — `RetrievalTrace` → **EvidenceItem** / eval
- `RFC-016` — retrieval·rerank는 **신호**; 최종 `resolved`는 Admission Gate 통과 시에만

**충돌 시 RFC-000 우선.**

0. 목적

Track B는 이런 질의를 처리해야 한다.

묵직한 레드
10만원 이하 선물용 와인
고기랑 잘 어울리는 달지 않은 와인
나파 카베르네 입문용
오푸스원 같은 10만원 와인의 candidate generation 부분

이 문제는 단일 retrieval 방식으로는 안 풀린다.

sparse만 쓰면 의미 recall이 약하고
dense만 쓰면 exact signal과 constraint 통제가 약하고
filter만 쓰면 discovery가 약하다

따라서:

Hybrid Retrieval은 sparse, dense, structured filter를 결합한 candidate generation layer 여야 한다.

**RFC-016:** retrieval candidate가 **EntityRef sealing**을 우회하여 exact identity authority로 승격되는 것은 금지한다.

1. 비목표

| 하지 않음 | 담당 |
|-----------|------|
| 최종 entity resolve | RFC-006 |
| ambiguity **최종** 확정 | Decision Layer (RFC-000 §8) |
| clarification UX | 제품 |
| **최종** decision authority | RFC-000 §8 / RFC-007 |
| counterfactual explanation | RFC-000 §9.4 |

즉 이 RFC는 **candidate generation + fusion contract**다 — **high recall pool**이지 최종 답이 아니다.

2. 핵심 원칙
2.1 Candidate generation, not final authority

이 RFC가 가장 중요한 이유는, 많은 시스템이 retrieval score를 final truth처럼 쓰기 때문이다.

절대 금지:

top1 retrieval result = final answer

정답:

retrieval = high-recall candidate pool
decision = downstream authority
2.2 Sparse와 Dense는 대체재가 아니라 상보재
sparse는 exact token/phrase/alias/field alignment에 강함
dense는 paraphrase/preference/discovery에 강함

즉:

둘 중 하나를 선택하는 게 아니라, 서로 다른 실패모드를 커버하게 조합해야 한다

2.3 Constraint-aware retrieval

이 시스템은 generic semantic search가 아니다.
따라서 retrieval 단계부터 constraint를 존중해야 한다.

예:

10만원 이하
레드
화이트
price <= 100k
style = red

2.4 Retriever extensibility contract

새 sparse variant, 새 dense retriever, 새 neighborhood generator를 붙일 수 있다. 다만 **후보 생성기 추가**는 아래 계약을 지켜야 한다.

- 출력은 항상 **`HybridCandidate` + `RetrievalTrace`** 로 수렴한다.
- 새 source는 hard filter·identity-safe field 규칙을 우회하지 않는다.
- source별 점수는 직접 authority가 아니라 **retrieval trace / fusion 입력**으로만 들어간다.
- 승격은 RFC-009·015 gate(utility, drift, latency, replay) 통과 후만 허용한다.

이런 hard constraint는 retrieval 이후가 아니라 retrieval 중에도 반영되어야 한다.

2.4 Query route별 retrieval profile 분리

모든 쿼리에 같은 retrieval profile을 쓰면 망한다.

예:

exact entity query
semantic preference query
mixed query anchor follow-up
comparison query

는 candidate generation 전략이 달라야 한다.

즉 query_class, route에 따라 retrieval profile을 분리해야 한다.

4. 입력 계약

**Blocking 전제 (RFC-006 §3.3):** Track A (entity resolve)에서는 Resolver 이전에 **blocking**으로 후보를 사전 필터한다. Track B (hybrid retrieval)에서도 structured filtering(§7)이 동일한 역할을 한다. 두 경로 모두 **정답이 candidate pool에서 탈락하지 않는 것**이 전제이며, blocking/filter recall은 RFC-009 eval에서 별도 추적한다.

5. Sparse Retrieval
5.1 목적

sparse는 다음에 강해야 한다.

canonical/alias token recall
region/grapes/style exact phrase
short phrase alignment
budget/style phrase recall
constraint-aware lexical recall
5.2 baseline

초기 baseline은 BM25가 맞다.

이유:

구현/운영 단순
해석 가능성 높음
sparse recall baseline으로 안정적

SPLADE는 옵션이지만, **eval에서 net gain**이 확인된 뒤에만 승격한다 (RFC-000 §12 **Baseline → Upgrade path**).
비용과 운영 복잡도가 올라가기 때문이다.

5.3 sparse query 구성

planner에서 넘어온 lexical expansion을 사용한다.

예:

묵직한 와인

lexical_queries:
- "묵직한 와인"
- "full-bodied wine"
- "rich red wine"

10만원 이하 드라이 레드

lexical_queries:
- "드라이 레드"
- "dry red wine"
- "red wine"

단, sparse expansion은 entity identity를 덮으면 안 된다.

5.5 Sparse Upgrade Evaluation Protocol (BM25 → SPLADE)

RFC-000 §12에서 "SPLADE는 eval 후에만"이라고 했다. 구체적 평가 프로토콜을 정의한다.

**평가 축:**

| 축 | 지표 | 기준 |
|----|------|------|
| **Recall** | Recall@50, Recall@100 (query_class별) | BM25 대비 순증 ≥ 2% |
| **Precision** | hard constraint 필터 후 candidate 정밀도 | 악화 없음 |
| **Latency** | P50, P95 sparse retrieval latency | BM25 대비 ≤ 1.5x |
| **Index size** | sparse index 크기 | BM25 대비 ≤ 3x (SPLADE는 term expansion으로 커질 수 있음) |
| **Decision Utility** | RFC-009 §5.1 | 회귀 없음 |
| **wrong-resolve** | RFC-009 §4.1 | 악화 없음 |
| **Alias recall** | identity-safe alias의 candidate 포함률 | 악화 없음 |

**실행 절차:**

1. **Offline:** gold query set으로 BM25 vs SPLADE 병렬 평가 (위 7축 모두)
2. **Shadow:** production traffic에서 SPLADE를 shadow로 실행, BM25 결과와 diff 분석
3. **Canary:** 소량 트래픽에서 SPLADE 결과를 실제 사용. Decision Utility·wrong-resolve 모니터링.
4. **Full:** 게이트 통과 후 점진 확대.

**금지:** "최신 SOTA이므로 SPLADE가 당연히 좋다"는 논리로 BM25를 교체하는 것. 와인 도메인의 alias·multilingual 특성에서 SPLADE가 regression을 일으킬 수 있다 (특히 한국어 tokenization).

5.4 sparse field weighting

retrieval projection 문서에서 다음 필드들을 다르게 본다.

canonical_label
aliases_identity_safe
aliases_noisy_recall
producer
region
grapes
search_text_ko
search_text_en
semantic_summary
style / pairing / occasion field

원칙:

identity 관련 field > descriptive field
catalog_noise_alias field는 하한/상한 통제
promotional text는 sparse 핵심 field에서 배제 또는 약화
6. Dense Retrieval
6.1 목적

dense는 다음에 강해야 한다.

paraphrase
preference query
discovery
style similarity
“비슷한 느낌” 질의
mixed query에서 anchor-based semantic neighborhood
6.2 baseline model

dense baseline은 **BGE-M3 class** multilingual retriever 같은 계열이 적합하다 (RFC-000 §12).

이유:

다국어 대응
dense/sparse/multi-vector 확장 경로
한국어/영어 혼합 질의 대응

하지만 이 RFC는 특정 모델 고정을 강제하지 않는다.
핵심은 multilingual dense retriever interface 다.

6.3 dense query 생성

semantic_queries는 planner가 만든다.

예:

고기랑 잘 어울리는 달지 않은 와인

semantic_queries:
- "dry wine that pairs well with beef"
- "structured red wine for steak"

오푸스원 같은 10만원 와인

semantic_queries:
- anchor-profile-based similarity query
- premium napa-like red under 100k
6.4 dense retrieval 규칙
dense는 recall 확장용
dense score 하나로 final authority 금지
dense hit는 반드시 downstream constraint/attribute layer와 같이 해석

즉 embedding만으로 다 해결하려 하면 안 된다.

6.5 Late Interaction Retrieval (P1 평가 대상)

single-vector dense retrieval은 query-document interaction을 단일 벡터 유사도로 압축한다. 와인처럼 **entity name + attribute + region이 혼재된 쿼리**에서는 token-level interaction이 중요할 수 있다.

**후보 기술:**

- **ColBERT v2 / PLAID:** query token별로 document token과 MaxSim을 계산. "오푸스원 같은 묵직한" 같은 mixed query에서 "오푸스원"과 "묵직한"이 각각 다른 document token과 매칭.
- **ColPali (vision):** multi-modal extension path(RFC-000 §12.1)와 연결 가능.

**P1 평가 프로토콜:**

1. single-vector baseline 대비 **Recall@K** 비교 (K=50, 100, 200)
2. **query_class별 분리 평가:** mixed_query·semantic_preference에서 gains가 클 것으로 예상. short_entity에서는 차이가 작을 수 있음.
3. **latency regression 측정:** late interaction은 scoring 비용이 높음. `QueryBudget.max_latency_ms` 내 처리 가능한지.
4. **index size 비교:** ColBERT은 token-level embedding을 저장하므로 index 크기 증가. 비용 대비 효과.
5. **Decision Utility 영향:** retrieval recall 개선이 최종 Decision 품질로 이어지는지 (RFC-009).

**Vespa 정합:** Vespa는 ColBERT-style MaxSim을 **nearestNeighbor + custom ranking expression**으로 구현 가능. second-phase에서 full interaction을 계산하는 패턴이 자연스러움.

**승격 조건:** Recall@100 순증 ≥ 3% AND Decision Utility 회귀 없음 AND latency P95 ≤ budget.

7. Structured Filtering

이 시스템에서는 필터가 retrieval 이후 옵션이 아니다.
hard constraint는 retrieval 단계부터 반영해야 한다.

7.1 hard filter 예시
price <= 100000
style = red
region in {napa}
sweetness <= 0.2 (가능한 경우)
availability = true
7.2 soft preference 예시
full-bodied
gift-worthy
beginner-friendly
premium
steak pairing

이건 필터가 아니라 retrieval 이후 ranking signal이나 evidence로 반영한다.

7.3 원칙
hard constraint는 candidate pool 오염을 줄인다
soft constraint는 recall을 죽이지 않도록 filter하지 않는다
8. Candidate Pool Construction
8.1 병렬 retrieval

다음 후보군을 따로 만든다.

SparseTopN
DenseTopN
OptionalAnchorNeighborhoodTopN
8.2 pool union
CandidatePool = Union(SparseTopN, DenseTopN, AnchorTopN)

중복은 entity_id 기준으로 정리한다.

8.3 pool 크기

초기 권장:

sparse top 100
dense top 100
union 후 top 100~200
downstream rerank top 30~50

정확 수치는 latency budget과 eval에 따라 조정한다.

9. Fusion
9.1 baseline fusion

기본은 RRF(Reciprocal Rank Fusion) 가 맞다.

이유:

구현 단순
scale mismatch에 robust
sparse/dense raw score 정규화 부담 적음

즉 P1 baseline으로 적합하다.

9.2 weighted merge

다음 단계에서 가능하다.

retrieval_fusion_score =
  α * sparse_rank_signal
+ β * dense_rank_signal
+ γ * anchor_signal

하지만 raw score calibration 전에는 weighted raw merge를 조심해야 한다.

9.3 route별 fusion profile

예:

hybrid semantic query: dense 비중 상대적으로 높음
exact-ish hybrid query: sparse 비중 높음
mixed query: anchor signal 별도 가산

이건 query_class 기반으로 profile 분기 가능하다.

9.4 Adaptive Retrieval Pipeline (Cascade / Early Exit)

모든 쿼리에 동일한 full pipeline(sparse + dense + ANN + fusion + rerank)을 태우면 latency budget을 낭비한다.

**Query Difficulty Estimation:**

간단한 쿼리(short_entity + high alias confidence)는 expensive한 단계를 건너뛸 수 있다.

```
difficulty_estimate =
  f(query_class, anchor_confidence, alias_match_strength, constraint_count)
```

**Cascade 단계:**

| 난이도 | 파이프라인 | 예시 |
|--------|-----------|------|
| **Easy** (difficulty < τ_easy) | Sparse only → top-K → Decision | "오푸스원" (strong alias, short_entity) |
| **Medium** (τ_easy ≤ difficulty < τ_hard) | Sparse + Dense → RRF → top-K → Decision | "나파 카베르네 추천" |
| **Hard** (difficulty ≥ τ_hard) | Full pipeline (Sparse + Dense + ANN + Rerank) | "오푸스원 같은 10만원 묵직한 레드" |

**Early Exit 규칙:**

- Sparse 단계에서 **canonical_exact_match + confidence > 0.95**이면 dense retrieval skip 가능 (entity route only)
- Rerank 단계에서 **top-1과 top-2의 calibrated gap > 2 × T_gap(Q)**이면 remaining candidates rerank skip 가능

**Budget enforcement:**

- `QueryBudget.max_latency_ms`(RFC-005 §7.6) 초과 시 현재 단계까지의 결과로 Decision에 넘김
- 어떤 단계가 skip됐는지 `RetrievalTrace.skipped_phases[]`에 기록 → evidence·eval에서 추적 가능

**원칙:** cascade는 **latency 최적화**이지 **품질 타협**이 아니다. skip된 단계로 인해 wrong-resolve가 증가하면 τ 조정 또는 cascade 비활성화.

RetrievalTrace {
  retrieval_profile: string

13. Failure Modes
13.1 Dense Drift

semantic retrieval이 엉뚱한 스타일로 샌다

13.2 Sparse Lock-in

lexical exact만 잡고 discovery를 못 한다

13.3 Filter Leakage

hard constraint가 candidate pool에 제대로 안 먹는다

13.4 Promotional Contamination

retailer noise text가 sparse recall을 오염시킨다

13.5 Score Misuse

retrieval fusion score가 final authority처럼 사용된다

13.6 Projection contamination batch (운영 — RFC-015)

**정기 배치**로 projection·alias 인덱스를 스캔한다:

- alias·noisy 필드가 **retrieval hit에는 크게 기여**하지만 **identity 관련 필드와의 의미 일치**가 낮으면 **contamination 후보**로 플래그.
- 자동 삭제보다 **`suppressed`·prior cap·human review`**(RFC-003) 우선.

13.7 Index / embedding migration hygiene (SOTA++ 운영)

모델 교체·projection rebuild·ANN 파라미터 변경은 **검색 품질뿐 아니라 replay·latency**에도 직접 영향을 준다.

- 새 dense model / 새 index는 가능하면 **shadow index** 또는 **canary traffic**로 먼저 검증한다.
- ANN 파라미터(HNSW efSearch 등)·vector schema 변경 시 **offline Recall@K floor**와 **latency regression**을 동시에 본다.
- dual-index / dual-embed 전환 기간에는 `DecisionSnapshot.index_versions`·`model_versions`로 **어느 경로가 응답했는지** 남긴다 (RFC-015).

sparse retrieval

candidate pool union
fusion

이 RFC가 넘기는 것:

final ranking·rerank·signal integration → **SignalSet / second phase** (RFC-000 §6, §12 Cross-Encoder)
**최종 authority** → RFC-000 **§8** (RFC-007)
