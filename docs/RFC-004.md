RFC-004
Facet / Attribute Normalization SSOT

**상위·연관 문서**

- `RFC-000: Wine Intelligence Engine Master Architecture.md` — `SignalSet`의 hard/soft constraint, **Decision Layer**는 `C`·`Δ`·정책으로 최종 판정; EvidenceItem에 constraint 기여(§9)
- `RFC-001: Entity Identity Graph SSOT` — `Entity.attributes`와 **이름·단위 정합** (body/sweetness/region 등); attribute는 identity 분리 금지
- `RFC-003` — anchor·텍스트는 alias, **의미·조건**은 이 RFC의 정규화 공간

0. 목적

사용자는 이렇게 말한다.

“묵직한 와인”
“달지 않은 와인”
“고기랑 어울리는”
“10만원 이하”
“선물용 와인”

이건 문자열 매칭 문제가 아니라 의미 매핑 문제다.

따라서:

자연어 표현 → 정규화된 속성 공간으로 매핑하는 SSOT가 필요하다

이 RFC가 없으면:

semantic 검색이 drift 나고
constraint가 일관되지 않고
ranking이 embedding에 종속된다

1. 설계 원칙
1.1 Attribute는 “검색용 필터”가 아니라 “의미 공간”

잘못된 접근:

body = "full"
sweetness = "dry"

정답:

body ∈ [0,1]
sweetness ∈ [0,1]

즉:

attribute는 discrete label이 아니라 연속 의미 공간이다 (필요 시 enum은 **스타일·가격 버킷** 등 제한된 축에만)

1.2 Attribute ≠ Identity

절대 금지:

body 다르면 entity 다름
sweetness 다르면 다른 wine

attribute는:

identity의 설명이지, identity 정의 요소가 아니다

(RFC-001 §2.3과 동일 철학: attribute mismatch로 entity 분리 금지)

1.3 Human Language → Normalized Space

핵심 매핑:

"묵직한" → body ≥ 0.7
"가벼운" → body ≤ 0.3
"달지 않은" → sweetness ≤ 0.2

이 mapping은 **버전 있는 SSOT**로 고정한다 (`mapping_version`). 재현성·오프라인 eval에 필요하다.

1.4 런타임 decision confidence와의 구분

`NLMapping.mapping_confidence`·`InferredAttribute.inference_confidence`는 **속성 매핑/추론 불확실도**다 (필드명에 `mapping_` / `inference_` 접두로 **decision `C`**와 타입 레벨에서 분리).  
RFC-000의 **calibrated decision confidence `C`**(RFC-006 `decision_confidence_c`, RFC-007 `decision_confidence`)와 **같은 스케일·같은 객체가 아니다** — 합칠 때는 별도 캘리브레이션 또는 가중 규칙을 문서화한다.

2. Attribute Schema (SSOT)

RFC-001 `Entity.attributes`와 **필드 이름·단위**를 맞춘다.

Attributes {
  body: float         // 0.0 ~ 1.0
  sweetness: float    // 0.0 ~ 1.0
  acidity: float      // optional
  tannin: float       // optional

  style: enum         // red | white | sparkling | rosé | dessert
  price_band: enum    // normalized bucket (로케일·통화 규칙과 함께 정의, §3.3)

  pairing: string[]   // 정규화된 태그: beef, seafood, cheese, …
  occasion: string[]  // gift, casual, premium, …

  region: string      // RFC-001과 동일 정규화 키
  grapes: string[]    // RFC-001 필드명 `grapes`와 통일 (단수 grape 혼용 금지)
}

3. Core Attribute Definitions
3.1 Body
0.0 → 매우 가벼움
0.5 → 중간
1.0 → 매우 묵직함
3.2 Sweetness
0.0 → 드라이
1.0 → 매우 달다
3.3 Price Band (중요)

기본 예 (KRW 가정 — **운영 로케일·통화는 SSOT에 명시**):

| band | 의미 (예) |
|------|-----------|
| low | < 50k |
| mid | 50k ~ 150k |
| high | > 150k |

region별·시즌별 dynamic band를 쓸 경우에도 **버킷 정의와 경계**는 코드가 아니라 **버전 있는 테이블**로 둔다.

3.4 Pairing
beef
pork
seafood
dessert
cheese

주의:

pairing은 확정 truth가 아니라 확률적 추천·힌트

4. Natural Language Mapping
4.1 Mapping Layer 정의
NLMapping {
  phrase: string
  mapped_attribute: string
  operator: >= | <= | range | in
  value: float | [float, float]
  mapping_confidence: float   // attribute mapping 신뢰도 — **≠ decision `C`**
  mapping_version: string
  source: string          // rule id / editor / batch
}
4.2 예시
"묵직한 와인" → body ≥ 0.7
"가벼운 와인" → body ≤ 0.3
"달지 않은" → sweetness ≤ 0.2
"적당히 달달한" → sweetness ∈ [0.3, 0.6]
4.3 중요 규칙

mapping은 **deterministic**이어야 한다 (같은 입력·같은 `mapping_version` → 같은 constraint).

LLM이 **즉흥적으로** 하드 제약을 만들면 안 된다. LLM은 선택적으로 **후보 phrase 추출** 등에만 쓰고, 최종 수치는 **테이블·룰 엔진**을 통과해야 한다 (RFC-000: LLM never authority).

5. Constraint System
5.1 Hard vs Soft
Constraints {
  hard: []
  soft: []
}

Hard constraint

- 반드시 만족
- 실패 시 RFC-000 `hard_constraint_pass`에 해당 — 랭킹 단계에서 **필터/대형 페널티**로 모델링

예:

“10만원 이하”
“화이트 와인”

Soft constraint

- penalty 기반 (RFC-000 `soft_constraint_score`)

예:

“묵직한 느낌”
“고기랑 잘 어울리는”

5.2 Constraint Scoring (개념)

```
hard_pass = all hard constraints satisfied
constraint_contribution =
  (hard_pass ? 0 : -∞)   // 구현에서는 큰 페널티 또는 후보 제외
  + soft_score
```

최종 **확정 여부**는 여전히 **Decision Layer**(RFC-000 §8.4) — constraint만으로 RESOLVED 강제 금지.

6. Attribute Inference

문제:

모든 wine에 attribute가 완벽히 있지 않다

해결:

6.1 Inference Sources
grapes
region
style
historical data
6.2 예시
Cabernet Sauvignon → body 높음
Burgundy Pinot Noir → body 낮음
Sauternes → sweetness 높음
6.3 Inference 규칙
deterministic + statistical 혼합
mapping·inference confidence 포함

InferredAttribute {
  attribute: string
  value: float
  inference_confidence: float    // 추론 신뢰도 — decision `C`와 혼동 금지
}

추론은 **identity를 덮어쓰지 않는다**. 불확실하면 missing을 두고 RFC-000 `uncertainty_penalty`·ambiguous 쪽으로 기여할 수 있다.

7. Attribute Conflict Handling
7.1 Source conflict
서로 다른 값 존재

해결:

weighted merge
source trust 기반 (RFC-002 `SourceTrustProfile` 정합)

7.2 Missing vs Wrong

원칙:

missing > wrong

즉:

없으면 inference
틀리면 correction 필요
8. Mixed Query 대응

예:

“오푸스원 같은 10만원 와인”

처리:

anchor: Opus One
→ anchor profile 생성 (RFC-001 AnchorProfile)

constraint:
price ≤ 100k

similarity:
attribute distance 기반

9. Attribute Distance
9.1 정의
distance = Σ |attr_query - attr_candidate|  (가중치는 스키마 버전과 함께 고정)
9.2 활용
similarity search
recommendation
reranking

distance만으로 **entity 확정 금지** — RFC-000 Decision·alias·identity와 동일한 “신호일 뿐” 원칙.

10. Failure Modes
10.1 Discrete Label Trap
“full-bodied” 같은 label만 쓰는 경우
10.2 Inconsistent Mapping
같은 문장이 다른 결과 — **`mapping_version` 불일치** 방지
10.3 Over-reliance on Embedding
attribute 없이 semantic만 사용
10.4 Attribute Drift
source마다 다른 값 — **정규화·merge 정책** 없이 누적
10.5 Constraint ↔ Evidence 단절

constraint가 계산됐는데 **EvidenceItem**(RFC-000 §9)에 안 실리면 디버깅·LLM 소비 불가

11. Metrics
constraint satisfaction rate
attribute inference accuracy
mapping accuracy (버전별)
mixed query success rate
constraint-induced **wrong-resolve** (틀린 필터 확정)

RFC-000 **§10.7 Decision Utility**와 함께 본다 — nDCG만으로 부족.

12. Output

이 RFC의 산출물:

normalized attribute store (또는 Entity projection 필드)
NL → attribute mapping table (**버전 관리**)
constraint evaluation module (hard/soft → 신호·Evidence)
inference 규칙 세트

**주의:** 스토어 갱신 후 RFC-001 **projection rebuild**와 순서 정합 (RFC-002 §11.4와 같은 정신).

14. 체크리스트 (리뷰용)

- [ ] attribute로 **entity identity를 쪼개지** 않는가 (§1.2)
- [ ] NL mapping이 **버전** 없이 바뀌지 않는가 (§4)
- [ ] `mapping_confidence` / `inference_confidence`와 RFC-000 **`C`**를 혼동하지 않는가 (§1.4)
- [ ] hard constraint가 **LLM 즉흥**에 의존하지 않는가 (§4.3)
- [ ] constraint 결과가 **EvidenceItem**/디버그 경로로 나가는가 (§10.5)
