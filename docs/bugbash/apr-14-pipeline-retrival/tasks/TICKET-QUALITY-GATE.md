# Ticket Quality Gate

> 목적: 각 티켓이 "읽을 수는 있는데 실제로는 모호한 문서"로 남지 않게, 머지 전에 문서 자체의 완결성을 점검하는 체크리스트.

## 티켓 문서가 반드시 포함해야 하는 항목

1. 목표
2. 현재 근거
3. 선행 티켓
4. 정확한 산출물
5. 수정 대상 파일
6. 수정 금지 범위
7. 예상 충돌 파일
8. 착수 전 확인
9. 구현 단계
10. 작업 중단 조건
11. 롤백 기준
12. 금지사항
13. 수용 예시
14. 테스트
15. 검증 명령
16. 머지 전 체크리스트
17. 완료 조건

## 좋은 티켓의 기준

- 작업자가 코드를 처음 봐도 `어디를`, `왜`, `어떤 순서로`, `무엇을 남기고` 수정해야 하는지 알 수 있다.
- 티켓을 닫았는지 아닌지를 사람마다 다르게 해석할 여지가 없다.
- 실패 시 어떤 조건에서 멈춰야 하는지 적혀 있다.
- 범위 밖 파일을 건드리지 않도록 경계가 적혀 있다.
- 결과물이 코드인지, 테스트인지, 문서인지, schema인지 명시돼 있다.

## 나쁜 티켓의 신호

- "적절히", "필요 시", "가능하면", "대충" 같은 표현이 많다.
- 산출물이 모호해서 구현자가 문서만 보고는 완료 기준을 알 수 없다.
- 검증 명령이 너무 넓거나 아예 없다.
- 하나의 티켓에서 여러 에픽을 동시에 닫으려 한다.
- 현재 근거가 코드 링크 없이 서술만 있다.

## 머지 전 문서 품질 체크

- [ ] 작업자에게 요구하는 산출물이 명시돼 있다
- [ ] 작업 중단 조건이 있다
- [ ] 수정 금지 범위가 있다
- [ ] 예상 충돌 파일이 있다
- [ ] 롤백 기준이 있다
- [ ] 검증 명령이 실제 repo 명령과 맞는다
- [ ] 수용 예시가 "수용/비수용"으로 둘 다 적혀 있다

## 권장 티켓 크기

- 한 티켓은 가능한 한 한 번의 머지로 닫을 수 있어야 한다.
- 한 티켓이 5개 이상 subsystem을 강하게 건드리면 분리 후보로 본다.
- 한 티켓의 검증 명령이 4개를 넘으면, 별도 하위 티켓 분리를 검토한다.
