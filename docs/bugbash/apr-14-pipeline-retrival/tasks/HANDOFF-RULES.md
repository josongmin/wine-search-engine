# Task Handoff Rules

> 목적: 이 폴더의 티켓은 "아이디어 메모"가 아니라 바로 구현 가능한 작업지시서다.  
> 이 문서는 처음 들어온 작업자가 티켓을 잘못 해석하거나 범위를 잘못 넓히지 않게 막는 공통 작업 규칙이다.

## 이 문서를 먼저 읽어야 하는 사람

- 이 프로젝트 맥락을 잘 모르는 작업자
- 특정 티켓을 처음 맡는 작업자
- 티켓 구현 전에 "어디까지 바꾸는지" 경계를 확실히 알고 싶은 작업자

## 절대 규칙

1. `CompiledWineQuery`가 execution SSOT라는 전제는 깨지지 않는다.
2. unknown, corrupt, malformed, missing 값을 정상값처럼 위장하지 않는다.
3. heuristic fallback, silent fallback, neutral masking을 새로 만들지 않는다.
4. production fail-closed를 test 편의를 위해 약화시키지 않는다.
5. 티켓에 적힌 범위를 넘는 설계 변경은 임의로 끼워 넣지 않는다.

## 티켓 착수 순서

1. [README.md](./README.md)에서 해당 티켓의 Wave와 선행 관계를 확인한다.
2. 맡은 티켓 파일의 `선행 티켓`이 닫혔는지 확인한다.
3. `현재 근거` 링크를 전부 열어 실제 코드 상태를 먼저 본다.
4. `착수 전 확인` 명령을 실행해 현재 repo가 문서 설명과 같은 상태인지 확인한다.
5. `수정 대상 파일`만 먼저 읽고, 나머지는 필요할 때만 확장한다.
6. `구현 단계`를 위에서 아래로 순서대로 수행한다.
7. 각 단계가 끝날 때마다 관련 테스트를 즉시 돌린다.
8. 마지막에 `검증 명령` 전체를 다시 돌린다.

## 작업 중단 조건

아래 중 하나가 나오면 바로 멈추고 티켓 문서를 보강하거나 상위 티켓으로 올린다.

1. 티켓을 끝내려면 다른 에픽의 public contract를 먼저 깨야 하는 경우
2. 문서에 없는 대규모 schema 변경이 필요한 경우
3. 같은 변경을 두 개 이상의 티켓이 동시에 요구하는 경우
4. production code에 heuristic/fallback을 추가하지 않고는 티켓을 닫을 수 없는 경우
5. `수정 금지 범위`를 건드리지 않으면 테스트를 녹색으로 만들 수 없는 경우

## 작업자가 반드시 남겨야 하는 산출물

모든 티켓은 아래 산출물이 함께 있어야 한다.

1. 코드 변경
2. 관련 테스트 또는 snapshot gate
3. 필요 시 schema 또는 response contract 변경
4. 티켓 완료 조건을 만족했다는 근거

## 금지되는 머지 패턴

1. 테스트만 고치고 production contract는 그대로 두는 머지
2. production fail-closed 대신 `warn + default`로 바꾸는 머지
3. `z.unknown()`, `as any`, 자유 문자열 reason code, 빈 객체 fallback으로 우회하는 머지
4. 티켓 문서의 `완료 조건`을 충족하지 못했는데도 "부분 완료" 상태로 머지하는 것

## 리뷰어 체크포인트

리뷰어는 아래만 보면 된다.

1. 티켓의 `목표`와 `완료 조건`이 실제 코드에서 충족됐는가
2. `수정 금지 범위`를 침범하지 않았는가
3. 새 silent fallback이나 neutral masking이 생기지 않았는가
4. 테스트가 티켓의 핵심 failure mode를 실제로 잡는가
5. response/schema/doc 중 하나라도 빠진 반쪽 변경이 아닌가

## 빠른 판단 기준

- "이상한 값이 들어오면 default로 살려도 되나?" -> 안 된다.
- "일단 테스트 seam으로만 fallback 남겨도 되나?" -> 티켓 문서에 test seam이라고 명시된 경우만 된다.
- "문서에 없는 추가 리팩터를 같이 해도 되나?" -> 안 된다. 새 티켓으로 분리한다.
- "관련 파일이 더 보이는데 같이 정리해도 되나?" -> 같은 contract closure를 직접 막는 경우만 된다.
