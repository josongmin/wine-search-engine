RFC-017
IR Quality Flywheel: Vivino Dataset Activation, Golden Query Set, LTR, and Reranker

**상위·정합 문서**

- `RFC-000` — §6 SignalSet, §10 Eval (Decision Utility SSOT), §12 기술 스택, §14 데이터 플라이휠
- `RFC-002` — Bronze → Silver → Gold canonicalization 원칙 (raw source를 바로 SSOT에 넣으면 안 된다)
- `RFC-003` — Alias type·scope; catalog_noise_alias vs identity_safe_alias
- `RFC-009` — Evaluation 철학 (wrong-top1 최악, abstain은 실패 아님), NDCG·MRR·AURC
- `RFC-010` — Learning loop·Data Flywheel; behavioral signal은 truth가 아니라 evidence
- `RFC-012` — Hybrid retrieval; sparse/dense/fusion candidate generation
- `RFC-013` — Ranking Signals; signal은 authority 아님

**충돌 시 RFC-000 우선.**

---

## 0. 한 줄 정의

> Vivino 10K Bronze 데이터를 Gold 인덱스로 승격하고,
> LLM 기반 Golden Query Set을 구축하며,
> LambdaMART LTR과 실 Cross-Encoder Reranker로
> 수동 가중치 tuning의 한계를 데이터 드리븐으로 돌파한다.

## 1. 해결하고자 하는 문제

### 1.1 현재 시스템의 품질 천장

현재 IR 스택은 구조적으로 완성도 높다:
BM25 + HNSW ANN + RRF fusion + two-phase wine_aware rerank.

그러나 아래 세 가지 이유로 품질이 제자리에 묶여 있다.

**문제 1 — 인덱스에 데이터가 없다**

`seed-wines-real.ts`의 수동 90개 와인으로 운영하는 중.
Vivino 10K snapshot이 Bronze DB에 잠들어 있고 Vespa에 들어가 있지 않다.
10K 데이터가 없으면 retrieval recall 자체가 의미 없다.

**문제 2 — 모든 ranking weight가 수동 tuning이다**

`scoring-weights.ts`의 가중치는 직관 기반이다:
```
entityIntegrity: 0.15, semantic: 0.25, softConstraint: 0.20 …
```
어떤 쿼리 분포에서, 어떤 데이터셋에서 이 수치가 최적인지 검증된 적 없다.
데이터가 커질수록 수동 tuning은 확장되지 않는다.

**문제 3 — 평가할 Ground Truth가 없다**

35개짜리 golden-set.test.ts는 smoke test 수준이다.
- 실제 query distribution을 반영 못 함
- hard negative가 없어 ranking 품질 측정 불가
- multilingual, ambiguous, constraint-heavy query 커버리지 부족
- NDCG@10, MRR@10, Recall@100 측정 불가

이 세 문제가 연결되어 있다:
```
데이터 없음 → 인덱스 빈약 → Recall@100 낮음
                            ↓
Ground Truth 없음 → 품질 측정 불가
                            ↓
수동 가중치 → 데이터 드리븐 개선 불가
```

### 1.2 비목표

| 하지 않음 | 담당 |
|-----------|------|
| Entity SSOT core 정의 변경 | RFC-001·002 |
| Decision 경계 수식 변경 | RFC-000 §8.4 |
| 실시간 behavioral signal로 canonical 덮어쓰기 | RFC-010 §2.1 금지 |
| Vespa schema 구조 변경 | 별도 RFC |
| 새 query_class 추가 | RFC-005 |

### 2.3 Dataset Leakage Prevention Contract ⚠️ P0

학습/검증/게이트 split 설계는 이 contract를 위반하는 순간 LTR 성능이 과대평가된다.
"성능 좋아 보이는데 프로덕션에서 망하는" 유형의 가장 흔한 원인이다.

#### 2.3.1 Split Key 정의

분할 단위는 단순 entity_id가 아니다. 아래 4개 키의 조합으로 정의한다:

```
split_key = (
  entity_id,
  query_template_id,     // 동일 템플릿으로 생성된 쿼리들 묶음
  generation_run_id,     // 동일 LLM 배치 실행 ID
  alias_cluster_id       // 동일 alias prefix를 공유하는 entity 클러스터
)
```

**각 키가 필요한 이유:**

| 키 | 위반 시 leakage 유형 |
|---|---|
| `entity_id` | 동일 wine이 train/val에 동시 등장 → rank 암기 |
| `query_template_id` | 같은 템플릿 변형이 양쪽에 → 패턴 암기 |
| `generation_run_id` | 동일 LLM run의 paraphrase cluster가 양쪽에 → semantic 중복 |
| `alias_cluster_id` | "레오빌-바르통"이 train에 있을 때 "레오빌-포이페레"가 val에 → alias recall 과대 |

#### 2.3.2 차단 규칙

```
금지:
  - 동일 entity_id가 train과 val/gate에 동시 등장
  - 동일 query_template_id의 인스턴스가 split 경계를 넘음
  - 동일 generation_run_id 내 쿼리 쌍이 양쪽에 존재
  - 동일 alias_cluster_id (예: 레오빌 3개 샤토) 내 entity들이 train/val에 분산
  - 동일 semantic paraphrase cluster (cosine similarity > 0.92)가 split 경계를 넘음

허용:
  - 같은 region의 다른 producer 간 split (Napa 와인이 양쪽에 있어도 됨)
  - 같은 grape variety의 다른 producer (Cabernet이 양쪽에 있어도 됨)
```

#### 2.3.3 Split 실행 방법

```typescript
// scripts/eval/build-splits.ts
type SplitAssignment = 'train' | 'val' | 'gate';

function assignSplits(queries: GoldenQuery[]): Map<string, SplitAssignment> {
  // 1. alias_cluster_id 기준으로 클러스터 그룹화
  const clusters = groupByAliasCluster(queries);

  // 2. 클러스터 단위로 train 70% / val 15% / gate 15% temporal 분할
  //    (query 단위가 아니라 cluster 단위 → leakage 차단)
  // 3. gate는 무조건 가장 최신 시간축 (temporal holdout)
  // 4. 동일 generation_run_id는 반드시 동일 split에 배치

  return assignments;
}
```

#### 2.3.4 Leakage 검증 스크립트

```typescript
// scripts/eval/verify-splits.ts
// 위반 발견 시 ETL 중단, split 재계산
function verifySplitIntegrity(splits: SplitResult): string[] {
  const violations: string[] = [];

  for (const [qid, assignment] of splits.assignments) {
    const query = splits.queryMap.get(qid)!;

    // entity_id 중복 체크
    if (splits.entityIdsByAssignment['gate'].has(query.entity_id) &&
        assignment !== 'gate') {
      violations.push(`entity_id ${query.entity_id} in both ${assignment} and gate`);
    }

    // alias_cluster 중복 체크
    if (clusterAppearsInMultipleSplits(query.alias_cluster_id, splits)) {
      violations.push(`alias_cluster ${query.alias_cluster_id} crosses split boundary`);
    }
  }

  return violations;  // 비어있으면 통과
}
```

```typescript
// 1. canonical_label: display_name에서 생산자 중복 제거, 연도 분리
function normalizeLabel(displayName: string, vintageYear: number | null): string {
  // "Opus One Winery Opus One 2018" → "Opus One 2018"
  // vintage가 이름 안에 없으면 append
}

// 2. body/acidity/tannin: Vivino 1–5 → 0–1
function normalizeScale(vivinoScore: number, max = 5): number {
  return vivinoScore / max;
}

// 3. popularityScore: log-normalize across corpus
// FIRST PASS: compute max_ratings_count across all 10K
// SECOND PASS: score = log1p(count) / log1p(max_count)
function computePopularity(ratingsCount: number, maxCount: number): number {
  return Math.log1p(ratingsCount) / Math.log1p(maxCount);
}

// 4. search_text_en: tasting notes 조합
function buildSearchText(record: VivinoRow): string {
  const parts = [
    record.payload?.style?.description,
    record.payload?.style?.body_description,
    (record.payload?.taste?.flavor ?? [])
      .map((f) => f.group.replace('-', ' '))
      .join(', '),
  ].filter(Boolean);
  return parts.join('. ');
}

// 5. wine_type: Vivino style_id → enum
const VIVINO_STYLE_MAP: Record<string, WineType> = {
  'Red Wine': 'red', 'White Wine': 'white',
  'Rosé Wine': 'rosé', 'Sparkling Wine': 'sparkling',
  'Dessert Wine': 'dessert', 'Fortified Wine': 'fortified',
};
```

#### Step 1.2 — Alias 생성

이것이 검색 품질에서 가장 임팩트 큰 단계.

**Alias 타입 (RFC-003 준수):**

```typescript
type ProposedAlias = {
  value: string;
  type: 'translation' | 'phonetic' | 'catalog_noise_alias';
  source: string;              // 예: "rule:accent_fold_v1", "llm:ko_translit_v1"
  confidencePrior: number;     // RFC-003 prior seed
  needsReview: boolean;
};

type AliasBundle = {
  // SSOT: typed alias proposal set
  proposed: ProposedAlias[];

  // Retrieval projection: typed alias에서 파생된 flatten 복사본
  identitySafeProjection: string[];
  noisyRecallProjection: string[];
};
```

주의:
- SSOT는 `string[]`가 아니라 typed alias proposal이다.
- `identitySafeProjection` / `noisyRecallProjection`는 `RetrievalDocument` projection용 flatten 결과물일 뿐이다.
- flatten alias는 recall/ranking 보조 신호이며 identity 결정권이 없다.

**자동 생성 규칙:**

```typescript
function generateAliases(record: SilverWineRecord): AliasBundle {
  const proposed: ProposedAlias[] = [];

  // 1. producer only (vintage 없이)
  proposed.push({
    value: record.producer,
    type: 'translation',
    source: 'rule:producer_identity_v1',
    confidencePrior: 0.95,
    needsReview: false,
  });

  // 2. producer + vintage
  if (record.vintageYear) {
    proposed.push({
      value: `${record.producer} ${record.vintageYear}`,
      type: 'translation',
      source: 'rule:producer_vintage_v1',
      confidencePrior: 0.95,
      needsReview: false,
    });
  }

  // 3. label without accents (Château → Chateau, Müller → Muller)
  proposed.push({
    value: removeAccents(record.canonicalLabel),
    type: 'translation',
    source: 'rule:accent_fold_v1',
    confidencePrior: 0.92,
    needsReview: false,
  });

  // 4. short producer name (Château Margaux → Margaux)
  const shortProducer = extractShortName(record.producer);
  if (shortProducer) {
    proposed.push({
      value: shortProducer,
      type: 'catalog_noise_alias',
      source: 'rule:short_name_v1',
      confidencePrior: 0.40,
      needsReview: true,
    });
  }

  const identitySafeProjection = projectIdentitySafeAliases(proposed);
  const noisyRecallProjection = projectNoisyRecallAliases(proposed);

  return { proposed, identitySafeProjection, noisyRecallProjection };
}
```

#### Step 1.3 — Korean alias 배치 생성 (LLM)

한국어 음역은 **후보 생성**에 LLM을 쓰되, RFC-003의 typed alias + collision check를 통과해야 한다.
LLM 출력은 SSOT 확정값이 아니라 Bronze proposal이다.

**배치 스크립트:** `scripts/etl/generate-korean-aliases.ts`

```
입력: canonicalLabel + producer (10K rows)
출력: { entity_id, alias_proposals: ProposedAlias[] }

프롬프트 전략:
- 와인 이름의 한국어 음역 3가지 변형 생성
  (예: "Château Margaux" → ["샤토 마고", "샤또 마고", "샤또마고"])
- 일반적으로 쓰이는 변형 우선 (실제 한국어 와인 리뷰 용법)
- 생산자 단독 + 생산자+빈티지 둘 다
- 각 결과는 기본적으로 `phonetic` 또는 `catalog_noise_alias` proposal로만 시작
- cross-entity collision / Unicode confusable 검사 통과 전에는 projection 반영 금지
- high-collision alias는 `needsReview=true`로 human review queue에 보냄

배치 크기: 50개씩 (rate limit 고려)
비용 추정: 10K × ~20 token output ≈ 200K output tokens ≈ $0.60 (Haiku)
```

#### Step 1.4 — Deduplication (Bronze → Silver 진입 전)

Vivino 10K는 동일 wine+vintage가 다른 시점에 재수집된 중복 rows를 포함할 수 있다.
RFC-002 idempotency 요구사항: 동일 source_record_id 재처리 시 멱등해야 한다.

**중복 정의:** `(external_id, vintage_year)` 기준으로 동일 entity를 가리키는 rows.

**선택 규칙 (우선순위 순):**

```
1. 가장 최근 scraped_at
2. ratings_count 더 높은 것 (데이터 풍부도)
3. payload.style.description이 있는 것 (tasting notes 존재)
```

**Idempotency:** `entity_id = hash(source + ":" + external_id)` 기반으로 Vespa upsert.
동일 entity_id 재처리 시 overwrite하므로 중복 삽입 없음.

#### Step 1.6 — Document Expansion (doc2query)

sparse retrieval recall을 극적으로 개선하는 SOTA 기법.
각 문서에 대해 LLM으로 합성 query 5~10개를 생성하여 `search_text_en`에 추가 인덱싱.

```
입력: Silver record (canonical_label, producer, region, grape, tasting notes)
출력: 합성 query 5~10개

예시 — Château Margaux 2015:
→ "best bordeaux first growth"
→ "full bodied french red under 1000"
→ "cabernet dominant investment wine"
→ "elegant tannin structure margaux aoc"
→ "보르도 1등급 와인"

효과: "full bodied investment wine" 같은 자연어 쿼리가 BM25에서 hit.
비용: 10K × ~50 output tokens ≈ $1~3 (Haiku)
```

생성된 합성 query는 `searchTextEn` 필드에 append (원본 tasting notes와 분리 가능하게 delimiter 사용).

#### Step 1.7 — Vespa 인덱싱

**스크립트:** `scripts/etl/index-to-vespa.ts`

```typescript
// Silver → RetrievalDocument → Vespa feed
async function indexBatch(records: SilverWineRecord[]): Promise<void> {
  for (const chunk of chunkArray(records, BATCH_SIZE)) {
    // 1. 임베딩 생성 (배치) — instruction prefix 필수
    const texts = chunk.map(buildEmbedText);
    const embeddings = await embeddingService.embedBatch(texts);

    // 2. RetrievalDocument 조립
    const docs = chunk.map((r, i) => silverToRetrievalDoc(r, embeddings[i]));

    // 3. Vespa feed
    await Promise.all(docs.map((d) => searchIndex.upsert(d)));
  }
}

function buildEmbedText(r: SilverWineRecord): string {
  // Document side: NO instruction prefix for BGE-M3
  // (Query side에서 "Represent this sentence for searching relevant passages:" prefix 사용)
  return [
    r.canonicalLabel,
    r.producer,
    r.region,
    r.grapePrimary,
    r.searchTextEn,
  ].filter(Boolean).join('. ');
}
```

**Embedding: BGE-M3 Multi-Representation 활용**

BGE-M3는 single forward pass로 3가지 representation을 동시에 생산하는 모델이다:
- **Dense** (현재 사용 중) — global semantic similarity
- **Sparse (learned lexical weights)** — SPLADE 유사, 별도 모델 배포 불필요
- **ColBERT multi-vector** — token-level late interaction, 별도 모델 불필요

현재 dense만 사용하고 sparse/colbert 출력을 버리고 있다.
SPLADE와 ColBERT를 "범위 밖"으로 뺐지만, 이미 돌리고 있는 모델의 출력을 받기만 하면 된다.

```
Phase 1 (Epic 1): dense만 사용 (현재)
Phase 2 (Epic 3 eval 이후): embedding service에서 sparse weights도 반환
  → Vespa에 learned sparse field 추가
  → BM25 + learned sparse + dense = 3-signal RRF
Phase 3 (NDCG 개선 필요 시): ColBERT multi-vector 반환
  → Vespa MaxSim operator 활용
```

**Instruction prefix (필수):**

BGE-M3는 asymmetric retrieval 모델이다. query/document에 다른 prefix를 써야 성능이 나온다.
이 한 줄 차이로 recall이 수 % 움직인다.

```typescript
// Query side (검색 시):
const queryText = `Represent this sentence for searching relevant passages: ${rawQuery}`;

// Document side (인덱싱 시):
// prefix 없이 raw document text 사용
const docText = buildEmbedText(record);
```

**Embedding dimension 확장:**

현재 schema: `tensor<float>(x[128])` — BGE-M3 native 1024에서 87.5% 정보 손실.

```

또는: Matryoshka Representation Learning (MRL) 사용 시 128 유지 가능
```

**목표:** bootstrapping용 500개 graded-relevance query pool + release gate용 human-validated holdout 구축

**설계 원칙:**
- RFC-009: WrongTop1 최악. negative 쿼리 포함 필수.
- RFC-006: ambiguous query에서 resolver가 올바르게 abstain 하는지 검증.
- graded relevance (0–3): 이진 레이블은 NDCG 측정 불가.
- LLM 생성/라벨은 Bronze tier까지만. release gate는 별도 human-validated set만 사용.
- 학습용 세트와 게이트용 세트는 파일·시간축·query family 기준으로 분리한다.

#### Step 2.1 — Query Space 정의 (8개 시나리오)

와인 검색의 전체 query space를 사람 검색 + LLM retrieval 관점에서 펼치면 8개 축이다.
Golden query set은 이 8개 축을 **모두** 커버해야 한다.

| 시나리오 | query_class | 비율 | 수 | 예시 |
|---|---|---|---|---|
| A. 정확 엔티티 | `exact_entity` | 15% | 75 | "Opus One 2018", "Château Margaux 2015" |
| B. 짧은/모호한 별칭 | `ambiguous_short_form` | 12% | 60 | "마고", "레오빌", "안티노리" |
| C. 속성/취향 기반 | `semantic_preference` | 15% | 75 | "묵직하고 탄닌 강한 나파 레드" |
| D. 제약 기반 | `pure_constraint` | 12% | 60 | "5만원 이하 이탈리안 레드 DOCG" |
| E. 탐색/추천형 | `exploration` | 10% | 50 | "스테이크랑 어울리는 와인", "선물용", "입문자용 보르도" |
| F. 비교/유사품 | `similar_compare` | 10% | 50 | "opus one 비슷한 거", "마고급 더 저렴한 것" |
| G. 생산자/지역 카탈로그 | `catalog_browse` | 10% | 50 | "안티노리 대표 와인들", "나파 까쇼 탑 5" |
| H. OOV/오타/불완전 | `noisy_recall` | 8% | 40 | "샤또마고 18", "cab sav napa under 100" |
| — 부정 (no match) | `no_match` | 8% | 40 | 존재하지 않는 와인, 완전 OOV |

**합계:** 500 queries

시나리오 E·F·G는 기존 RFC-017 초안에서 빠져 있었다.
이 세 축은 단순 top-1 retrieval이 아니라 **set retrieval + diversity**가 핵심이다.

**시나리오별 평가 기준 차이:**

| 시나리오 | primary metric | 비고 |
|---|---|---|
| A, B, H | WrongTop1, MRR@10 | single entity resolve 중심 |
| C, D | NDCG@10, constraint satisfaction rate | ranking 품질 중심 |
| E, F, G | Recall@10, set diversity, coverage | set retrieval 중심 — top-1 accuracy보다 커버리지가 중요 |
| no_match | abstain precision | 올바르게 "결과 없음" 반환하는지 |

**시나리오 F 특수 요구사항 — Anchor-based similarity search:**
```
쿼리: "opus one 비슷한 거"
→ seed entity: Opus One 2018
→ attribute extraction: body=0.9, tannin=0.85, region=Napa, grape=Cabernet
→ constraint rewrite: body≥0.7, tannin≥0.6, region=Napa OR Bordeaux, price < seed.price
→ candidate retrieval + diversity (동일 producer 제외)
```
이 시나리오의 golden set에서는 seed entity가 relevant에 포함되지 않는다.
대신 "유사하지만 다른 와인"이 grade 3이다.

**시나리오 G 특수 요구사항 — Set retrieval:**
```
쿼리: "안티노리 대표 와인들"
→ target_type: producer → entity set
→ relevant: {Tignanello, Solaia, Guado al Tasso, Pèppoli, …}
→ grade 3 = 해당 producer의 대표 와인, grade 2 = 해당 producer의 마이너 와인
```
top-1 accuracy가 아니라 **Recall@10 + diversity within producer** 평가.

**언어 비율:** EN 60% / KO 30% / Mixed 10% (모든 시나리오에 균등 분배)

#### Step 3.1 — Offline Eval 스크립트

```typescript
type EvalResult = {
  dataset_tier: 'bronze' | 'silver' | 'gate';

  // 전체 요약
  ndcg_at_10: number;
  mrr_at_10: number;
  recall_at_100: number;
  decision_utility: number;      // RFC-009 §5.1
  wrong_top1_rate: number;       // RFC-009 §4.1 (가장 중요)
  safe_abstain_rate: number;
  avoidable_abstain_rate: number;

  // query_class별 슬라이스 (RFC-009 §6)
  by_query_class: Record<QueryClass, SliceMetrics>;
  // language별 슬라이스
  by_language: Record<'en' | 'ko', SliceMetrics>;

  // Selective prediction (RFC-009 §5.3)
  aurc: number;                  // Area Under Risk-Coverage Curve
  e_aurc: number;                // Excess AURC
};

// NDCG@K 계산
function ndcg(ranked: { entity_id: string; grade?: number }[], relevance: Map<string, number>, k: number): number {
  const dcg = ranked.slice(0, k).reduce((sum, hit, i) => {
    const grade = relevance.get(hit.entity_id) ?? 0;
    return sum + (Math.pow(2, grade) - 1) / Math.log2(i + 2);
  }, 0);
  const ideal = [...relevance.values()]
    .sort((a, b) => b - a)
    .slice(0, k)
    .reduce((sum, grade, i) => sum + (Math.pow(2, grade) - 1) / Math.log2(i + 2), 0);
  return ideal === 0 ? 0 : dcg / ideal;
}
```

운영 규칙:
- `bronze` / `silver` 결과는 진단용 대시보드와 모델 선택에만 사용.
- release blocking metric은 `gate` tier에서만 계산한다.
- `gate` tier는 LTR train/val 데이터와 disjoint여야 한다.

#### Step 4.3 — LambdaMART 학습

**도구:** `lightgbm` (TypeScript에서 Node.js child_process로 호출)
또는 Python 스크립트 (`scripts/ltr/train_lambdamart.py`)로 분리.

**Overfitting 경고:** 23 features × ~500 queries × ~100 candidates ≈ 50K 학습 예제.
GBDT에게 충분하지만 regularization이 반드시 필요하다.

```python
# scripts/ltr/train_lambdamart.py
import lightgbm as lgb
import numpy as np

params = {
    'objective': 'lambdarank',
    'metric': 'ndcg',
    'ndcg_eval_at': [5, 10],
    'learning_rate': 0.05,
    'num_leaves': 31,
    'min_data_in_leaf': 20,       # 5는 너무 낮음 — 50K 데이터에서 최소 20
    'feature_fraction': 0.8,       # random subspace — overfitting 방어
    'bagging_fraction': 0.8,
    'bagging_freq': 5,
    'lambda_l1': 0.1,
    'lambda_l2': 1.0,
    'n_estimators': 500,
    'early_stopping_rounds': 50,
}

# train / val은 temporal split
# gate holdout은 이후 시점의 별도 human-validated set으로 분리
# random split 금지, same query family cross-split 금지
model = lgb.LGBMRanker(**params)
model.fit(
    X_train, y_train, group=group_train,
    eval_set=[(X_val, y_val)], eval_group=[group_val],
)
model.booster_.save_model('models/lambdamart_v1.txt')

# === Feature importance 분석 (필수) ===
# 학습 후 반드시 실행. 결과를 models/feature_importance_v1.json에 저장.
importance = model.booster_.feature_importance(importance_type='gain')
# gain이 0인 feature → 제거 후보
# top-5 feature에 과도하게 집중 → 나머지 feature 엔지니어링 재검토
```

**Feature importance 출력 예시:** gain 기준 상위 feature가 bm25_canonical, closeness_embedding, entity_integrity에 쏠리면 정상.
popularity, availability 등이 0이면 해당 signal이 무용 → 근본 원인 (데이터 커버리지 등) 재검토.

### Epic 5: Cross-Encoder Reranker 실 구현

**목표:** 현재의 canonical-label 중심 reranking을 wine-aware passage reranking으로 확장

현재 구현은 완전한 `entityId placeholder` 스텁은 아니다.
실제 문제는 reranker 입력 passage가 `canonicalLabel` 위주라서
producer / vintage / region / tasting note 정보가 충분히 전달되지 않는다는 점이다.

#### Step 5.1 — 모델 선택

| 모델 | 언어 | 크기 | NDCG vs MiniLM | 추천 이유 |
|---|---|---|---|---|
| `cross-encoder/ms-marco-MiniLM-L-6-v2` | EN | 66M | baseline | 빠름, EN only |
| `BAAI/bge-reranker-v2-m3` | multilingual | 568M | +6% | BGE-M3 family, KO 지원 |
| `cross-encoder/mmarco-mMiniLMv2-L12-H384` | multilingual | 118M | +3% | 경량 multilingual |

**권장:** `BAAI/bge-reranker-v2-m3`
- BGE-M3와 동일 family → embedding space 일관성
- KO 쿼리 지원 필수 (한국어 사용자 30%)
- 568M이지만 top-20 rerank만 하므로 레이턴시 허용 범위

#### Step 5.2 — 와인 텍스트 조합

현재 `ranker.ts`는 대체로 `canonicalLabel`만 passage text로 넣는다.
Epic 5의 핵심은 `RerankerPort` 계약을 유지한 채,
candidate text assembly를 wine-aware하게 확장하는 것이다.

```typescript
// src/domain/ranking/service/ranker.ts 또는 text-assembly helper에서 구성
function buildWineText(entry: ScoredEntry): string {
  const parts: string[] = [
    entry.canonicalLabel,
    entry.producer,
    entry.vintageYear ? String(entry.vintageYear) : '',
    entry.appellation ?? entry.region ?? '',
    entry.country ?? '',
    entry.grapePrimary ?? '',
    entry.searchTextEn ?? '',
  ].filter(Boolean);
  return parts.join('. ');
}

const rerankCandidates: RerankCandidate[] = topK.map((entry) => ({
  entityId: entry.entityId,
  text: buildWineText(entry),
}));
```

**Adaptive Blend 전략 (query_class 기반):**

cross-encoder reranker는 semantic 쿼리에서 가장 효과적이다.
exact entity 쿼리에서는 BM25가 이미 정답을 1위에 올려놓으므로
reranker 가중치를 높이면 오히려 노이즈 개입이 늘어난다.

```typescript
// src/domain/ranking/service/rerank-blend.ts
const RERANK_BLEND_BY_CLASS: Record<QueryClass, number> = {
  semantic_preference:  0.75,  // reranker 효과 극대화 구간
  pure_constraint:      0.70,  // constraint-aware reranking 유효
  comparison_query:     0.65,  // passage 비교에 cross-encoder 유효
  ambiguous_short_form: 0.65,  // reranker가 disambiguation에 기여
  anchored_similarity:  0.60,  // anchor context 활용
  short_entity:         0.40,  // BM25 + entity_integrity 압도적, reranker 보조만
  unknown:              0.50,  // 중립
};

export function rerankBlendWeight(queryClass: QueryClass): number {
  return RERANK_BLEND_BY_CLASS[queryClass] ?? 0.55;
}

// blend: weight * rerank_score + (1 - weight) * aggregated_score
```

**Epic 4 LTR 완료 후 최종 목표:**
`RERANK_BLEND_BY_CLASS`도 결국 사람이 설계한 값이다.
Epic 4 LambdaMART 학습 시 `f24_rerank_score`를 feature로 추가하면
blend weight 자체가 데이터에서 학습된다 — query_class 테이블도 불필요해진다.

```typescript
// Epic 4 이후 LTR feature 추가:
f24_rerank_score: number;  // cross-encoder raw score (blend 없이 feature만)
// LambdaMART가 f24와 f01~f23의 상대적 중요도를 데이터에서 결정
```

즉 Epic 5는:
- `RerankerPort` 시그니처 변경이 아니라 candidate text assembly 개선이 핵심
- 필요하면 `ScoredEntry` / mapping layer에 producer, region, tasting note 필드 전달 경로를 추가
- adapter는 HTTP contract parsing과 score 반환에 집중

### Epic 6: Embedding Fine-tuning & Cross-Encoder Distillation

**목표:** retrieval recall 자체를 끌어올리기 (LTR은 이미 recall된 후보 안에서만 reorder)

이것이 아마 **LambdaMART보다 더 큰 NDCG 점프**를 줄 수 있는 이유:
LTR은 Recall@100 안에 들어온 candidate의 순서를 최적화한다.
embedding fine-tune는 Recall@100 자체를 넓힌다.
놓친 candidate는 아무리 좋은 LTR도 살릴 수 없다.

#### Step 6.1 — Contrastive Fine-tuning

500 golden queries + hard negatives → (query, positive, negative) triplets 구성.

```python
# sentence-transformers 활용
from sentence_transformers import SentenceTransformer, losses

model = SentenceTransformer('BAAI/bge-m3')

# Triplet: (query, positive_doc_text, hard_negative_doc_text)
train_loss = losses.MultipleNegativesRankingLoss(model)
# + in-batch negatives로 학습 효율 극대화
```

**주의:** fine-tune 후 기존 인덱스 전체 re-embedding 필요.
10K 문서이므로 비용 허용 범위 (~30분 CPU, ~3분 GPU).

#### Step 6.2 — Cross-Encoder → Bi-Encoder Distillation

Epic 5에서 배포된 cross-encoder score를 soft label로 사용하여 bi-encoder를 추가 fine-tune.
Hinton knowledge distillation을 retrieval에 적용한 표준 파이프라인이다.

```
1. Golden queries top-100 candidate에 대해 cross-encoder score 수집
2. (query, doc, cross_encoder_score) triplet 구성
3. Bi-encoder를 MSE loss로 fine-tune: cos_sim(q_emb, d_emb) → cross_encoder_score
4. 결과: retrieval 단계에서 이미 cross-encoder 수준 품질
        cross-encoder는 top-20 polish에만 집중
```

**의존성:** Epic 5 (cross-encoder 운영) + Epic 2 (golden queries) 필요
**효과:** Recall@100 개선 + 1-stage retrieval 품질 향상

**deliverable:**
- `scripts/ltr/finetune_embedding.py`
- `scripts/ltr/distill_cross_encoder.py`
- `models/bge-m3-wine-ft-v1/` (fine-tuned model weights)

## 6. 비목표 및 주의사항

### 6.1 RFC-010 §2.1 준수

Vivino `statistics.ratings_average`는 popularity signal의 초기값으로만 사용.
behavioral truth로 canonical을 덮어쓰지 않는다.

### 6.2 RFC-002 canonicalization 원칙

Vivino `display_name` → 바로 `canonical_label` 금지.
반드시 normalizeLabel() 변환 거친 후 Silver record로 만든 다음 SSOT에 반영.

### 6.3 LTR 모델 버전 관리 (RFC-015)

DecisionSnapshot 필드명은 RFC-015 SSOT를 그대로 따른다.
즉 `modelVersions` 같은 camelCase 변형을 새로 만들지 않는다.

LTR가 활성화되면 scorer bundle version은 우선 `policy_rule_version`에 포함하고,
향후 별도 RFC로 `DecisionSnapshot` 확장을 할 수 있다.
```typescript
decision_snapshot: {
  model_versions: {
    dense_model: 'BAAI/bge-m3@sha256:...',
    sparse_model: 'vespa-bm25-default@sha256:...',
    reranker_model: 'BAAI/bge-reranker-v2-m3@sha256:...',
  },
  index_versions: {
    retrieval_index_version: 'vespa-wine-entity@2026-04-05',
    alias_projection_version: 'alias-projection@2026-04-05',
  },
  policy_rule_version: 'ranking-policy:ltr_v1_bundle@sha256:...',
}
```

### 6.4 Temporal Split (RFC-009 §10.6)

Golden query set 분할 시 random split 금지.
고정 날짜 하드코딩 대신 수집 시점 기준 상대 분할을 사용한다.

- train: 가장 이른 시점의 Bronze/Silver query
- val: 그 다음 시점의 Bronze/Silver query
- gate holdout: 가장 늦은 시점의 human-validated Gate query
- same query family / same paraphrase cluster / same seed entity generated variant가 split을 가로지르지 않게 차단
- release gate는 항상 training / tuning cutoff 이후에 수집된 holdout만 사용

### 6.5 Decision Utility는 NDCG를 대체하지 않는다

반대도 마찬가지: NDCG가 좋아도 WrongTop1이 오르면 배포 금지.
두 지표를 **동시에** 게이트에 넣는다.

## 8. Architectural Dependencies (이 RFC가 열어두는 문제)

RFC-017은 "IR 품질 플라이휠"이다 — data pipeline, eval, LTR, reranker.
하지만 retrieval이 사람 검색 + LLM retrieval substrate로 동작하려면
아래 3개가 별도 RFC로 닫혀야 한다.

이 섹션은 RFC-017이 직접 해결하지 않지만,
**RFC-017의 결과물 (인덱스, eval, LTR)이 연결되어야 할 architectural gap**을 정의한다.

### 8.1 Entity Type Hierarchy & Query Target Type (→ RFC-001 확장)

**문제:**

현재 인덱스는 wine entity만 있다.
하지만 실제 검색의 30%+는 wine이 아닌 것을 찾는다:

```
"안티노리"        → producer 찾기
"마고"            → Château Margaux (wine)? Margaux AOC (appellation)?
"나파 까쇼"       → region + grape 조합 browse
"토스카나 슈퍼투스칸" → classification set browse
```

wine entity 하나를 resolve하는 문제와, producer/region/classification set을 찾는 문제는 다르다.
이 구분 없이 모든 쿼리를 wine entity resolve로 밀어넣으면:
- "안티노리" → Tignanello 하나만 반환 (producer의 다른 와인 누락)
- "마고" → entity type confusion → wrong resolve 또는 불필요한 abstain

**RFC-017과의 연결:**
- Epic 2 golden query set의 시나리오 B(모호 별칭), G(카탈로그 browse)가 이 gap에 직접 영향 받음
- Epic 4 LTR feature에 `query_target_type` feature 추가 필요 (wine/producer/region/style)
- Eval 시 entity type confusion을 별도 failure mode로 추적해야 함

**필요한 것 (별도 RFC):**

```
1. Logical entity type: Wine | Producer | Region | Appellation | Style | GrapeFacet
2. Query target type 추론:
   - "안티노리" + no vintage + no wine name → target_type = producer
   - "마고 2015" + vintage present → target_type = wine
   - "나파 까쇼" + region + grape, no entity name → target_type = region_grape_browse
3. Entity family resolver:
   - producer → 소속 wine set 반환
   - appellation → 소속 wine set 반환
   - 이 set에 대해 diversity + popularity ranking 적용
```

### 8.2 LLM Retrieval Envelope (→ RFC-008/014 확장)

**문제:**

사람은 검색 결과를 보고 재시도할 수 있다.
LLM은 한번 retrieve한 결과를 사실처럼 이어붙여 reasoning에 쓴다.

따라서 LLM용 retrieval 응답은 **단순 top-k doc list가 아니라 structured evidence packet**이어야 한다.

현재 RFC-008/014는 SearchResponseV1에 `evidence_items`과 `decision_status`가 있지만,
아래가 빠져있다:

```typescript
// LLM-safe retrieval envelope (RFC-008/014 확장 후보)
type LLMRetrievalEnvelope = {
  // 현재 있는 것
  decision_status: 'resolved' | 'ambiguous' | 'failed';
  evidence_items: EvidenceItem[];

  // 빠져있는 것 — LLM이 안전하게 쓰려면 필요
  result_type: 'single_entity' | 'entity_set' | 'comparison' | 'no_match';
  query_target_type: 'wine' | 'producer' | 'region' | 'style' | 'unknown';
  parsed_constraints: {
    hard: ConstraintBundle;
    violated: string[];       // 결과가 만족 못한 constraint
    missing_info: string[];   // 파싱 못한 constraint
  };
  candidate_evidence: Array<{
    entity_id: string;
    match_reasons: string[];   // ["producer exact", "vintage match", "style inferred"]
    violated_constraints: string[];
    confidence: number;
  }>;
  ambiguity_set?: Array<{
    entity_id: string;
    disambiguation_hint: string;  // "Léoville-Barton (Saint-Julien)"
  }>;
  abstain_reason?: string;  // "multiple equally likely entities", "no matching entity"
};
```

**RFC-017과의 연결:**
- Epic 3 eval에서 `candidate_evidence.match_reasons` 정확도를 측정해야 함 (evidence faithfulness, RFC-009 §8.1)
- Epic 5 reranker의 `buildWineText()`가 `match_reasons`의 원천 데이터
- LTR feature importance 결과가 `match_reasons` 생성 로직에 직접 입력됨

**이거 없으면:** LLM이 retrieval 결과를 맹신해서 hallucination 위험 증가.
특히 ambiguity 상황에서 LLM이 arbitrary하게 top-1을 선택하는 문제.

### 8.3 Multi-step Search & Retrieval Mode Surface (→ RFC-005/012 확장)

**문제:**

실사용 쿼리의 상당수는 단발 검색이 아니라 다단계 탐색이다:

```
Step 1: "Opus One 찾아줘" → resolve_entity
Step 2: "그거랑 비슷한 거" → search_similar (anchor = Step 1 result)
Step 3: "$150 이하로" → refine_constraint (carry forward Step 2 candidates)
```

LLM agent가 이걸 처리하려면 retrieval API에 최소한 이런 mode가 필요:

```
resolve_entity       — single entity lookup (Track A)
search_by_attributes — constraint/preference search (Track B)
search_similar       — anchor entity + attribute projection + diversity
browse_catalog       — producer/region/classification set retrieval
compare_set          — 복수 entity의 attribute comparison table
```

**RFC-017과의 연결:**
- Epic 2 golden query set의 시나리오 E(탐색), F(유사품), G(카탈로그)가 이 mode들을 전제
- Epic 4 LTR에서 `search_similar` mode는 scoring weight가 완전히 달라짐 (anchor similarity ↑, entity integrity ↓)
- 현재 `scoring-weights.ts`의 `anchored_similarity` query_class가 이 방향이지만, retrieval 단계에서 mode 분리가 없으면 signal 자체가 달라짐

**필요한 것 (별도 RFC):**
- RFC-005 planner에 retrieval_mode 출력 추가
- RFC-012 candidate-pool에 mode별 retrieval strategy 분기
- RFC-013 ranking signals에 mode별 weight preset 추가
