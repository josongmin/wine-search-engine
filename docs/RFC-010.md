RFC-010
Learning Loop / Data Flywheel (Feedback, Alias Overlay, Controlled Online Adaptation)

**상위·정합 문서**

- `RFC-000: Wine Intelligence Engine Master Architecture.md` — **§14 Query distribution & data flywheel** (운영 입력·파이프라인 요약). 이 RFC는 §14를 **구현·거버넌스 관점**에서 확장한다. **충돌 시 RFC-000 우선.**
- `RFC-003` — alias type·scope; **observed_query_alias**만 온라인 확장 허용 (§6)
- `RFC-009` — **Decision Utility**·wrong-top1 — 학습의 상한선 (§2.3, §13)
- `RFC-008` — 로그에 `decision_trace_ref`·engine_decision이 있어야 환류 품질이 나온다
- `RFC-015` — **Kill switch**, drift·Replay와 연동
- `RFC-016` — **Admission Gate**; overlay·온라인 적응은 **core SSOT overwrite 금지**(§6)와 함께, `resolved`는 identity·snapshot·evidence invariant를 깨지 않아야 한다

0. 목적

이 시스템은 한 번 설계해두고 끝나는 검색기가 아니다.

새로운 오타가 계속 생기고
새로운 음역이 생기고
시즌별 수요가 바뀌고
ambiguity가 실제 운영에서만 드러나고
잘못된 확정 사례가 로그에 쌓인다

즉 이 RFC의 한 줄은 이거다.

운영 로그를 alias, ambiguity policy, ranking overlay, eval set으로 환류시키는 데이터 플라이휠을 정의한다.

중요한 전제는 하나다.

학습은 허용하되, Entity SSOT core와 Decision core를 직접 오염시키면 안 된다.

즉 이 RFC는 “온라인 적응”을 다루지만, guardrail이 있는 적응만 허용한다.

1. 비목표

| 직접 하지 않음 | 담당 |
|----------------|------|
| Entity Identity Graph **규칙 SSOT** 정의 | RFC-001 |
| 최종 decision authority·§8.4 수식 변경 | RFC-000 / 거버넌스 |
| raw 클릭만으로 identity 재정의 | 금지 (§2.1) |
| 무제한 self-learning | 금지 — **shadow·승인** (§14) |

즉 이 RFC는 **feedback ingestion + controlled adaptation + offline-to-online feedback loop**다.

2. 핵심 원칙
2.1 Behavior is evidence, not truth

클릭/구매/재검색은 유용하다.
하지만 정답 그 자체는 아니다.

왜냐하면:

position bias
stock/availability bias
seasonal demand bias
retailer exposure bias
UI placement bias

가 강하게 섞이기 때문이다.

따라서:

behavioral signal은 truth가 아니라 probabilistic evidence로만 사용한다

2.2 Core vs Overlay 분리

이 RFC의 가장 중요한 규칙이다.

Entity SSOT / Canonical Alias / Decision Boundary Core
= slow, guarded, mostly offline

Behavioral Overlay / Clarification Ordering / Suggestion Reorder
= dynamic, online-adaptive

즉 온라인 학습은 허용하지만,
resolver core identity prior를 바로 흔들면 안 된다.

2.3 Wrong-top1 방지 우선

운영 학습이 좋아 보여도 wrong-top1이 늘면 실패다.

즉 optimization objective는 CTR maximization이 아니다.

Decision Utility Score를 해치지 않는 범위에서만 적응한다

이건 RFC-000 **§10.7**·RFC-009와 직접 연결된다.

2.4 모든 학습은 provenance를 가져야 한다

어떤 alias prior가 왜 올라갔는지,
어떤 ambiguity 패턴이 왜 policy로 승격됐는지,

전부 lineage가 있어야 한다.

3.1.1 Privacy / data minimization (운영 필수)

이 RFC는 학습을 위해 로그를 쓰지만, **원문 전체를 영구 저장하는 것**을 기본값으로 두지 않는다.

- `user_id`는 가능하면 pseudonymous / hashed identifier로 취급한다.
- raw `query`에 개인정보·주문번호·연락처 등 비검색성 토큰이 섞일 수 있으므로, 학습 파이프라인 전 단계에서 **redaction / filtering**을 둔다.
- replay·감사를 위해 필요한 최소 필드만 보존하고, retention / TTL / 삭제 정책은 제품·법무 정책과 연결한다.

3.1.2 Data Governance & Retention Policy

학습 파이프라인이 수집하는 로그는 **개인 행동 프로파일**에 해당할 수 있다. 법규(개인정보보호법, GDPR 등) 준수와 데이터 위생을 위한 운영 규칙.

**Retention 정책:**

| 데이터 유형 | 기본 보존 기간 | 비고 |
|-------------|---------------|------|
| Raw query + session log | **90일** | PII redaction 후 저장; 90일 후 anonymized aggregate만 보존 |
| FeedbackEvent (§3.1) | **180일** | entity_id·action_type·query_class는 보존, raw query는 hash로 대체 |
| ReformulationTrace (§3.2) | **90일** | session 연결 해제 후 패턴만 보존 |
| AliasExpansionCandidate (§5.1) | **무기한** (승인된 것만) | proposed 상태는 180일 후 자동 만료 |
| EvalCaseCandidate (§5.3) | **무기한** (gold 편입 시) | 편입 안 된 후보는 180일 후 자동 만료 |

**Right to Erasure:**

- 사용자 삭제 요청 시 해당 `user_id`(또는 pseudonymous id) 관련 **FeedbackEvent·ReformulationTrace**를 **30일 이내** 삭제
- 이미 aggregate된 통계·학습 산출물(alias proposal 등)에서 개별 사용자를 역추적할 수 없어야 함
- 삭제 후 해당 사용자 기반으로 생성된 alias·overlay 제안이 있으면 재검증

**접근 통제:**

- raw query log 접근은 **데이터 엔지니어 + 팀 리드** 이상으로 제한
- PII 포함 가능 필드 (`query`, `user_id`)는 저장 시 **별도 encrypted store**에 분리
- 학습 파이프라인은 **redacted/anonymized** 데이터만 소비

**감사:**

- 분기 1회 retention 정책 준수 감사
- 데이터 접근 로그 보존 (누가 언제 어떤 데이터에 접근했는지)

3.2 Reformulation Link

중요한 로그는 단일 이벤트가 아니라 연속성이다.

예:

마고
샤또마고
샤또마고 2015

이건 같은 intent일 가능성이 높다.

  trace_id: string

이건 ambiguity 학습과 alias 후보 생성에 매우 중요하다.

전체 흐름은 이렇게 된다.

출력은 명시적 학습 산출물이어야 한다.

  target_layer:
    | "clarification_ordering"
    | "post_ranking"
    | "suggestion_reorder"

  feature_context: object
  proposed_weight_delta: float

  approval_status: "shadow" | "validated" | "deployed"
}

이게 bandit이나 contextual adaptation이 실제 적용되는 위치다.

5.5 Retrieval Model Feedback (P1–P2)

alias·ambiguity 학습 외에, **dense/sparse retrieval 모델 자체**의 품질도 운영 로그에서 개선할 수 있다.

**Hard Negative Mining (P1):**

- wrong-resolve 케이스에서 **top-K에 올라왔지만 정답이 아닌 entity**를 hard negative로 수집
- clarification에서 사용자가 **선택하지 않은 후보**도 soft negative로 활용
- `{ query, positive_entity_id, hard_negative_entity_ids[], source: "wrong_resolve_log" | "clarification_reject" }`
- 수집된 triplet은 **offline** fine-tuning 입력으로만 사용 — online model update 금지

**Contrastive Fine-tuning (P2):**

- dense retriever (BGE-M3 등)를 수집된 hard negative로 **offline contrastive fine-tuning**
- fine-tuning 전/후 반드시 RFC-009 release gate 통과 (Recall@K, Decision Utility, wrong-resolve, calibration)
- fine-tuned model은 RFC-015 shadow → canary → full rollout

**Sparse 피드백:**

- BM25 자체는 학습 불가이지만, **query expansion 사전**을 로그 기반으로 보강 가능
- SPLADE 사용 시 동일 hard negative 기반 fine-tuning 가능

**가드레일:**

- retrieval model fine-tuning이 **entity integrity score**·**constraint satisfaction**을 악화시키면 금지 — recall만 올라가고 precision이 떨어지는 것은 이 시스템에서 허용 불가
- fine-tuning 빈도: 최대 **월 1회** (데이터 충분성 + 안정성)
- 모든 fine-tuning job은 **`model_version`에 반영** → `DecisionSnapshot`(RFC-015)

6. Alias Learning Policy
6.1 허용되는 학습 대상

온라인/반온라인 학습이 가능한 alias는 제한한다.

허용
observed_query_alias
일부 catalog_noise_alias의 검색 recall 보조 가중치
금지
canonical
translation
phonetic core mapping
misspelling core generation rule 자체의 온라인 overwrite

즉 core alias taxonomy는 오프라인/가드레일 기반으로 관리한다.

6.2 Promotion Rule

로그에서 관측된 alias가 바로 SSOT에 들어가면 안 된다.

Observed alias
→ proposed
→ validated
→ active

최소 필요 조건 예시:

support count 충분
target entity consistency 높음
wrong-target evidence 낮음
high-risk ambiguity 없음

6.2.1 Promotion gate (RFC-009 §13 정합)

**validated → deployed**(또는 alias **active**)로 올리기 전, 아래는 **릴리즈 게이트와 동일한 축**으로 non-regression을 증명해야 한다 (수치는 RFC-009·팀 baseline에 맞춤).

| 축 | 요구 |
|----|------|
| wrong-resolve | 악화 없음 |
| Decision Utility | 악화 없음 |
| ECE (calibration) | 악화 없음 |
| ambiguity-heavy query slice | 회귀 없음 |
| decision trace 완전성 | 유지 |

overlay·alias prior·threshold 제안·랭킹 오버레이 모두 **예외 없이** 이 게이트를 거친다.

**자동 배포 금지 (재확인):** core identity / canonical alias / translation / phonetic **룰 본체**는 온라인 자동 배포하지 않는다 — RFC-006 §6.1·본 RFC §6.1과 동일.

6.2.2 Kill switch & containment (RFC-015)

운영 플래그로 즉시:

- **alias overlay**·온라인 prior bump 비활성화
- **learning 적용** 중단 (shadow 로그만 허용)
- **신규 `threshold_profile_id`** 트래픽 비율 0%

장애·drift 알람 시 RFC-009 §12.7과 함께 발동한다.
6.3 Slow Update Rule

alias prior는 천천히 움직여야 한다.

이유:

짧은 시즌성 편향
UI 실험 편향
일시적 트렌드 왜곡

즉 update는 EMA나 capped delta처럼 완만하게 가는 게 맞다.

7. Contextual Bandit (제한적 허용)

이 RFC에서 제일 조심해야 하는 부분이다.

7.1 적용 목적

bandit은 “무엇이 truth인가”를 배우는 데 쓰지 않는다.
bandit은 여러 안전한 후보 중 무엇을 먼저 보여줄지 에 쓴다.

7.2 허용 적용 위치
허용
clarification candidate ordering
hybrid result post-ranking overlay
suggestion correction ordering
query suggestion ranking
금지
Entity SSOT rewrite
resolver core canonical prior overwrite
decision boundary core threshold auto-mutation

즉 bandit은 presentation/control overlay 에만 먼저 쓴다.

7.3 Context Features

`query_class`는 **RFC-005**와 동일 키를 쓰면 오프라인 eval·정책 튜닝과 연결된다.

BanditContext {
  locale: string
  season?: string
  event_period?: string
  device?: string

  query_class: string
  route: string

  user_segment?: string
}

여기서 seasonal scope가 들어갈 수 있다.

예:

여름 → white/sparkling suggestion reorder
연말/추석 → gift/premium emphasis

하지만 이것도 query-context prior 로 취급하고, identity core를 바꾸지 않는다.

8. Bias-aware Signal Construction

행동로그는 그대로 쓰면 안 된다.

8.1 주요 편향
position bias
exposure bias
stock bias
promotion bias
UI treatment bias
8.2 원칙

가능한 경우 최소한 다음을 분리해 본다.

노출됐는데 안 눌린 것
아예 노출이 안 된 것
1위라서 눌린 것
clarification 이후 선택된 것

즉 click 자체보다 selection under controlled ambiguity 를 더 높은 품질의 signal로 본다.

8.3 고품질 신호 우선순위

대략 이렇게 본다.

clarification 선택
explicit negative 후 수정 선택
reformulation 후 최종 resolve
purchase
click + dwell
raw click

raw click은 가장 약한 신호다.

10. Eval Harness 환류

RFC-000 **§14.2**·RFC-009와 강하게 묶인다.

10.1 자동 편입 대상

다음은 eval 후보로 자동 승격한다.

wrong resolve
repeated clarification failure
repeated reformulation
explicit negative
ambiguity false negative
10.2 회귀 방지

한 번 큰 사고 낸 query는 반드시 gold set에 남긴다.

예:

마고
오푸스원 18
케이머스 나파

이렇게 해서 학습이 아니라 regression firewall 도 같이 만든다.

11. Human-in-the-loop Boundary

모든 학습을 자동 배포하면 안 된다.

11.1 수동 검토가 필요한 것
high-traffic alias promotion
top brand ambiguity policy 변경
resolver threshold 변경 제안
seasonal scope override
catalog_noise_alias의 recall 승격 요청
11.2 이유

이건 검색 시스템이 아니라 decision system이라서,
작은 online uplift가 큰 wrong-top1 사고로 이어질 수 있다.

12. 주요 실패 모드
12.1 Behavior Overwrite

클릭이 identity truth를 덮어씀

12.2 Short-term Trend Overfit

짧은 시즌 데이터를 전체 prior로 일반화

12.3 CTR Optimization Trap

CTR은 오르는데 wrong-top1도 같이 오름

12.4 Eval Disconnect

운영에서 터진 문제를 eval set이 못 잡음

12.5 Alias Explosion via Logs

로그 기반 alias 후보가 무한정 늘어남
