RFC-003
Alias System (Typed + Scoped + Guardrailed Dynamics)

**상위·연관 문서**

- `RFC-000: Wine Intelligence Engine Master Architecture.md` — Alias SSOT, **Decision Layer**가 최종 권한(§8.4), `confidence_prior` ≠ 런타임 **calibrated C**, evidence packet(§9)
- `RFC-001: Entity Identity Graph SSOT` — alias는 identity 정의 금지; projection은 복제
- `RFC-002` — ingestion 산출 `alias_candidates`는 **후보**이며, 이 RFC에서 **type·scope·lineage** 부여 후 인덱스에 반영

0. 목적

사용자는 절대 canonical label로 검색하지 않는다.

오푸스원
옵스원
opusone
opus one napa
오푸스원 18
오푸스원 와인

이걸 전부 같은 entity로 수렴시키는 게 이 레이어다.

하지만 핵심은 이거다:

Alias는 매칭을 돕는 signal이지, identity를 정의하면 안 된다

여기서 선 넘으면 바로 망한다.

1. 설계 원칙
1.1 Alias ≠ Identity

절대 금지:

alias = canonical label

alias는:

noisy
ambiguous
context-dependent

즉:

alias는 항상 불완전한 힌트다

1.2 Typed Alias (필수)

alias를 string list로 두는 순간 끝이다.

Alias {
  alias_id: string              // 불변 ID (갱신 시에도 추적용)
  entity_id: EntityId
  value: string
  type: AliasType
  confidence_prior: float        // 사전 가중치 — **런타임 calibrated confidence C와 동일 스케일 아님**
  source: string               // 예: ingestion:RFC-002, rule:transliteration_v2, log:observed_2025Q1
  scope: Scope

  effective_from?: timestamp   // temporal scope와 별도로 “유효 시작”이 필요할 때
  suppressed?: bool            // 잘못 학습된 observed 등 비활성화
  lineage_ref?: string         // RFC-002 LineageRecord 또는 배치 job id
}

1.3 Scope (이거 없으면 터짐)

같은 alias라도 의미가 달라진다.

예:

“마고” → 프랑스/와인 맥락에서는 Château Margaux
“마고” → 그냥 텍스트에서는 meaningless

따라서:

Scope =
  global
  locale_ko
  locale_en
  marketplace_specific
  retailer_specific
  temporal
1.4 Prior는 고정값이 아니다 (근데 core에 넣지 마라)

prior는 중요하지만:

behavioral signal이 identity core를 오염시키면 안 된다

→ bandit은 overlay로만 쓴다 (§6)

**한 줄:** `confidence_prior`는 **resolver 입력 신호**일 뿐, RFC-000 **Decision boundary function**을 대체하지 않는다.

예:

2.5 observed_query_alias (핵심)

로그에서 나온 실제 사용자 표현

예:

“오푸스원 와인”
“오푸스원 가격”
“옵us one”

특징:

실제 유저 행동 기반
강력하지만 위험함 (bias 있음)
2.6 catalog_noise_alias

마켓플레이스 오염

예:

“Opus One Napa Red 750ml Gift Box”
“프리미엄 선물세트 오푸스원”

특징:

절대 canonical로 승격 금지
매칭에는 쓰되 prior 낮게

**필드 기여 상한 (RFC-012·013과 연결):** `catalog_noise_alias`는 **sparse recall**·noisy 전용 필드에만 실어 보낸다. **`canonical_label` 동치·exact-safe path의 primary evidence**가 되거나 identity 결정을 단독으로 끌어올 수 없다.

2.7 Typed alias(SSOT) vs 검색용 flatten

- **Typed alias**(type·scope·prior·lineage)만 **SSOT**다 (RFC-000 §3.2).
- **Flatten alias**는 `RetrievalDocument` projection의 **검색용 복사본**일 뿐이다 (RFC-000 §3.2.1, RFC-012).
- flatten은 **ranking·recall** 보조 — **identity 결정권 없음**.
- flatten에서 type·scope·prior를 복구할 수 없으면 **decision signal로 직접 승격할 수 없다** (RFC-007·RFC-006).

3. Alias Prior System
3.1 기본 구조
confidence_prior ∈ [0, 1]

초기값 예시 (팀이 튜닝):

| type | prior (예시) |
|------|----------------|
| canonical | 1.0 |
| translation | 0.95 |
| phonetic | 0.85 |
| misspelling | 0.6 |
| observed_query_alias | 0.7 |
| catalog_noise_alias | 0.4 |

3.2 Prior는 어디에 쓰이나

resolver **scoring 입력**에 들어간다.

```
entity_match_signal ≈ f(alias_match_score × weight(type, prior), …)
```

- 이 신호는 **EvidenceItem**(RFC-000 §9)의 `contribution` / `strength`로도 흘러간다.
- **최종 `decision_status`**(`resolved` / `ambiguous` / `failed`)와 **`next_action`**은 **Decision Layer**(RFC-000 §8.4)가 `C`, `Δ`, `A`, 정책으로 결정 — alias prior 단독 **확정 권한 없음**.

3.3 절대 규칙

alias prior는 resolution을 “도울 수는 있지만 강제할 수는 없다”

→ Decision Layer가 항상 override 가능해야 한다

4.4 충돌·중복

동일 `value`·유사 표기가 **서로 다른 entity**에 붙으면 **침묵 병합 금지** — ambiguity로 올리거나 수동 큐(RFC-002 §10과 연동).  
**Idempotency:** 동일 `(value, scope, type, entity_id)` 재삽입은 멱등 처리.

4.4.1 Alias Conflict Resolution Protocol

동일 `value`가 서로 다른 entity에 매핑될 때 (예: "마고" → Château Margaux wine vs Margaux region):

**자동 해결 가능 조건 (모두 충족 시):**

1. 한쪽의 `alias_type` priority가 명확히 높음 (canonical > translation > phonetic > observed > catalog_noise)
2. 높은 쪽의 `confidence_prior` ≥ 0.9이고 낮은 쪽 ≤ 0.5
3. `scope`가 다름 (예: locale_ko vs global)

**자동 해결 불가 → 구조적 ambiguity 등록:**

1. 해당 `value`를 **ambiguity registry**에 등록 (surface_form, conflicting_entity_ids, conflict_type)
2. RFC-005 planner의 `known short-form ambiguity 사전`에 자동 반영
3. RFC-007 Decision Layer에서 해당 surface form은 **resolve 시 추가 ambiguity penalty** 적용
4. **human queue:** conflict 양쪽 모두 high-traffic entity면 수동 검토 필수

**점수 함수 (자동 해결 시):**

```
conflict_resolution_score(alias, entity) =
  type_priority_weight(alias.type)
  × alias.confidence_prior
  × source_trust(alias.source)
  × (1 - scope_mismatch_penalty)
```

winner = argmax over conflicting entities
margin < 0.2이면 자동 해결 금지 → ambiguity registry

4.5 Cross-lingual Transliteration Pipeline

와인 도메인의 핵심 난제는 **프랑스어·이탈리아어·스페인어 원어 → 한국어 음역**이다. 일관된 transliteration 없으면 alias 폭발과 collision이 동시에 발생한다.

**파이프라인:**

1. **Rule-based transliteration:** 언어쌍별 음역 규칙 테이블 (SSOT, 버전 관리)
   - `fr → ko`: Château → 샤또/샤토, Margaux → 마고, Haut → 오
   - `it → ko`: Barolo → 바롤로, Brunello → 브루넬로, Chianti → 키안티
   - `es → ko`: Rioja → 리오하, Tempranillo → 템프라니요
   - `en → ko`: Cabernet → 카베르네, Sauvignon → 소비뇽

2. **예외 사전:** 규칙으로 안 되는 관용 음역 (예: Opus One → 오푸스원 (오퍼스원 아님), Moët → 모엣 (모에트 아님))

3. **자동 생성 + 검증:** rule 적용 → 후보 생성 → 기존 alias와 collision 검사 → `proposed` 상태로 진입 (§6.2 promotion rule 적용)

**품질 목표:**

- 자동 생성 transliteration precision ≥ 0.95 (주요 100대 와인 기준)
- 규칙 테이블 커버리지 ≥ 0.90 (카탈로그 내 비영어 entity 기준)

**업데이트:** 규칙 테이블은 `transliteration_rule_version`으로 관리. 변경 시 기존 alias 재생성·diff 검토.

7. Temporal Scope

계절/이벤트 영향

예:

추석 → 선물용 alias 상승
여름 → 화이트/샴페인

중요:

→ **Planner / Policy / hybrid re-ranking**에서 처리 — `temporal` scope는 메타데이터로 남겨도, **코어 alias 테이블을 시즌마다 흔들지 말 것**.

8. Alias Contamination 방지

이 RFC에서 제일 중요

8.1 contamination 유형
catalog noise가 canonical로 승격
observed alias가 identity override
alias 간 충돌
8.2 방지 규칙
catalog_noise_alias는 canonical 승격 금지
observed alias는 slow update
high ambiguity alias는 resolution 금지

8.2.1 Promotion firewall (RFC-010과 동일 축)

**자동·반자동 승격 금지:**

- `alias.type ∈ { catalog_noise_alias, retailer_listing, marketplace_title }` (팀이 정의한 retailer 계열) → **`canonical_label` 동치·identity 동치로 승격 불가** — projection **recall 전용**만 (RFC-002·RFC-012).
- 인기 클릭만으로 **canonical prior**를 덮어쓰지 않는다 — RFC-010 §6.1.

8.2.2 Adversarial Alias Injection Defense

의도적 alias 오염 공격을 방어한다.

**위협:**

- **Redirect 공격:** 경쟁 와인의 canonical name을 자사 entity의 observed_query_alias로 삽입 시도
- **Pollution 공격:** 대량 저품질 alias를 주입해 resolver noise 증가
- **Homoglyph 공격:** 유니코드 유사 문자로 canonical alias를 흉내 (예: Оpus One with Cyrillic О)

**방어 계층:**

1. **Cross-entity uniqueness check:** canonical·translation alias는 **entity 간 유일성**을 강제. 충돌 시 §4.4.1 protocol.
2. **Homoglyph normalization:** alias 저장 전 unicode confusable 정규화 (Unicode TR39). 정규화 후 기존 alias와 충돌하면 reject.
3. **Velocity limit:** 단일 source에서 단일 entity에 24시간 내 alias 추가 > 10건이면 throttle + human review.
4. **Source trust gate:** `SourceTrustProfile.marketplace_noise_risk` > 0.7인 소스에서 온 alias는 `catalog_noise_alias`만 허용, 다른 type으로 승격 금지.
5. **Anomaly detection:** 기존 alias 분포 대비 갑자기 새 패턴이 급증하면 알람 (RFC-010 drift detection과 연동).

8.3 잘못된 alias 비활성화

학습·로그로 잘못 붙은 alias는 **삭제보다 `suppressed=true` + lineage**로 남겨 재발·감사 가능하게 (RFC-002 §9 정합).
