0. 한 줄 정의 (SSOT)

Wine Intelligence Engine = Entity-governed, Decision-boundary, Evidence-bearing Retrieval System

It is not a generic retrieval stack.
It is a search system that decides when to resolve, when to abstain, and when to surface ambiguity.

Retrieval이 아니라
“Entity-first + 결정 경계 통제 + Evidence-bearing” 의사결정형 검색 시스템이다.
차별점은 retrieval 품질만이 아니라, **언제 확정하면 안 되는지까지 시스템이 통제**한다는 점이다.
(aware ≈ 알고 있다 / governed ≈ 확정·보류·실패를 통제한다)

1. 시스템 목표 (Non-negotiable Requirements)
1.1 핵심 기능 (2-track)
Track A — Exact Entity Resolution
Messy user queries must converge to the correct wine entity through alias, typo, transliteration, and behavioral normalization.
The engine must never force resolution under unresolved ambiguity.

개떡같은 쿼리도 정확한 와인 entity로 수렴
오타 / 음역 / 축약 / 행동·카탈로그 정규화 대응
ambiguity 시 절대 틀린 확정 금지

Track B — Hybrid Intelligence Search
The engine must support lexical, semantic, structured, and LLM-consumable search for discovery, recommendation, comparison, and constrained retrieval.

lexical + semantic + structured + AI 친화
사람 + LLM 둘 다 사용 가능
추천 / 비교 / 조건 검색 대응

1.2 실패 정책 (핵심)
Wrong resolution is worse than ambiguity.
Ambiguity must be surfaced, not hidden.
Every decision must leave a machine-readable trace.
LLM explanation is optional; evidence is mandatory.

틀린 결과 반환 금지
ambiguity는 반드시 surface
decision trace 항상 남김

2. 전체 아키텍처 (SOTA++ SSOT)
[Client / LLM]

→ Query API

→ Query Planner (fast + deep 분리)
   - intent
   - anchor detection
   - constraint extraction
   - route proposal

→ Policy Compiler
   - require_exact
   - allow_approximate
   - require_clarification
   - fallback_policy

Planner는 “무엇을 찾을지”를 정리하고,
Policy는 “어디까지 허용할지”를 정한다.
(예: 오푸스원 → entity 확정 가능 / 마고 → ambiguity surface 필수 / “오푸스원 같은 10만원” → approximate 허용 / 샤또마고 2018 wrong-top1 리스크 높으면 clarification 우선)
route 품질과 policy 품질을 **별도로** 평가·튜닝할 수 있게 분리한다.

→ Candidate Generation
   - Track A: Entity Resolver
   - Track B: Hybrid Retrieval

→ Signal Computation
   - entity integrity
   - constraint satisfaction (hard / soft)
   - semantic relevance
   - preference alignment
   - popularity / availability
   - uncertainty

→ Decision Layer
   - resolved / ambiguous / failed
   - **마지막 서브단계: Admission Gate (RFC-016)** — `resolved` 허용 여부·identity sealing·snapshot·evidence sufficiency·`failure_reason` SSOT

→ Response Builder
   - structured SSOT response
   - optional natural-language explanation

→ Output

처리 순서 (중요):

candidate generation → ranking **signals** 계산 → **decision policy evaluation** → **Admission Gate (RFC-016)** → 최종 resolve / ambiguous / fail

**Admission Gate (system closure)** — Decision Layer **내부**의 마지막 단계 (RFC-016).

역할:

- `resolved` 허용 여부의 **단일 확정 지점**
- identity sealing 검사
- snapshot consistency 검사
- evidence sufficiency 검사
- `failure_reason` SSOT 부여

즉: resolver / ranking / retrieval은 **신호**를 만들고, Decision은 정책·수치 게이트를 적용하며, **Admission Gate가 최종적으로 `resolved` 가능 여부를 닫는다.** `resolved`는 RFC-016 Admission Gate를 통과한 경우에만 가능하다.

Ranking produces evidence-bearing signals.
Decision Layer consumes those signals and determines:
- resolved
- ambiguous
- failed

Ranking never has the authority to force resolution.

Entity SSOT is graph-shaped at the logical layer.
Physical storage is implementation-free (relational + adjacency, document + denormalized edges, graph store, 등).
The retrieval index is a **projection** of the identity graph, not the identity source itself.

논리 모델은 graph이고, graph DB 강제가 아니다.
Vespa index는 identity의 **투영(projection)**이지 SSOT 원천이 아니다.

- clarification **후보 순서** (ordering)

- `observed_query_alias` / `catalog_noise_alias` → online contextual update은 **허용 가능하되**, 업데이트 타깃은 **reordering layer·overlay** 우선

- 추석/연말: gift, premium, boxed set  
- 여름: white, sparkling, chilled

**한 줄:** bandit은 **찬성** — 단, **behavioral overlay**로 쓰고, entity SSOT core를 행동신호로 흔들지 말 것.

8. Decision Layer (핵심 차별점)
8.1 역할
**최종** `decision_status`와 `next_action`을 확정한다. **"fallback"은 상태가 아니라 라우팅 의미**이며, 스키마에서는 `next_action`으로만 표현한다.
잘못된 확정 방지
8.2 출력 상태 (SSOT — 이름 고정)

- **`decision_status`** ∈ { `resolved`, `ambiguous`, `failed` } — 셋만. *(문서·코드에서 "fallback"을 status로 쓰지 말 것.)*
- **`next_action`** ∈ { `return_result`, `clarify`, `hybrid_search`, `fail` } — 사용자/시스템이 취할 다음 행동.

`QueryPolicy.fallback_mode`·`fallback_policy` 문자열은 최종적으로 **`next_action`** (주로 `hybrid_search`·`clarify`·`fail`)에 매핑된다.

8.3 정책 (직관)
if high_confidence:
  resolve → decision_status=resolved, next_action=return_result

elif ambiguity_detected:
  decision_status=ambiguous, next_action=clarify (또는 return_result+후보만)

else:
  hybrid로 넘김 → **상태는** failed 또는 ambiguous가 될 수 있고, **행동은** next_action=hybrid_search

(§8.3은 직관 설명; **형식화는 §8.4·`decision_status`/`next_action`.**)

8.4 Decision boundary function (formal)

본질은 “잘 찾는 검색기”가 아니라 **확정하면 안 되는 순간을 통제하는 시스템**이다.  
raw score gap만으로는 부족하다 — 모델·프로파일이 바뀌면 스케일이 흔들리고, 같은 `Δ`라도 쿼리 타입에 따라 의미가 달라진다.

**개념적으로** resolve는 다음 형태의 함수로 두는 것이 맞다 (구현은 모듈화):

`resolve = f(S1, S2, Δ, query_class, alias_type, vintage_presence, ambiguity_flags, C_calibrated, …)`

Let:

- `S1` = top-1 **calibrated** decision score (fusion 이후; **raw retrieval/rerank 단일값 그대로 금지**)
- `S2` = top-2 동일
- `Δ` = `S1 - S2`
- `A` = ambiguity classifier 출력 (또는 구조적 ambiguity 집계를 bool로 요약)
- `Q` = query class (`QueryPlanV1.query_class`)
- `C` = **calibrated** confidence ∈ [0, 1] (§10.5·§10.7과 직결)

**규칙 (권장 기본형; 임계값은 `Q`에 따라 달라질 수 있음):**

```
if C >= T_resolve(Q) and Δ >= T_gap(Q) and not A:
    decision_status = resolved
    next_action = return_result

elif conformal_set_size >= 2 or A or Δ < T_gap(Q):
    decision_status = ambiguous   // 후보·clarify
    next_action = clarify 또는 return_result (정책)

else:
    decision_status = failed | ambiguous   // 정책에 따라
    next_action = hybrid_search | fail       // fallback_policy → 여기로만
```

P0/P1에서는 `conformal_set_size`를 **아직 쓰지 않으면** 해당 조건을 끄거나 `conformal_set_size = 1`로 간주해 **§8.4만으로** 가동한다 (§8.5는 P2).

- `T_resolve(Q)`, `T_gap(Q)`는 **쿼리 클래스별** 튜닝 가능 (고정 전역 상수일 필요 없음).
- `Δ < T_gap(Q)`이면 강제로 clarification 쪽으로 보내는 **ambiguity gate** — Vespa에서 phase별 signal을 계산한 뒤 Decision Layer가 최종 상태를 고정하는 패턴과 정합.

**필수 제약**

- `C`는 **calibration된 값**만 사용한다 (§10.5). raw score에 threshold를 걸지 않는다.
- `A`는 planner·resolver·alias collision 등에서 오는 **구조적** 모호성과 classifier 출력을 합친 개념으로 둘 수 있다.

**Conformal prediction (§8.5)** 은 distribution-free coverage 관점에서 유용하지만, retrieval/entity resolution에서는 **exchangeability·candidate quality** 현실과 어긋나 set 효율이 흔들릴 수 있다. 그래서 **P0 핵심 결정권의 단독 기준으로 두지 않고**, §8.5처럼 **보조 ambiguity gate**로 먼저 넣는다.

8.5 Conformal prediction (auxiliary ambiguity gate; P2 권장)

**역할:** 1차는 `C` + `Δ` + `A` (§8.4). **2차 안전장치**로 conformal-style prediction set을 쓸 경우, 정책 예시:

- `conformal_set_size >= 2` → **AMBIGUOUS** (멀티 후보를 “불확실성 있는 집합”으로 노출)

coverage 보장(예: 95% 정답 포함)은 강하지만 set이 자주 커지면 UX가 망가지므로, **핵심 로직 전부를 conformal 하나에 걸지 말 것.** P2에서 도입·A/B가 안전하다.

8.6 Conformal Implementation Guide (P2 준비용)

**Exchangeability 검증:** conformal guarantee는 calibration set과 test 분포가 교환 가능(exchangeable)하다는 전제에 의존한다. 와인 검색에서는 계절·트렌드·카탈로그 변동으로 분포가 계속 바뀌므로:

- **검증:** calibration set과 production query의 `query_class` 분포·entity 분포를 주기적으로 비교 (KL divergence 또는 PSI)
- **adaptive conformal:** distribution shift 대응 — Gibbs & Candès (2021) ACI(Adaptive Conformal Inference) 패턴으로 coverage를 시간에 따라 보정
- **calibration set 갱신:** conformal calibration set은 최소 2주 단위 sliding window 또는 모델·인덱스 변경 시 즉시 재구성

**Calibration set vs Conformal set 관계:**

- **calibration set** (§10.5): Platt/isotonic 등으로 `C`를 만드는 데이터
- **conformal calibration set**: nonconformity score 분위수를 산출하는 별도 홀드아웃 — 위 calibration set과 **겹치면 coverage 보장이 깨진다**
- 즉 데이터 분할은 최소 **train / calibration(C) / conformal / eval** 4-way

**Set efficiency 관리:**

- `conformal_set_size` 평균이 2.5 이상이면 UX 저하 → `α` 조정 또는 nonconformity function 개선
- query_class별 set size 분포를 모니터링 — 특정 클래스에서만 set이 비대해지면 해당 클래스 calibration 분리

8.7 Closed-world invariant

본 시스템에서 **`decision_status = resolved`**는 다음을 **모두** 만족할 때만 허용된다.

- calibrated decision gate 통과 (§8.4)
- policy / ambiguity gate 통과
- RFC-016 identity sealing 통과
- RFC-016 snapshot consistency 통과
- RFC-016 evidence sufficiency 통과

그 외에는 **`ambiguous` 또는 `failed`로 downgrade**한다 (RFC-007·RFC-016).

9.3 Evidence-bearing retrieval & Vespa explainability

Vespa는 ranking expressions, **rank features**, phased ranking, **document summaries**, **summary-features** 등으로 “어떤 신호가 계산됐는지”를 결과에 실어 보내기 좋다. named function·`summary-features` 조합으로 **구조화된 evidence packet**을 만들고, LLM/tool 호출 시 그대로 넘기는 것이 권장된다.

**Attribution 주의:** 선형식이면 기여 분해가 쉬워지지만, **RRF + cross-encoder + thresholded constraint + 비선형 상호작용**이 섞이면 “정확한 % 기여”는 쉽게 **오해의 소지**가 있다. 그래서 §9.1에서는 **% 단정이 아니라** `contribution` + `strength` **band** 또는 **signed contribution**을 쓴다.

예시 (형식만; 스케마는 버전과 함께 고정):

```json
{
  "evidence": [
    {"type":"alias_match","source":"observed_query_alias","contribution":"+0.42","strength":"high"},
    {"type":"vintage_match","source":"query_parse","contribution":"+0.19","strength":"medium"},
    {"type":"semantic_similarity","source":"embedding_v3","contribution":"+0.11","strength":"medium"},
    {"type":"price_constraint_miss","source":"constraint_engine","contribution":"-0.36","strength":"high"}
  ]
}
```

9.4 Counterfactual explanations (P2–P3)

반사실적 설명은 UX·LLM 설득력에 좋지만, **P0는 아니고 P2–P3.** 구현 난이도가 높고 잘못하면 explanation hallucination처럼 보일 수 있다.

**권장 시작점:** “constraint dropped re-score” — 현재 랭크 vs **가격(등) 조건만 제거한 재채점** 후 delta 비교.  
예: “가격 조건만 없었으면 1위였음”에 **실제 재점수 근거**가 생긴다. 고급 counterfactual은 그 다음 단계.

retrieval 품질 / rerank 품질 / 최종 decision 품질을 한 숫자로 합치지 않는 것이 좋다.

10.6 Decision thresholds & calibration (연동)

§8.4의 `T_resolve(Q)`, `T_gap(Q)`는 **§10.5·§10.7과 함께** 선택한다.  
`C`가 캘리브레이션되지 않으면 threshold 튜닝이 의미 없다. 오프라인에서는 (1) calibration 곡선·ECE (2) `Δ` 분포 (3) ambiguity·query-class 조건부 정확도 (4) §10.7 utility를 **동시에** 본다.

10.7 Decision Utility Score (wrong-top1-heavy; eval harness 핵심)

일반 IR은 nDCG·MRR·Recall@K로도 충분한 경우가 많다. 이 시스템은 **“근처 정답”이 아니라 틀린 확정 금지**가 목적함수에 가깝다 → **selective prediction / abstention-aware** 평가가 필요하다 (conformal의 “coverage vs set efficiency”와 같은 긴장).

**쿼리 단위 utility (예시 가중치; 튜닝 가능):**

```
Utility(query) =
  + 1.0   if correct_resolve
  + 0.4   if safe_abstain
  + 0.1   if useful_clarification_set
  - 1.5   if wrong_resolve
  - 0.3   if avoidable_abstain
```

**집계:**

`Decision Utility Score = mean_q Utility(query)`

**반드시 같이 볼 지표**

- Wrong Top1 Rate (또는 wrong-resolve rate)
- Safe abstain rate / Avoidable abstain rate
- Clarification success rate (useful_clarification_set 정의와 함께)
- Coverage at resolve threshold (확정에 동의한 비율 vs 품질)
- Calibration error (ECE 등, §10.5)

이렇게 해야 nDCG만으로는 안 드러나는 **과확신 오답**이 벤치에 잡힌다.

11. 구현 로드맵 (현실형)

**P0 (당장)**

- Calibrated decision function (§8.4: `C`, `Δ`, `Q`, `A`; raw 금지)
- Wrong-top1-heavy **utility metric** + safe/avoidable abstain (§10.7)
- **Evidence packet** 스키마 (§9.1–9.3: contribution + strength, Vespa summary-features 연동)
- Entity SSOT, Alias typing (+ scope), Policy Compiler 분리
- Lexical search, Eval harness (threshold·calibration·utility 연동)
- Data flywheel v0 (§14)

**P1**

- Ambiguity classifier (`A`) 고도화
- Contextual alias **overlay** (§3.4: core 오염 방지)
- Clarification ordering model / hybrid post-ranking overlay
- Dense retrieval, RRF, Cross-Encoder rerank **interface**, Query planner 확장

**P2**

- Conformal set generation (§8.5: **보조** ambiguity gate, |set|≥2 정책)
- Counterfactual explanation — **constraint dropped re-score**부터 (§9.4)
- Mixed query solver 고도화, evidence packet 고도화, AI response

**P3**

- LTR / learned rerank, personalization, multi-vector when needed
- 고급 counterfactual·개인화 실험

12. 기술 스택 (2026 SOTA++ — baseline + upgrade path)

Baseline stack
- Retrieval engine: Vespa
- Sparse retriever: **BM25 first**; SPLADE optional **after eval proves net gain** (비용↑, 전환 시 측정 필수)
- Dense retriever: BGE-M3 class multilingual retriever (다국어·dense/sparse/multi-vector를 한 계열에서 확장 가능)
- ANN: HNSW
- Reranker: **Cross-Encoder interface** (DeBERTa 등 구체 모델에 고정하지 않음; second/global phase에 배치)
- LLM: explanation only, **never authority**

Upgrade path
- Sparse: BM25 → SPLADE (측정된 순증만)
- Dense: single-vector → multi-vector when needed
- Ranking: heuristic fusion → learned rerank / LTR
- Evidence: static reasons → calibrated evidence packet

Vespa는 hybrid retrieval, HNSW 기반 ANN, phased ranking을 지원하며, 비싼 모델 추론은 second/global phase에 두는 패턴이 잘 맞는다.
BGE-M3는 다국어·다기능·다입도 retrieval에 맞춰 dense/sparse/multi-vector를 한 모델 계열에서 다룰 수 있다는 점에서 이 스택과 정합적이다.

12.1 Multi-modal Input Extension Path (P2)

와인 도메인은 **라벨 이미지 기반 검색**이 중요한 use case다 (촬영 → entity resolution).

**P2 권장 경로:**

- **OCR + Entity Resolution:** 라벨 이미지 → OCR → 텍스트 추출 → RFC-006 resolver 입력. 기존 alias·entity 파이프라인을 최대한 재사용.
- **Vision-Language Retrieval:** CLIP / SigLIP 계열로 이미지 → embedding → dense retrieval(RFC-012) 경로에 추가 source로 합류. `HybridCandidate.candidate_sources`에 `"vision"` 추가.
- **Hybrid:** OCR 텍스트 + vision embedding을 **동시에** 사용해 recall 확보 후 기존 Decision 파이프라인으로 합류.

**불변 원칙:** 이미지 입력이 들어와도 **Decision Layer 권한·Evidence 의무·Entity SSOT**는 동일하게 적용. Vision score도 ranking **신호**일 뿐 authority 아님.

**projection 확장:** `RetrievalDocument`(RFC-012)에 `label_image_embedding?: vector` 필드 추가 가능 — identity-strong 필드와 분리.

13. 핵심 설계 원칙 (절대 깨면 안됨)
Entity가 항상 먼저다
틀린 확정보다 ambiguous가 낫다
**Decision이 ranking 위에 있다** — Score는 입력 신호일 뿐, 확정 권한은 Decision Layer에만 있다
Explanation보다 Evidence가 먼저다
Planner(무엇을 찾을지)와 Policy Compiler(어디까지 허용할지)를 분리해 평가한다
Embedding으로 다 해결하려 하지 마라
Alias는 type·scope 없으면 망한다
Hybrid는 필수지만 후순위

13.1 Extensibility invariants (새 모델 / 새 IR 기법을 넣을 때도 안 변하는 것)

새 retriever, 새 reranker, 새 LLM, 새 index 최적화는 **얼마든지 교체 가능**하지만, 아래는 바뀌면 안 된다.

- **Entity SSOT / typed alias SSOT**를 우회하지 않는다.
- retrieval / ranking은 **신호 생산자**로만 들어오고, **최종 authority**는 여전히 Decision Layer다.
- 새 컴포넌트는 최소한 **versioned trace + provenance + replay 가능한 snapshot key**를 남긴다.
- 성능 승격은 “더 최신 모델”이 아니라 **RFC-009 utility / wrong-resolve / calibration / drift gate 통과**로만 한다.

**한 줄:** 이 시스템은 검색엔진이 아니라 **결정(decision) 시스템**이다. 모델만큼 **데이터 플라이휠**(§14)이 중요하다.

오프라인·릴리즈 판단은 **§10.7 Decision Utility**를 중심에 두고, nDCG 등 일반 IR 지표만으로 대체하지 않는다. Conformal(§8.5)은 **보조** 게이트로만 도입한다.

14. Query distribution & data flywheel (operational SSOT)

설계만으로 끝나지 않는다. 운영에서 **쿼리 분포·실패·클릭**이 누적되며, 이 엔진은 retrieval stack이 아니라 **data flywheel system**에 가깝다 (모델보다 데이터가 우선하는 경우가 많다).

14.1 Feedback loop — 입력

- user queries (원문·로케일·세션)
- clicks / skips / dwell (가능한 범위)
- reformulations (같은 의도 추정)
- **failures** (wrong-top1, no-click, explicit negative)
- clarification responses (사용자가 고른 후보)

14.2 Feedback loop — 파이프라인 (출력이 SSOT·정책으로 환류)

- **alias expansion:** query log → `observed_query_alias` 후보 생성·검증·prior 갱신
- **constraint pattern mining:** 반복 패턴(가격대·포맷·지역) → planner·정규화 규칙
- **ambiguity pattern detection:** 예: “마고” → 항상 다의적 → Policy에 `require_clarification` 또는 높은 `T_ambiguous`
- **eval set 업데이트:** wrong-top1·사용자 수정 → gold / counterfactual 케이스 추가

14.3 특히 중요한 세 가지

1. **alias 자동 확장:** 로그에서 관측된 표기 → 타입·scope 붙여 SSOT 반영  
2. **ambiguity 패턴 학습:** 특정 surface form이 반복적으로 분기되면 확정 금지 정책으로 승격  
3. **실패 로그 기반 eval:** wrong-top1 → 오프라인 벤치에 편입, 회귀 방지

14.4 원칙

운영 없는 스펙은 incomplete다. **Query distribution**을 가정하지 말고, 로그로 분포를 측정하고 플라이휠을 돌린다.

14.5 Determinism & operational containment

**모델·인덱스·임계 프로파일**이 바뀌면 동일 쿼리도 결과가 달라질 수 있다. **DecisionSnapshot**, Replay API, threshold versioning, evidence obligation, drift·kill switch는 **RFC-015**(RFC-009·010·014와 연동)에서 정의한다. **`resolved`의 최종 closure**(identity sealing·snapshot·evidence·`FailureReason` SSOT)는 **RFC-016** Admission Gate에서 정의한다.
